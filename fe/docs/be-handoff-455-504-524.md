# BE 전달 사항: S15P11D202-455, 504, 524

작성일: 2026-08-04  
대상: 게시글 첨부파일·본문 이미지, 프로필 이미지 업로드 및 정적 파일 제공

## 먼저 확인할 공통 문제

현재 로컬 환경에서 게시글 본문 이미지를 선택하면 다음 요청이 실패한다.

```text
POST http://localhost:5173/backend/api/files/upload
Status: 500 Internal Server Error
```

FE는 `multipart/form-data`의 `file` 필드로 파일 하나를 전송한다. BE의
`FileController.uploadFile(@RequestParam("file") MultipartFile file)` 규격과 일치하므로,
현재 확인된 실패 지점은 FE 요청 생성 이후의 BE 파일 저장 처리다.

로컬 저장 경로와 관련해 확인된 내용은 다음과 같다.

- 저장소의 `be/.env`에는 Linux 배포용 값인 `FILE_UPLOAD_DIR=/home/ubuntu/ait/uploads/`가 설정되어 있다.
- 테스트를 수행한 BE 실행 환경은 Windows다.
- 현재 파일 저장 구현은 기본 경로 아래에 `boards`, `profiles` 하위 폴더를 만든 후 `MultipartFile.transferTo(...)`를 호출한다.
- 로컬의 `C:\home\ubuntu\ait\uploads\boards` 폴더는 존재하지만 비어 있으며, 실패한 요청으로 새 파일이 생성되지 않았다.
- 과거 업로드 파일은 `C:\aitserver\uploads` 바로 아래에 남아 있다. 즉, 하위 폴더 도입 전 경로와 도입 후 경로를 모두 고려해야 한다.

BE에서 우선 확인을 요청하는 항목:

1. 실행 중인 애플리케이션이 실제로 읽은 `file.upload.dir` 값을 시작 로그로 확인한다.
2. 로컬 Windows에서는 `FILE_UPLOAD_DIR=C:/aitserver/uploads/`처럼 절대 경로를 사용한다.
3. 업로드 루트를 `Path.toAbsolutePath().normalize()`로 정규화하고 `Files.createDirectories(...)`의 실패를 무시하지 않는다.
4. `MultipartFile.transferTo(...)`에 전달하는 대상이 실행 환경에서 실제 절대 경로인지 확인한다.
5. 원본 파일명이 `null`이거나 확장자가 없는 경우 `substring(lastIndexOf("."))`에서 500이 발생하지 않도록 검증한다.
6. 저장 실패 로그에 대상 디렉터리와 실제 예외 원인을 남긴다. 토큰이나 사용자 개인정보는 기록하지 않는다.
7. 잘못된 확장자·MIME·용량은 일반 500 대신 구분 가능한 4xx 응답으로 반환한다.

## S15P11D202-455: 게시글 첨부파일 처리 개선

### FE 반영 상태

FE 수정은 `develop`에 병합되어 있다.

- `storedFilename`이 `boards/uuid.ext` 형식이어도 폴더 구분자는 유지하고 각 경로 조각만 인코딩한다.
- 보호된 첨부파일은 Bearer 토큰을 포함한 요청으로 Blob을 받은 뒤 원본 파일명으로 다운로드한다.
- 게시글 상세 응답의 `files` 중 `usageType === "ATTACHMENT"`인 파일을 별도 목록으로 표시한다.
- 과거의 `uuid.ext` 형식과 현재의 `boards/uuid.ext` 형식을 모두 처리한다.

### BE 확인 요청

다음 계약이 단일·다중 업로드와 게시글 생성·수정·조회에서 동일하게 유지되어야 한다.

```text
POST /api/files/upload
multipart field: file
response data: "boards/{uuid}.{ext}"

POST /api/files/uploads
multipart field: files
response data: ["boards/{uuid}.{ext}", ...]
```

게시글 상세 조회의 각 파일에는 아래 값이 누락되지 않아야 한다.

```json
{
  "id": 1,
  "originalFilename": "면접자료.pdf",
  "storedFilename": "boards/{uuid}.pdf",
  "fileType": "PDF",
  "usageType": "ATTACHMENT"
}
```

추가 확인 사항:

- `GET /images/boards/{uuid}.{ext}`가 유효한 Bearer 토큰으로 200과 올바른 파일 본문을 반환하는지 확인한다.
- 파일 조회는 읽기 전용이어야 하며 DB 상태나 실제 파일을 변경·삭제하지 않아야 한다.
- `Content-Type`을 실제 파일에 맞게 반환한다.
- 과거 DB에 저장된 `uuid.ext` 경로도 `GET /images/{uuid.ext}`로 계속 조회할 수 있어야 한다.

## S15P11D202-504: 프로필 사진 등록 시 화면에서 튕기는 현상

### 관련 요청 흐름

FE는 프로필 사진 선택 시 다음 multipart 요청을 보낸다.

```text
PUT /api/users/me
request: application/json 파트
profileImage: 이미지 파일 파트
```

성공 응답의 `profileImageUrl`을 받은 뒤 FE가 해당 이미지를 인증 요청으로 다시 조회한다.

```text
GET /images/profiles/{uuid}.{ext}
Authorization: Bearer {accessToken}
```

이미지 조회가 401이면 현재 FE의 공통 인증 계층이 로그아웃 이벤트를 발생시키므로, 사용자는 프로필 사진 등록 직후 화면에서 튕긴 것처럼 느낄 수 있다. FE에서도 정적 이미지 401 처리 정책을 별도로 점검할 예정이지만, 먼저 BE에서 업로드 성공 여부와 이미지 조회 응답을 확인해야 한다.

### BE 확인 요청

- 프로필 업로드가 게시글과 동일한 공통 저장 로직을 사용하므로 `profiles` 디렉터리의 경로·생성 권한을 확인한다.
- `PUT /api/users/me`가 성공하면 응답의 `profileImageUrl`을 `/images/profiles/{uuid}.{ext}` 형식으로 일관되게 반환한다.
- 정상 access token을 포함한 이미지 조회가 401이 아닌 200을 반환하는지 확인한다.
- 프로필 수정 요청이나 이미지 조회가 access token을 무효화하거나 Redis blacklist에 등록하지 않는지 확인한다.
- 새 이미지 저장이 성공하기 전에 기존 프로필 이미지 파일을 삭제하지 않는다.
- DB 갱신 실패 시 새 파일을 정리하고 기존 이미지 경로는 유지해 데이터와 파일 상태가 어긋나지 않게 한다.
- 이미지 저장·조회 실패 시 BE 로그에서 저장 단계와 조회 단계를 구분할 수 있게 한다.

### 완료 조건

1. 프로필 이미지를 선택하면 `PUT /api/users/me`가 200을 반환한다.
2. 응답의 `profileImageUrl`을 조회하면 200과 이미지 본문이 반환된다.
3. 사용자의 인증 상태가 유지된다.
4. 새로고침 후에도 새 프로필 이미지가 표시된다.
5. 두 번째 이미지를 등록하면 새 이미지가 표시되고 기존 파일만 안전하게 정리된다.

## S15P11D202-524: 첨부파일 다운로드 후 본문 이미지가 깨지는 현상

### FE 반영 상태

FE 수정은 `develop`에 병합되어 있다.

- 본문 이미지 Blob URL을 DOM에 직접 주입하던 방식을 제거했다.
- 인증 조회로 얻은 Blob URL을 HTML 문자열에 반영한 뒤 렌더링한다.
- 첨부파일 다운로드로 부모 컴포넌트가 다시 렌더링되어도 본문 이미지의 `src`가 유지된다.

### 현재 검증 차단 원인

원래 현상을 검증하려면 먼저 본문 이미지를 업로드해야 하지만, 현재 로컬에서
`POST /api/files/upload`가 500을 반환한다. 따라서 FE 수정은 단위 테스트로는 통과했지만 실제 BE 연동 E2E 검증은 완료할 수 없다.

BE에서 공통 업로드 500을 해결한 뒤 다음 순서로 함께 확인이 필요하다.

1. 게시글 본문에 PNG 또는 JPEG 이미지를 추가한다.
2. 별도의 첨부파일을 추가한다.
3. 게시글을 저장하고 상세 화면으로 이동한다.
4. 본문 이미지가 정상적으로 표시되는지 확인한다.
5. 첨부파일을 다운로드한다.
6. 다운로드 전후로 본문 이미지가 그대로 유지되는지 확인한다.
7. 새로고침 후에도 본문 이미지와 첨부파일이 모두 정상인지 확인한다.

### BE 확인 요청

- 본문 이미지(`INLINE`)와 첨부파일(`ATTACHMENT`)이 같은 저장 경로 계약을 사용하되 게시글 상세 응답에서는 `usageType`으로 정확히 구분되어야 한다.
- 첨부파일 조회와 본문 이미지 조회는 서로 독립적인 읽기 요청이어야 한다.
- 파일 다운로드가 본문 이미지 파일이나 `PostFile` 레코드를 변경·삭제하지 않아야 한다.
- `storedFilename`의 `/`가 `%2F`로 전달되는 과거 요청과 `boards/...`로 전달되는 현재 요청의 호환성을 확인한다.

- BE에서 수행한 통합 테스트 또는 재현 결과
