# Ait Domain UX Rules

이 문서는 Ait 프론트엔드 화면의 정보 위계, 면접 흐름, AI 피드백과 UX Writing 기준이다. [design_guide.png](./design_guide.png)의 예약, 면접 진행, 기록과 리포트 예시를 도메인 규칙으로 구체화한다.

실제 API, WebRTC, 아이트래킹 또는 AI 분석 로직을 정의하지 않는다. 목업 상태는 실제 저장·녹화·분석이 완료된 것처럼 표현하지 않는다.

## 1. 핵심 사용자 흐름

화면은 다음 흐름을 일관되게 표현한다.

1. 진입 및 지원 정보 입력
2. 면접 유형과 일정 예약
3. 카메라·마이크·네트워크 환경 점검
4. 대기실
5. AI 모의면접 또는 화상 스터디 진행
6. 분석 대기
7. 피드백 리포트와 면접 기록 확인

예약 이후의 Stepper는 `환경 점검 → 대기실 → 면접 진행 → 리포트` 네 단계를 사용한다.

- 완료 단계: Check 아이콘과 완료된 연결선
- 현재 단계: 단계 번호, 강조 ring과 단계명
- 예정 단계: Neutral 색상과 단계 번호
- 현재 위치는 색상만이 아니라 아이콘, 번호와 텍스트로 함께 전달한다.

## 2. 화면 공통 원칙

- 화면마다 사용자가 지금 해야 할 핵심 행동을 하나로 명확히 한다.
- 진행 상태, 남은 단계와 다음 행동을 숨기지 않는다.
- 목업 데이터와 미연동 기능을 실제 완료된 데이터처럼 표현하지 않는다.
- Loading, Empty, Error, Disabled 상태에서도 화면의 목적과 다음 행동을 이해할 수 있어야 한다.
- 같은 개념과 상태에는 모든 화면에서 같은 용어와 아이콘을 사용한다.
- 운영 상태와 평가 결과를 같은 Badge로 혼용하지 않는다.

운영 상태의 기본 용어는 `예정 · 준비 완료 · 진행 중 · 분석 중 · 완료`다. 상태를 추가할 때는 기존 용어로 표현할 수 없는지 먼저 확인한다.

## 3. 면접 예약과 예정된 면접

### 예약 Form

- 지원 직무, 면접 유형, 날짜와 시간처럼 예약에 필요한 정보를 Label과 함께 제공한다.
- `지원 직무`와 `면접 유형`을 혼용하지 않는다.
- 검증 실패 시 입력값은 유지하고 잘못된 항목 가까이에 해결 문구를 표시한다.
- 예약 화면의 Primary 행동은 `면접 예약하기` 하나로 둔다.
- 실제 저장 연동이 없으면 로컬 목업 예약임을 코드 구조와 화면 맥락에서 구분한다.

### Interview Card

예정된 면접 Card는 다음 순서로 정보를 보여준다.

1. 면접 유형과 세부 유형
2. 상태 Badge
3. 날짜와 시간
4. 환경 점검 기반 준비도
5. `면접 시작` 행동

- `준비 완료`는 필요한 점검이 모두 완료된 상태에서만 사용한다.
- 준비도는 Progress와 `80%` 같은 수치를 함께 제공하되, 근거 없이 임의의 진행률을 만들지 않는다.
- 시작할 수 없는 경우 버튼만 Disabled로 두지 않고 미완료 항목과 해결 행동을 함께 표시한다.
- Card 안의 Primary 행동은 하나만 둔다.

### Empty State

예정된 면접이 없을 때는 다음 구조를 사용한다.

- 제목: `예정된 면접이 없습니다`
- 안내: `새로운 모의면접을 예약하고 준비를 시작해 보세요.`
- CTA: `면접 예약하기`

## 4. 환경 점검

- 카메라, 마이크와 네트워크 상태를 각각 구분해 보여준다.
- 권한을 요청하기 전에 권한이 필요한 이유를 설명한다.
- 권한 거부, 장치 없음, 점검 실패와 다시 시도 상태를 각각 디자인한다.
- 실제 장치 제어는 현재 범위가 아니며 화면 상태와 안내 흐름만 구현한다.
- `다시 시도`, `설정 확인`, `대기실로 이동`처럼 해결 행동을 구체적으로 표시한다.

권장 피드백은 다음과 같다.

| 상태 | 문구 | 후속 행동 |
| --- | --- | --- |
| Success | `카메라와 마이크 환경 점검이 완료되었습니다.` | `대기실로 이동` |
| Warning | `네트워크가 불안정합니다. 연결을 확인해 주세요.` | `다시 확인` |
| Error | `마이크를 찾을 수 없습니다.` | `설정 확인` |
| 권한 거부 | `카메라를 사용할 수 없습니다. 브라우저 설정에서 권한을 허용해 주세요.` | `권한 설정 확인` |

완료 문구는 실제 점검 결과 또는 명시적인 목업 상태가 완료일 때만 사용한다.

## 5. 대기실

- 면접 유형, 시작 조건과 현재 준비 상태를 보여준다.
- 카메라·마이크 상태와 면접 시작 행동을 한눈에 확인할 수 있게 한다.
- 준비되지 않은 항목이 있으면 시작 버튼의 비활성 이유와 해결 행동을 함께 제공한다.
- 면접 시작은 화면의 Primary 행동으로 취급한다.
- 면접 시작 전에는 `면접을 시작할까요?` Dialog로 점검 완료 상태를 다시 알리고, `취소`와 `면접 시작` 행동을 제공한다.
- `실전`과 `연습` 같은 모드가 있으면 Segmented Control 또는 Radio로 하나만 선택하게 한다.

## 6. 면접 진행

- 현재 질문, 영상 영역과 진행 상태를 가장 먼저 보여준다.
- 질문 순서, 남은 시간, 카메라와 마이크 상태를 항상 확인할 수 있게 한다.
- 녹화 또는 분석 중임을 알리는 시각적 상태를 제공한다.
- 연결 문제나 분석 지연 상태에서도 사용자가 데이터가 사라졌다고 오해하지 않게 안내한다.
- 면접 종료에는 확인 Dialog를 제공한다.
- 반복되는 장식 애니메이션이나 집중을 방해하는 효과를 사용하지 않는다.

실제 녹화, 연결, 장치 제어와 재연결 로직은 구현 범위에 포함하지 않는다.

## 7. 분석 대기

- 현재 처리 중인 단계와 예상되는 다음 화면을 설명한다.
- 진행률을 알 수 없을 때 임의의 퍼센트를 표시하지 않는다.
- 오래 걸리는 상황을 위한 안내와 다시 확인할 수 있는 행동을 제공한다.
- 완료되지 않은 결과를 완성된 리포트처럼 미리 보여주지 않는다.
- 실제 완료 신호가 없으면 자동으로 `리포트` 단계가 완료된 것처럼 전환하지 않는다.

## 8. 피드백 리포트

정보는 다음 순서로 제공한다.

1. 리포트 제목과 결과 맥락
2. Radar Chart와 종합 점수
3. 종합 평가
4. 항목별 점수
5. 관찰 근거와 개선 행동
6. 분석 범위와 한계 안내

기본 평가 항목은 `논리력 · 표현력 · 순발력 · 태도 · 직무 전문성 · 자신감`이다.

면접 상세를 Tabs로 나누는 경우 `면접 개요 · 질문 목록 · 피드백 · 리포트` 순서를 사용한다. 아직 생성되지 않은 피드백이나 리포트는 빈 완료 화면으로 보여주지 않고 처리 상태와 확인 가능한 시점을 안내한다.

- 종합 점수를 단독으로 강조하지 않고 항목별 근거와 개선 행동을 함께 보여준다.
- Radar Chart와 동일한 값을 텍스트 또는 표로도 제공한다.
- 점수 범위는 `/ 10점`처럼 단위를 명시하며, 확정된 평가 계약이 없으면 임의의 점수를 생성하지 않는다.
- 잘한 점과 개선할 점을 균형 있게 제공한다.
- 관찰된 행동과 가능한 인상을 시각적으로 구분한다.
- 결과가 참고용이며 분석에 한계가 있다는 안내를 제공한다.
- Gold는 최고 점수, `우수`와 같이 승인된 성취 요소에만 제한적으로 사용한다.

### 결과와 성취 문구

- `우수`는 정의된 점수 구간이나 평가 기준이 있을 때만 종합 평가로 사용한다.
- `합격`은 AI가 추론하거나 생성하는 결과로 사용하지 않는다.
- `합격` Badge는 외부에서 확정된 채용 결과이거나, 합격 상태가 명시된 승인 목업임을 사용자가 오해하지 않는 맥락에서만 표시한다.
- AI 모의면접 리포트에는 합격 가능성, 적합 여부나 채용 결정을 암시하는 Badge를 표시하지 않는다.

### AI 표현 원칙

- AI 결과를 합격 여부나 사람의 감정을 확정하는 판단처럼 표현하지 않는다.
- 의학적 진단, 성격 평가나 차별적 판단처럼 읽힐 수 있는 표현을 피한다.
- 가능성과 관찰 근거를 중심으로 작성한다.
- `자신감`이 평가 항목명이더라도 사용자의 내적 감정을 단정하지 않는다.

권장:

- `긴장 상태로 보일 수 있는 움직임이 감지됐어요.`
- `답변 중 시선이 화면 밖에 머문 구간이 있었어요.`
- `핵심 경험을 먼저 말하면 답변을 더 쉽게 이해할 수 있어요.`

피해야 할 표현:

- `긴장했습니다.`
- `자신감이 부족합니다.`
- `면접에 적합하지 않습니다.`

## 9. 면접 기록

면접 기록 Table은 `면접 유형 · 날짜 · 점수 · 결과` 순서로 구성한다.

- 날짜, 면접 유형, 진행 상태와 리포트 확인 행동을 명확히 구분한다.
- 점수와 결과는 분석 또는 외부 결과가 실제로 존재할 때만 표시한다.
- 화면은 하나의 `결과` 열을 사용할 수 있지만 데이터 의미는 구분한다. `합격`은 채용 결과, `우수 · 보통`은 평가 등급으로 모델링하고 Badge의 접근 가능한 이름이나 보조 문구에도 구분을 반영한다.
- 모바일에서는 각 행을 Card로 바꾸더라도 열 Label의 의미가 사라지지 않게 한다.
- 기록이 없을 때는 Empty State와 첫 면접을 시작하거나 예약할 수 있는 CTA를 제공한다.
- 목업 목록은 실제 저장된 사용자 기록처럼 오해되지 않게 전용 fixture 또는 mock 모듈에 둔다.

## 10. 상태와 피드백

- Loading은 Skeleton을 사용하고 데이터 구조를 예측할 수 있게 한다.
- Empty State는 현재 상황, 짧은 안내와 다음 행동을 함께 제공한다.
- Error는 원인 또는 현재 상황과 해결 행동을 함께 제공한다.
- Disabled 상태에는 비활성 이유를 가까운 위치에 표시한다.
- Toast는 짧은 완료 결과, Alert는 사용자가 계속 확인해야 하는 상태에 사용한다.
- `면접 결과가 저장되었습니다.` Toast와 `리포트 보기` 행동은 저장 성공이 실제로 확인된 뒤에만 표시한다.

## 11. UX Writing

문장 톤은 `간결 · 긍정 · 차분 · 신뢰`다.

- 문장은 짧고 차분한 한국어로 작성한다.
- 버튼은 `확인`, `다음`보다 행동을 설명하는 동사형을 사용한다.
- 성취 문구는 긍정적이고 간결하게 작성하되 사실로 확인된 범위를 넘지 않는다.
- 사용자를 비난하거나 불안하게 만드는 표현을 피한다.
- 오류 문구에는 현재 상황과 해결 행동을 함께 쓴다.
- 기술 오류 메시지를 그대로 노출하지 않고 이해할 수 있는 안내로 바꾼다.

| 상황 | 권장 문구 |
| --- | --- |
| 면접 시작 | `면접 시작` |
| 결과 저장 | `결과 저장` |
| 지원 정보 저장 | `지원 정보 저장하기` |
| 필수값 누락 | `지원 직무를 입력해 주세요.` |
| 점검 완료 | `환경 점검이 완료되었습니다.` |
| 네트워크 경고 | `네트워크가 불안정합니다. 연결을 확인해 주세요.` |
| 장치 오류 | `마이크를 찾을 수 없습니다. 설정을 확인해 주세요.` |
| 기록 없음 | `아직 완료한 면접이 없습니다. 첫 면접을 시작해 보세요.` |

## 12. 개인정보와 신뢰 표현

- 카메라, 마이크, 녹화와 분석 여부를 화면에서 숨기지 않는다.
- 개인정보나 녹화 데이터가 저장됐다고 실제 연동 없이 단정하지 않는다.
- 권한 허용을 유도하기 위해 불안감을 조성하거나 기능을 과장하지 않는다.
- 보안과 개인정보 관련 문구는 확정된 정책이 없으면 임의로 작성하지 않는다.
- 목업에서 저장·녹화·분석 상태를 보여줄 때는 실제 서비스 보장으로 읽히지 않도록 화면과 코드에서 목업임을 분리한다.
