# Ait Frontend UI Agent Guide

이 문서는 Ait 프론트엔드 UI를 구현하는 AI 코딩 에이전트와 팀원이 따르는 작업 절차다. 프로젝트·제품·디자인 기준은 `CLAUDE.md`를 우선한다.

## 1. 작업 범위

현재 저장소에서는 React 기반 웹 화면과 공통 UI를 구현한다.

- 레이아웃, 컴포넌트, 스타일, 반응형 화면
- 화면 이동을 위한 클라이언트 라우팅
- 접근성과 인터랙션 상태
- 화면 확인용 로컬 상호작용과 목업 데이터

백엔드, 실제 API 연동, 서버 상태 관리, WebRTC, 아이트래킹 데이터 처리, AI 모델과 인프라는 현재 범위가 아니다. 관련 로직을 임의로 추가하지 않는다.

## 2. 지시 우선순위

충돌하는 지시가 있으면 다음 순서로 판단한다.

1. 사용자가 현재 작업에서 명시한 요구사항
2. `CLAUDE.md`
3. 팀이 승인한 최신 Figma 화면
4. `docs/design-system.md`와 `docs/domain-rules.md`
5. 이 `AGENTS.md`의 작업 절차
6. 기존 코드의 구조와 패턴
7. 라이브러리 기본값과 일반적인 관례

- Figma와 문서가 다르면 최신 Figma를 우선하고 차이를 보고한다.
- 설치 상태, 스크립트, 빌드 설정은 `package.json`과 실제 설정 파일로 확인한다.
- 요구사항이 모호하면 기존 화면과 공통 컴포넌트를 먼저 조사하고, 결과를 크게 바꾸는 선택만 질문한다.

## 3. 작업 시작 전 조사

코드를 수정하기 전에 다음을 확인한다.

1. 관련 페이지, 라우트, 레이아웃과 화면 흐름
2. 재사용 가능한 공통 UI와 도메인 컴포넌트
3. 디자인 토큰과 최신 Figma 화면
4. 사용할 수 있는 로고, 이미지와 아이콘 에셋
5. Loading, Empty, Error, Disabled 등 필요한 화면 상태
6. 모바일·태블릿·데스크톱 레이아웃
7. 키보드 탐색, Label, 대체 텍스트, Focus 상태

검색은 파일명 추측보다 `rg`와 `rg --files`를 우선한다. 수정 범위는 요청에 필요한 최소 단위로 유지한다.

## 4. 프론트엔드 UI 구조

### 4.1 페이지와 컴포넌트

- 페이지 컴포넌트는 레이아웃과 하위 UI 조합을 담당한다.
- 공통 UI는 특정 페이지나 목업 데이터 구조에 직접 의존하지 않게 한다.
- 같은 역할의 컴포넌트를 새로 만들기 전에 기존 variant 확장을 검토한다.
- 한 컴포넌트에 대규모 레이아웃과 여러 독립 인터랙션을 모두 넣지 않는다.
- 반복되는 화면 패턴은 공통 컴포넌트로 추출하되, 한 번만 쓰이는 작은 마크업을 성급하게 추상화하지 않는다.

### 4.2 로컬 상태와 목업 데이터

- 탭, Dialog, Accordion, Carousel처럼 UI 확인에 필요한 상태는 컴포넌트 지역 상태로 관리한다.
- 화면 확인용 데이터는 전용 fixture 또는 mock 모듈에 두고 목업임을 명확히 한다.
- 실제 API 요청, 인증, 업로드, 실시간 연결을 구현하지 않는다.
- API URL, 서버 응답 타입, 임의의 fallback 계약을 만들지 않는다.
- 서버 연동이 필요한 버튼은 시각 상태와 예상 흐름까지만 구현하고 실제 완료 동작처럼 속이지 않는다.

### 4.3 라우팅

- 여러 화면 사이의 이동을 확인해야 할 때만 React Router 도입을 검토한다.
- URL 구조는 화면 역할을 이해할 수 있게 작성한다.
- 인증 Guard나 서버 기반 접근 제어는 현재 범위에 포함하지 않는다.

### 4.4 주석 작성

- 코드만 봐서는 알기 어려운 비자명한 로직(우회 처리, 숨은 제약, 특정 버그 대응)에만 주석을 남기고, 코드가 이미 보여주는 내용을 그대로 풀어 쓰지 않는다.
- 주요 컴포넌트나 함수 상단에는 구현 방식이 아니라 책임과 역할을 한 줄로 설명하는 주석을 남긴다.
- 목업 데이터나 실제 연동이 빠진 부분에는 `// TODO: 실제 API 연동 필요` 형식으로 남은 작업을 표시한다.
- 주석은 `~한다` 평서체로 통일하고 한 문장으로 간결하게 쓴다. 대상 이름을 문장에서 반복하지 않는다.
- 작업을 완료한 뒤 위 기준에 맞는 주석이 빠진 곳이 없는지 확인한다.

```tsx
// 좋음 — 책임 한 줄 (구현 방식이 아니라 역할)
// 마이페이지. 프로필과 등록 자료를 불러와 보여주고, 저장소 조회는 별도로 재시도할 수 있다.
export function MyPage() { ... }

// 좋음 — 코드만으로는 드러나지 않는 이유를 설명
// StrictMode의 개발용 이중 마운트로 연동 요청이 두 번 나가지 않도록 한 번만 실행한다.
if (hasRequestedRef.current) return

// 나쁨 — 코드가 이미 보여주는 내용을 그대로 반복
// user를 가져온다
const { user } = useAuth()
```

### 4.5 커밋 메시지

- 커밋 메시지는 `<type>: <한국어 요약>` 형식으로 작성한다.
  - `type`: `feat`(기능), `fix`(버그 수정), `docs`(문서·주석), `style`(포맷·스타일 변경), `refactor`(동작 변화 없는 구조 개선), `test`(테스트), `chore`(설정·빌드)
  - 요약은 무엇을 했는지 한국어로 간결하게 쓴다. 예: `docs: pages 화면 컴포넌트에 역할 주석 추가`
  - 세부 설명이 필요하면 한 줄 비우고 `- ` 불릿으로 무엇을·왜를 적는다.
- 한 커밋에는 하나의 논리적 작업만 담고, 성격이 다른 변경(예: 기능 구현과 주석 정리)은 나눠 커밋한다.
- 요청 범위와 무관한 작업 트리 변경은 함께 스테이징하지 않는다.

## 5. 디자인 시스템

구체적인 색상, 타이포그래피, 간격, radius, elevation, z-index, 모션과 컴포넌트 상태는 `docs/design-system.md`를 단일 기준으로 사용한다.

- 임의의 hex, 크기, 간격, radius, 그림자, z-index를 추가하지 않는다.
- 그림자는 `elevation-1`, `elevation-2`, `elevation-3` 명칭만 사용한다.
- 색상만으로 상태를 전달하지 않고 문구나 아이콘을 함께 제공한다.
- shadcn/ui 기본 스타일은 Ait 토큰에 맞게 조정한다.
- 모든 모션은 `prefers-reduced-motion`을 반영한다.

## 6. 접근성과 반응형

- 본문 텍스트는 WCAG AA 기준인 `4.5:1` 이상의 대비를 확보한다.
- 모든 인터랙티브 요소에 명확한 `focus-visible` 스타일을 제공한다.
- `outline: none`을 사용할 때는 동등하거나 더 명확한 Focus 스타일이 있어야 한다.
- 아이콘 버튼에는 접근 가능한 이름을 제공한다.
- 의미 있는 이미지에는 대체 텍스트를 제공하고 장식 이미지는 보조기술에서 제외한다.
- 모든 입력 요소에는 화면에 보이는 Label을 제공하고 Placeholder로 대체하지 않는다.
- Dialog가 열리면 포커스를 내부에 유지하고 닫힌 뒤 원래 요소로 돌려보낸다.
- 키보드만으로 주요 화면 흐름을 확인할 수 있어야 한다.
- 모바일·태블릿·데스크톱에서 콘텐츠가 잘리거나 주요 행동이 사라지지 않아야 한다.

## 7. Ait 화면과 문구

면접 단계, AI 피드백 표현, 오류와 안내 문구의 기준은 `docs/domain-rules.md`를 따른다.

- 질문, 영상 영역, 진행 상태의 시각적 우선순위를 유지한다.
- 녹화·분석·권한 사용 여부를 숨기지 않는 화면을 디자인한다.
- AI 결과를 합격 여부나 감정에 대한 확정적 판단처럼 표현하지 않는다.
- 오류 문구에는 상황과 사용자가 취할 수 있는 다음 행동을 함께 제공한다.
- 같은 개념에는 모든 화면에서 같은 용어를 사용한다.

## 8. 금지 사항

- 요청 범위와 무관한 대규모 리팩터링
- 기존 사용자 변경사항 덮어쓰기
- 근거 없는 의존성이나 UI 라이브러리 도입
- 실제 API, 서버 상태, 인증, WebRTC 또는 데이터 처리 로직 구현
- 목업 화면을 실제 연동이 완료된 것처럼 표현
- 공통 토큰을 우회한 임의 스타일 값
- 같은 역할의 공통 컴포넌트 중복 생성
- 접근성 Focus 제거
- 골드 색상의 일반 CTA·강조 사용
- AI 분석 결과의 단정적·의학적·차별적 표현
- 테스트나 빌드 통과를 위한 기능 삭제, 타입 검사 우회, 광범위한 lint 예외
- 비밀키, 토큰, 개인정보 또는 녹화 데이터 커밋

## 9. 검증

코드를 변경한 경우 실제 `package.json`에 정의된 명령을 영향 범위에 맞게 실행한다.

```bash
npm run lint
npm run typecheck
npm run build
```

- `lint`: ESLint로 코드 규칙과 React Hooks 사용을 검사한다.
- `typecheck`: 결과물을 만들지 않고 TypeScript 타입 오류를 검사한다.
- `build`: 타입 검사 후 배포용 결과물이 정상 생성되는지 확인한다.
- UI 변경은 관련 화면을 모바일·태블릿·데스크톱 크기에서 확인한다.
- Hover, Focus, Active, Disabled, Loading, Empty, Error 상태 중 화면에 해당하는 상태를 확인한다.
- 문서만 변경한 경우 Markdown 구조, 링크, 중복과 오래된 참조를 확인한다.

현재 자동 테스트 도구와 `test` 스크립트는 없다. 추후 도입되면 변경 범위에 맞는 테스트를 실행한다.

실행하지 못한 검증은 성공한 것처럼 말하지 않고 항목과 이유를 최종 보고에 명시한다.

## 10. 완료 체크리스트

- [ ] 요청한 화면 범위만 수정했는가?
- [ ] 기존 레이아웃과 공통 컴포넌트를 재사용했는가?
- [ ] 목업 데이터와 UI 컴포넌트가 분리되어 있는가?
- [ ] 필요한 Loading, Empty, Error, Disabled 상태가 표현되어 있는가?
- [ ] Primary 버튼이 핵심 행동 하나에만 사용됐는가?
- [ ] 색상, 타입, 간격, radius, elevation, z-index가 토큰을 사용하는가?
- [ ] 모바일·태블릿·데스크톱에서 주요 콘텐츠와 행동을 사용할 수 있는가?
- [ ] 키보드 탐색, Label, 대체 텍스트, Focus, 대비 기준을 지켰는가?
- [ ] AI 문구가 근거와 한계를 포함하고 단정적이지 않은가?
- [ ] 화면을 실제 서버 연동이 완료된 것처럼 오해하게 만들지 않았는가?
- [ ] 비자명한 로직 설명, 컴포넌트/함수 역할 주석, 미구현 지점 TODO가 필요한 곳에 남아 있는가?
- [ ] 주석이 평서체로 통일되어 있고, 코드가 이미 보여주는 내용을 반복하지 않는가?
- [ ] 커밋을 나눈다면 `<type>: <요약>` 형식을 따르고, 논리적 작업 단위로 분리했는가?
- [ ] 변경 범위에 맞는 lint, typecheck, build와 수동 확인을 수행했는가?

## 11. 작업 결과 보고

작업 완료 시 다음을 간결하게 보고한다.

1. 무엇을 변경했는지
2. 사용자에게 보이는 화면이나 동작이 어떻게 달라졌는지
3. 어떤 검증을 실행했고 결과가 어땠는지
4. 목업 처리, 미구현 연동, 남은 확인 사항

파일 목록만 나열하지 말고 결과 중심으로 설명한다.
