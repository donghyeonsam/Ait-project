# Ait Agent Guide

이 문서는 Ait 저장소에서 작업하는 AI 코딩 에이전트와 팀원이 따라야 할 구현 기준이다.
목표는 기능 구현 속도보다 **기존 구조의 보존, UX/UI 일관성, 접근성, 면접 서비스의 신뢰성**을 우선하는 것이다.

## 1. 프로젝트 개요

Ait는 WebRTC 기반 AI 면접 훈련 및 화상 면접 스터디 서비스다.

주요 사용자 흐름:

1. 로그인 및 지원 정보 입력
2. 면접 유형과 일정 설정
3. 카메라·마이크·네트워크 환경 점검
4. AI 모의면접 또는 화상 스터디 진행
5. 녹화·STT·행동 분석 결과 확인
6. 피드백 리포트와 면접 기록 관리

핵심 디자인 키워드는 `Professional · Trustworthy · Focused`다.

## 2. 지시 우선순위

충돌하는 지시가 있으면 다음 순서로 판단한다.

1. 사용자가 현재 작업에서 명시한 요구사항
2. 프로젝트·제품·디자인 기준을 정의하는 `CLAUDE.md`
3. 저장소의 최신 기획·디자인 문서와 Figma 디자인 시스템
4. 에이전트 작업 절차를 정의하는 이 `AGENTS.md`
5. 기존 코드의 구조와 패턴
6. 라이브러리 기본값과 일반적인 관례

요구사항이나 디자인이 모호할 때는 임의의 새 규칙을 만들지 않는다. 기존 화면과 공통 컴포넌트를 먼저 조사하고, 결과를 크게 바꾸는 선택만 사용자에게 질문한다.

- 디자인 토큰과 최신 Figma가 다르면 `CLAUDE.md`에 따라 Figma를 우선하고 차이를 사용자에게 알린다.
- 설치된 의존성, 실행 가능한 스크립트, 빌드 설정은 `package.json`과 실제 설정 파일을 기준으로 확인한다.

## 3. 기준 문서와 역할

- 프로젝트·제품·디자인 규칙의 현재 기준: `CLAUDE.md`
- 상세 디자인 규칙 전체: 작성 예정인 `docs/Ait_UX_UI_그라운드룰_v2.md`
- 실제 구현된 토큰의 기준: 저장소의 `globals.css`, Tailwind 설정, 공통 UI 컴포넌트
- 화면 구조와 최신 시안의 기준: 팀이 지정한 최신 Figma 화면

> 작성 예정 문서는 생성된 뒤 실제 경로에 맞게 수정한다. 존재하지 않는 문서나 설정을 현재 구현처럼 가정하지 않는다.

디자인 문서 전체를 컴포넌트에 다시 하드코딩하지 않는다. 색상, 타이포그래피, 간격, 반경, 그림자, 모션은 반드시 공통 토큰을 통해 사용한다.

## 4. 목표 기술 스택과 역할

- React + TypeScript + Vite
- React Router: 페이지 라우팅
- TanStack Query: 서버 상태 조회·캐시·동기화
- Zustand: 여러 화면에서 공유되는 클라이언트 상태
- Tailwind CSS: 레이아웃과 토큰 기반 스타일링
- shadcn/ui: 공통 UI의 기반
- React Hook Form + Zod: 폼 상태와 입력 검증
- LiveKit React SDK: 화상 면접과 미디어 세션
- Lucide React: 아이콘
- ESLint: 정적 검사 (Oxlint 대신 채택)

현재 저장소의 `package.json`과 기존 구현이 이 목록과 다르면 저장소를 우선하며, 의존성을 임의로 추가하거나 교체하지 않는다.

## 5. 작업 시작 전 조사

코드를 수정하기 전에 다음을 확인한다.

1. 관련 페이지, 라우트, 기능 모듈, API 호출 위치
2. 재사용 가능한 shadcn/ui 및 Ait 공통 컴포넌트
3. 색상·간격·타이포그래피·모션 토큰
4. 로딩, 빈 상태, 오류, 권한 거부, 연결 끊김 처리
5. 모바일·태블릿·데스크톱에서 달라지는 동작
6. 같은 기능을 검증하는 기존 테스트

검색은 파일명 추측보다 `rg`와 `rg --files`를 우선한다. 수정 범위는 요청에 필요한 최소 단위로 유지한다.

## 6. 아키텍처 규칙

### 6.1 상태 관리

- 서버에서 가져온 데이터는 TanStack Query로 관리한다.
- 단일 컴포넌트 또는 단일 폼의 상태는 지역 상태나 React Hook Form으로 관리한다.
- 여러 비연관 화면이 공유하는 클라이언트 상태만 Zustand에 둔다.
- 서버 응답을 Zustand에 중복 저장하지 않는다.
- URL로 표현 가능한 검색 조건, 탭, 페이지 번호는 가능한 한 URL 상태로 유지한다.

### 6.2 컴포넌트

- 페이지 컴포넌트는 데이터 조합과 화면 구성을 담당한다.
- 공통 UI 컴포넌트는 특정 API 응답 구조에 직접 의존하지 않게 한다.
- 같은 기능의 컴포넌트를 새로 만들기 전에 기존 컴포넌트의 variant 확장을 검토한다.
- 한 컴포넌트에 데이터 조회, 미디어 제어, 복잡한 폼, 대규모 레이아웃을 모두 넣지 않는다.
- shadcn/ui 기본 스타일은 그대로 노출하지 않고 Ait 토큰으로 오버라이드한다.

shadcn/ui Coverage Map과 화면별 컴포넌트 조합은 중복 정의하지 않고 `CLAUDE.md`를 따른다. 목록에 없는 컴포넌트는 필요하다는 근거와 팀 합의 없이 추가하지 않는다.

### 6.3 API와 타입

- API 응답 타입을 `any`로 우회하지 않는다.
- 외부 입력과 서버 응답 중 검증이 필요한 값은 Zod 스키마를 사용한다.
- 컴포넌트 내부에서 API URL을 직접 조합하지 않는다.
- 오류를 삼키지 말고 사용자가 취할 수 있는 다음 행동과 함께 표시한다.
- 백엔드 계약이 불명확하면 가짜 필드나 임의의 fallback 데이터를 추가하지 않는다.

### 6.4 WebRTC·LiveKit

- 카메라·마이크 권한 요청 전 사용 목적을 안내한다.
- 권한 거부, 장치 없음, 장치 변경, 네트워크 불안정, 재연결 상태를 각각 처리한다.
- 트랙과 이벤트 리스너는 화면 이탈 또는 세션 종료 시 정리한다.
- 면접 종료는 실수로 실행되지 않도록 확인 절차를 둔다.
- 연결 상태, 카메라, 마이크, 남은 시간, 질문 순서는 면접 중 항상 확인 가능해야 한다.
- 미디어 오류의 기술 메시지를 그대로 노출하지 말고 이해할 수 있는 한국어 안내로 변환한다.

## 7. 디자인 시스템 적용

색상, 타이포그래피, 간격, 반경, elevation, 모션, 컴포넌트 상태의 구체적인 값은 `CLAUDE.md`를 단일 기준으로 사용한다. 이 문서에는 작업 시 확인할 원칙만 둔다.

### 7.1 레이아웃과 간격

- 최신 Figma와 `CLAUDE.md`의 레이아웃·간격 토큰을 사용한다.
- 모바일·태블릿·데스크톱에서 핵심 기능이 유지되는지 확인한다.

### 7.2 색상

- 컴포넌트에 색상을 하드코딩하지 않고 정의된 토큰을 사용한다.
- 색상만으로 상태를 전달하지 않고 문구 또는 아이콘을 함께 제공한다.

### 7.3 타이포그래피와 시각 토큰

- 타이포그래피, radius, z-index에 임의 값을 추가하지 않는다.
- 그림자는 `elevation-1`, `elevation-2`, `elevation-3` 토큰만 사용한다.

### 7.4 버튼과 폼

- 한 화면 또는 한 명확한 작업 영역의 Primary 버튼은 1개만 둔다.
- 버튼 문구는 `확인`, `다음`보다 `면접 시작`, `환경 점검으로 이동`처럼 행동을 설명하는 동사형으로 쓴다.
- 파괴적 행동과 면접 종료에는 확인 Dialog를 제공한다.
- 모든 입력 요소에 화면에 보이는 Label을 제공하고 Placeholder로 대체하지 않는다.
- 오류 메시지는 해당 입력 가까이에 원인과 해결 방법을 함께 표시한다.
- 검증 실패 후에도 사용자가 입력한 값은 유지한다.

### 7.5 필수 상태와 피드백

- 해당하는 인터랙티브 상태는 `CLAUDE.md`의 상태 기준을 따라 구현한다.
- 로딩 중에는 중복 제출과 중복 클릭을 방지한다.

### 7.6 모션

- 모션 값과 React Bits 허용 범위는 `CLAUDE.md`를 따른다.
- 모든 모션은 `prefers-reduced-motion`을 반영한다.
- 면접 진행 화면에는 반복 장식 애니메이션을 넣지 않는다.

### 7.7 아이콘과 로고

- 아이콘 값과 로고 사용 규칙은 `CLAUDE.md` 및 로고 에셋 가이드를 따른다.
- 같은 의미에는 같은 아이콘을 사용한다.
- 로고는 비율을 유지하고 임의 색상 변경을 하지 않는다.

## 8. 접근성

- 본문 텍스트 대비는 WCAG AA 기준인 `4.5:1` 이상을 확보한다.
- 모든 인터랙티브 요소에 3px Navy 25% focus ring을 유지한다.
- `outline-none`을 사용할 때는 동등하거나 더 명확한 focus-visible 스타일이 있어야 한다.
- 아이콘 버튼에는 접근 가능한 이름과 필요한 경우 Tooltip을 제공한다.
- 이미지에는 목적에 맞는 대체 텍스트를 제공하고, 장식 이미지는 보조기술에서 제외한다.
- 모달이 열리면 포커스를 내부에 유지하고 닫힌 뒤 원래 요소로 돌려보낸다.
- 키보드만으로 핵심 흐름을 완료할 수 있어야 한다.

## 9. Ait 도메인 UX 원칙

### 9.1 면접 진행

- 질문, 영상, 진행 상태를 가장 먼저 보여준다.
- `환경 점검 → 대기실 → 면접 진행 → 리포트`의 현재 단계를 표시한다.
- 녹화·분석 중이라는 사실과 사용되는 권한을 숨기지 않는다.
- 연결 문제나 분석 지연 시 데이터가 사라진 것처럼 보이지 않게 상태를 설명한다.

### 9.2 AI 피드백

- 종합 점수만 단독으로 제시하지 않고 항목별 근거와 개선 행동을 함께 제공한다.
- AI 결과를 합격 여부나 사람의 감정을 확정하는 판단처럼 표현하지 않는다.
- 관찰된 행동과 가능한 인상을 구분한다.
- `긴장했습니다`보다 `긴장 상태로 보일 수 있는 움직임이 감지됐어요`처럼 가능성 중심으로 쓴다.
- 결과가 참고용이며 분석에 한계가 있음을 알린다.
- 잘한 점과 개선할 점을 균형 있게 제공한다.

### 9.3 UX Writing

- 문장은 짧고 차분한 한국어로 작성한다.
- 사용자를 비난하거나 불안하게 만드는 표현을 피한다.
- 오류 문구에는 상황과 해결 행동을 함께 쓴다.
- 같은 개념의 용어는 모든 화면에서 동일하게 사용한다.

## 10. 금지 사항

- 요청 범위와 무관한 대규모 리팩터링
- 기존 사용자 변경사항 덮어쓰기
- 근거 없는 새 의존성, 상태 관리 도구, UI 라이브러리 도입
- 공통 토큰을 우회한 임의 색상·크기·간격·반경·그림자·z-index
- 같은 기능의 공통 컴포넌트 중복 생성
- 접근성 focus 제거
- 골드 색상의 일반 강조·CTA 사용
- AI 분석 결과의 단정적·의학적·차별적 표현
- 카메라·마이크 권한 및 녹화 상태를 사용자에게 알리지 않는 구현
- 테스트 통과를 위한 기능 삭제, 타입 검사 우회, 광범위한 lint 예외
- 비밀키, 토큰, 개인정보, 녹화 데이터의 로그 출력 또는 커밋

## 11. 검증

변경 후 저장소에 정의된 명령을 사용해 영향 범위에 맞게 검증한다.

```bash
npm run lint
npm run typecheck
npm run build
```

- `lint`: ESLint로 코드 규칙과 React Hooks 사용을 검사한다.
- `typecheck`: 결과물을 빌드하지 않고 TypeScript 타입 오류를 검사한다.
- `build`: 타입 검사 후 배포용 결과물이 정상 생성되는지 확인한다.
- 현재 자동 테스트 도구와 `test` 스크립트는 없다. 추후 테스트 도구를 도입하면 영향 범위에 맞는 테스트를 추가해 실행한다.

- 사소한 UI 변경: lint + 해당 화면 수동 확인
- 타입·상태·API 변경: lint + typecheck
- 라우팅·빌드 설정·의존성 변경: 전체 build
- WebRTC 변경: 권한 허용/거부, 장치 없음, 재연결, 종료·정리 시나리오 확인

검증 명령이 없거나 실행할 수 없으면 성공한 것처럼 말하지 않고, 실행하지 못한 항목과 이유를 최종 보고에 명시한다.

## 12. 완료 체크리스트

- [ ] 요청한 범위만 수정했는가?
- [ ] 기존 구조와 공통 컴포넌트를 재사용했는가?
- [ ] 서버 상태, 폼 상태, 전역 클라이언트 상태를 올바르게 분리했는가?
- [ ] 로딩·빈 상태·오류·비활성 상태를 처리했는가?
- [ ] Primary 버튼이 핵심 행동 하나에만 사용됐는가?
- [ ] 색상·타입·간격·radius·elevation·z-index가 토큰을 사용하는가?
- [ ] 골드가 성취 맥락에만 사용됐는가?
- [ ] 모바일에서 주요 기능을 사용할 수 있는가?
- [ ] 키보드 탐색, Label, focus ring, 대비 기준을 지켰는가?
- [ ] AI 문구가 근거와 한계를 포함하고 단정적이지 않은가?
- [ ] 미디어 권한·연결·장치 오류와 cleanup을 처리했는가?
- [ ] 변경 범위에 맞는 lint, typecheck, build를 실행했는가?

## 13. 작업 결과 보고 형식

작업 완료 시 다음을 간결하게 보고한다.

1. 무엇을 변경했는지
2. 사용자 경험 또는 동작이 어떻게 달라졌는지
3. 어떤 검증을 실행했고 결과가 어땠는지
4. 남아 있는 제한사항이나 확인이 필요한 항목

파일 목록만 나열하지 말고 결과 중심으로 설명한다.
