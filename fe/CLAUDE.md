# CLAUDE.md

이 파일은 Claude Code가 Ait 프론트엔드 UI를 구현할 때 따르는 최상위 프로젝트 규칙이다.

## 프로젝트와 작업 범위

**Ait(에잇)**은 AI 기반 모의면접 훈련 및 화상 면접 스터디 서비스다. 프론트엔드 팀은 사용자가 면접을 준비하고 진행 상태와 피드백을 이해할 수 있는 웹 화면을 구현한다.

현재 작업 범위는 **프론트엔드 UI 구현**이다.

포함 범위:

- 화면 레이아웃과 React 컴포넌트
- 디자인 토큰과 공통 UI
- 반응형 화면과 접근성
- 화면 이동을 위한 클라이언트 라우팅
- Hover, Focus, Disabled, Loading, Error 등 시각적 상태
- 화면 확인에 필요한 제한적인 로컬 상호작용과 목업 데이터

제외 범위:

- 백엔드, 데이터베이스, AI 모델, 인프라 구현
- 실제 API 연동과 서버 상태 설계
- 실제 로그인, 파일 업로드, 결제 등 서버가 필요한 기능
- WebRTC·LiveKit을 이용한 실제 면접 세션 연결(화상 통화, 녹화, 재연결 로직) — 단, 스터디 세션(`StudySessionRoom`)의 LiveKit 화상 연결은 예외적으로 실연동 완료됨
- 아이트래킹 수집·계산·전송 로직

제외 범위가 필요한 작업은 임의로 구현하지 않고 사용자와 범위를 먼저 확인한다. 목업 화면을 실제 연동이 완료된 것처럼 표현하지 않는다.

예외: 면접 시작 전 환경 설정(장치 점검) 화면은 사용자 확인을 거쳐 `navigator.mediaDevices`(`getUserMedia`, `enumerateDevices`) 기반의 실제 카메라 미리보기·장치 목록·Web Audio 레벨 미터를 사용한다. 이는 위 WebRTC·LiveKit 세션 연결 제외 범위와 별개다.

## 기준과 우선순위

1. 사용자가 현재 작업에서 명시한 요구사항
2. 이 `CLAUDE.md`의 프로젝트 범위와 원칙
3. 팀이 승인한 최신 Figma 화면
4. `docs/design-system.md`와 `docs/domain-rules.md`
5. 기존 화면과 공통 컴포넌트의 패턴
6. 라이브러리 기본값과 일반적인 관례

- Figma와 디자인 문서의 값이 다르면 최신 Figma를 우선하고 차이를 사용자에게 알린다.
- 설치된 의존성과 실행 가능한 명령은 항상 `package.json`을 기준으로 확인한다.
- 존재하지 않는 설정이나 미도입 라이브러리를 이미 사용할 수 있다고 가정하지 않는다.

## 프론트엔드 구성

현재 기반:

- React + TypeScript + Vite
- ESLint

UI 구현 과정에서 필요할 때 도입하는 목표 구성:

- React Router: 화면 이동
- Tailwind CSS: 디자인 토큰 기반 스타일링
- shadcn/ui: 공통 UI 기반
- Lucide React: 아이콘
- React Bits: 제한적인 수치·진입 모션

새 의존성은 관련 작업에서 필요성이 확인됐을 때만 추가한다. Zustand, TanStack Query, React Hook Form, Zod는 현재 UI 전용 범위에 포함하지 않는다. LiveKit은 스터디 세션 화상 연결(`livekit-client`, `@livekit/components-react`)에 한해 예외적으로 도입됨.

## 기준 문서

- 시각 토큰, 컴포넌트 상태, 반응형, 접근성: `docs/design-system.md`
- 면접 화면 흐름, AI 피드백 표현, UX Writing: `docs/domain-rules.md`
- 로고 에셋 사용법: `public/Logo_Assets/README.md`

## 코드 작성 시 항상 지킬 것

- 새 컴포넌트를 만들기 전에 기존 컴포넌트로 구현 가능한지 확인한다.
- 페이지는 화면 구성에 집중하고 재사용 가능한 UI는 별도 컴포넌트로 분리한다.
- 공통 UI가 특정 목업 데이터 구조에 직접 의존하지 않게 한다.
- 색상, 글꼴 크기, 간격, radius, elevation, z-index를 임의로 하드코딩하지 않는다.
- 인터랙티브 컴포넌트는 화면에 필요한 상태를 빠짐없이 디자인한다.
- 한 화면 또는 한 명확한 작업 영역에는 Primary 버튼을 하나만 둔다.
- 삭제나 면접 종료처럼 되돌리기 어려운 행동에는 확인 Dialog를 제공한다.
- 오류 화면에는 원인과 사용자가 취할 수 있는 다음 행동을 함께 표시한다.
- AI 피드백은 합격 여부나 감정을 확정하는 표현을 사용하지 않는다.
- 키보드 탐색, 대체 텍스트, Label, Focus 상태를 시각 디자인의 일부로 취급한다.

## 주석 작성

- 코드만 봐서는 알기 어려운 비자명한 로직(우회 처리, 숨은 제약, 특정 버그 대응)에만 주석을 남기고, 코드가 이미 보여주는 내용을 그대로 설명하는 주석은 작성하지 않는다.
- 주요 컴포넌트나 함수 상단에는 구현 방식이 아니라 책임과 역할을 한 줄로 설명하는 주석을 남긴다.
- 목업 데이터나 실제 연동이 빠진 부분에는 `// TODO: 실제 API 연동 필요` 형식으로 남은 작업을 표시한다.
- 주석은 `~한다` 평서체로 통일하고 한 문장으로 간결하게 쓴다. 대상(컴포넌트·함수) 이름을 문장에서 반복하지 않는다.
- 작업 완료 시 위 기준에 맞는 주석이 필요한 곳에 빠짐없이 남아 있는지 확인한다.

예시:

```tsx
// 좋음 — 책임 한 줄 (구현 방식이 아니라 역할)
// 마이페이지. 프로필과 등록 자료를 불러와 보여주고, 저장소 조회는 별도로 재시도할 수 있다.
export function MyPage() { ... }

// 좋음 — 코드만으로는 드러나지 않는 이유를 설명
// StrictMode의 개발용 이중 마운트로 연동 요청이 두 번 나가지 않도록 한 번만 실행한다.
if (hasRequestedRef.current) return

// 나쁨 — 코드가 이미 보여주는 내용을 그대로 반복
// user를 가져온다
const { user } = useAuth()
```

## 목업과 로컬 상호작용

- 화면 확인용 데이터는 실제 API 응답처럼 위장하지 않고 목업임을 코드 구조에서 구분한다.
- 목업 데이터는 컴포넌트 내부에 반복해서 작성하지 않고 전용 fixture 또는 mock 모듈에 둔다.
- 탭, Dialog, Accordion, Carousel 등 UI 확인에 필요한 로컬 상태만 구현한다.
- API URL, 인증 토큰, 서버 응답 fallback, 임의의 데이터 계약을 만들지 않는다.

## 파일 구조

실제 구조가 생기면 기존 패턴을 우선하며 다음 역할을 기준으로 확장한다.

- `src/pages`: 화면 단위 컴포넌트
- `src/layouts`: 공통 페이지 레이아웃
- `src/components/ui`: 공통 UI
- `src/components/interview`: 면접 도메인 UI
- `src/assets`: 소스에서 import하는 이미지와 아이콘
- `src/mocks`: 화면 확인용 목업 데이터
- `src/styles`: 전역 스타일과 디자인 토큰

## 브랜치와 커밋

- 브랜치: `feat/기능명`
- 커밋 메시지는 `<type>: <한국어 요약>` 형식으로 작성한다.
  - `type`: `feat`(기능), `fix`(버그 수정), `docs`(문서·주석), `style`(포맷·스타일 변경), `refactor`(동작 변화 없는 구조 개선), `test`(테스트), `chore`(설정·빌드)
  - 요약은 무엇을 했는지 한국어로 간결하게 쓴다. 예: `docs: pages 화면 컴포넌트에 역할 주석 추가`
  - 세부 설명이 필요하면 한 줄 비우고 `- ` 불릿으로 무엇을·왜를 적는다.
- 한 커밋에는 하나의 논리적 작업만 담고, 성격이 다른 변경(예: 기능 구현과 주석 정리)은 나눠 커밋한다.
- 요청 범위와 무관한 작업 트리 변경은 함께 스테이징하지 않는다.
- 린터: ESLint

## 모를 때

- Figma나 디자인 문서에 없는 값을 임의로 만들지 않는다.
- 가장 가까운 기존 토큰과 컴포넌트를 먼저 확인한다.
- 선택에 따라 화면 결과가 크게 달라질 때만 사용자에게 확인한다.
- 기능 구현이 필요한 요구사항은 프론트 UI 범위를 벗어나는지 먼저 알린다.
