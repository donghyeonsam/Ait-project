# AI 모의 면접 — AI/FastAPI 파트 개발 일지

## 개요

AI 모의 면접 서비스의 **AI(FastAPI) 파트**를 구현했다. 이력서/자소서/GitHub 분석 데이터를
Chroma 벡터 DB에 임베딩하고, 면접 시작 시 RAG로 관련 문서를 검색해 GMS LLM(gpt-5.4-nano)으로
질문과 꼬리질문을 생성한다. 추가로 CS 지식 데이터를 별도 컬렉션으로 관리하고, 서버 기동 시
자동으로 시딩되는 구조까지 구현했다.

- 담당 범위: `ai/` 폴더 (FastAPI). FE(React) / BE(Spring Boot)는 별도 담당.
- 기술 스택: FastAPI, Chroma DB, ko-sroberta 임베딩, GMS gpt-5.4-nano
- 시작 시점 산출물: 기획 / 시퀀스 다이어그램 / ERD / WBS / GMS 사용 가이드

---

## 1. BE/FE 연동을 위해 확보한 자료

AI 파트 구현에 앞서 다음 자료를 기반으로 API 경계를 설계했다.

| 자료 | 용도 |
|---|---|
| ERD (CSV) | analyses / ai_interviews / ai_interview_questions / github_repos 등 테이블 구조 파악 |
| 시퀀스 다이어그램 | FE → BE → AI FastAPI 간 호출 흐름, 요청/응답 시점 |
| GMS 사용 가이드 | gpt-5.4-nano 호출 방식 (엔드포인트, 인증, developer role) |
| 면접 규칙 | 질문 10개, 꼬리질문 질문당 최대 2회, 면접 5종 |

핵심 연동 규칙: BE(Spring Boot)가 문서 분석·세션 관리·DB 저장을 담당하고, AI(FastAPI)는
**임베딩 / 질문 생성 / 꼬리질문 생성** 세 가지 기능을 API로 제공한다.

## 2. 구현한 프로젝트 구조

```
ai/
├── main.py                     # FastAPI 엔트리포인트 (lifespan, 라우터 등록)
├── config.py                   # .env 설정 (GMS 키, Chroma, 면접 규칙)
├── requirements.txt / Dockerfile / docker-compose.yml / .env.example
├── data/
│   └── cs_knowledge.json       # CS 지식 시드 (git 공유용)
├── core/
│   └── gms_client.py           # GMS LLM async 클라이언트
├── db/
│   └── chroma.py               # Chroma 클라이언트 (컬렉션 2개 관리)
├── schemas/
│   ├── common.py               # enum (면접유형, 난이도, 문서종류)
│   ├── embedding.py            # 개인 문서 임베딩 스키마
│   ├── interview.py            # 질문/꼬리질문 스키마
│   └── cs_knowledge.py         # CS 지식 스키마
├── prompts/
│   └── templates.py            # 면접 유형별 LLM 프롬프트
├── services/
│   ├── embedding_service.py    # 개인 문서 청킹 + 저장
│   ├── cs_embedding_service.py # CS 지식 저장 + 자동 시딩
│   ├── rag_service.py          # RAG 검색 (개인 문서 + CS 지식)
│   ├── question_service.py     # 질문 생성 총괄
│   └── followup_service.py     # 꼬리질문 생성
└── routers/
    ├── health.py               # 헬스체크
    ├── embedding.py            # 개인 문서 임베딩 API
    ├── interview.py            # 질문/꼬리질문 API
    └── cs_knowledge.py         # CS 지식 임베딩 API
```

역할 분리 원칙: **routers = API 입구, services = 로직, core/db = 외부 연결, schemas = 데이터 형식.**

## 3. 핵심 데이터 흐름

### ① 임베딩 흐름 (면접 전 — Chroma DB 구축)

```
BE가 이력서/자소서/깃허브 분석(analyses) 저장
  → POST /api/v1/embeddings
      → embedding_service: 텍스트를 500자 청크로 분할 (문단 존중, 80자 overlap)
      → chroma.py: ko-sroberta로 벡터화 → user_documents 컬렉션에 저장
         (metadata: user_id / doc_type / target_id)
```

### ② 질문 생성 흐름 (면접 시작 — RAG)

```
BE가 ai_interviews 세션 생성
  → POST /api/v1/interviews/questions
      → question_service: RAG 검색어 조립
      → rag_service: Chroma에서 user_id 필터로 관련 청크 검색 (R)
      → templates: 면접 유형별 프롬프트 구성
      → gms_client: GMS 호출 → 질문 10개 + 예상답안 생성 (G)
  → 응답: questions[] (question / expected_answer / topic / source)
```

### ③ 꼬리질문 흐름 (답변 후)

```
BE가 사용자 답변(STT 텍스트) 저장
  → POST /api/v1/interviews/followup
      → followup_service: 남은 횟수 체크 (2회 도달 시 LLM 호출 없이 종료)
      → rag_service: 답변 기반 재검색
      → gms_client: 꼬리질문 필요 여부 판단 + 생성
  → 응답: need_followup / question / expected_answer / followup_depth
```

## 4. GMS LLM 연동 (gpt-5.4-nano)

- SSAFY GMS 게이트웨이 경유 (`https://gms.ssafy.io/gmsapi/api.openai.com/v1`)
- gpt-5 계열이라 지시문을 `system`이 아닌 **`developer` role**로 전송
- `response_format: json_object`로 JSON 강제 + 코드펜스 방어 파서 내장
- 실패 시 tenacity로 최대 3회 지수 백오프 재시도

## 5. 면접 유형별 RAG 문서 우선순위

| 면접 유형 | 개인 문서 | CS 지식 |
|---|---|---|
| 직무(job) | 이력서 + 자소서 | ✗ |
| 기술(tech) | 깃허브 + 이력서 | ✗ |
| 포폴(portfolio) | 깃허브 + 이력서 | ✗ |
| CS | 이력서 + 자소서 | ✓ |
| 종합(comprehensive) | 전체 | ✓ |

CS/종합 면접은 개인 문서 검색 결과에 CS 전역 지식을 합쳐서 "지원자 기술 배경 + CS 개념"이
엮인 질문을 생성한다. (예: 자소서에 Redis → Redis 자료구조/캐시 전략 질문)

## 6. CS 지식 임베딩 (전역 지식)

개인 문서와 성격이 다른 CS 지식을 별도로 관리한다.

| | 개인 문서 | CS 지식 |
|---|---|---|
| 소유자 | 특정 사용자 | 없음 (전역 공용) |
| user_id | 있음 | 없음 |
| 컬렉션 | user_documents | cs_knowledge |

- 데이터 형식: `category` / `concept` / `content` (gyoogle 기술면접 레포 가공 예정)
- API: `POST/DELETE /api/v1/cs-knowledge`
- 검색 시 user_id 필터 없이 모든 사용자 공용으로 조회

### 자동 시딩 (git 공유 대응)

Chroma 데이터는 Docker 볼륨에 저장되어 **git으로 공유되지 않는다.** 이를 해결하기 위해:

- 원본 CS 지식을 `data/cs_knowledge.json`으로 만들어 **git에 커밋**
- 서버 기동 시 CS 컬렉션이 비어있으면 이 JSON을 **자동 임베딩** (`seed_cs_knowledge_if_empty`)
- 이미 데이터가 있으면 스킵 (재임베딩 방지)

→ 팀원이 `git pull` 후 `docker compose up` 하면 CS 지식이 자동으로 채워진다.

## 7. API 명세 (BE 연동용)

### 개인 문서 임베딩 — `POST /api/v1/embeddings`
```json
{
  "user_id": 1, "replace": true,
  "items": [
    {"doc_type": "resume", "target_id": 10, "title": "이력서", "content": "..."},
    {"doc_type": "github", "target_id": 5, "title": "my-repo", "content": "..."}
  ]
}
```

### 질문 생성 — `POST /api/v1/interviews/questions`
```json
{
  "user_id": 1, "ai_interview_id": 100,
  "interview_type": "tech", "difficulty": "normal",
  "company_name": "삼성전자", "position": "백엔드 개발자"
}
```

### 꼬리질문 — `POST /api/v1/interviews/followup`
```json
{
  "user_id": 1, "ai_interview_id": 100,
  "parent_question": "...", "user_answer": "...",
  "interview_type": "tech", "followup_depth": 0
}
```

### CS 지식 임베딩 — `POST /api/v1/cs-knowledge`
```json
{
  "replace": true,
  "items": [
    {"category": "운영체제", "concept": "프로세스와 스레드", "content": "..."}
  ]
}
```

## 8. 환경 구성 및 실행

- **Docker 구조 정리**: import 경로를 프로젝트 루트 기준(`from config`, `from services...`)으로
  통일. WORKDIR /app에서 `uvicorn main:app` 실행되도록 맞춤.
- **볼륨 2개**: `chroma_data`(임베딩 영속), `hf_cache`(임베딩 모델 캐시) — 컨테이너 재시작에도 유지
- **한국어 임베딩 모델**: `jhgan/ko-sroberta-multitask` (768차원), 빌드 시 캐시

```bash
cd ai
# .env 생성 후 GMS_KEY 입력
docker compose up --build
# → http://localhost:8000/docs
```

## 9. 검증 완료 내역

로컬 Docker 환경에서 전체 파이프라인 동작 확인:

- ✅ 서버 기동 + 임베딩 모델 로딩 (`준비 완료` 로그)
- ✅ 개인 문서 임베딩 저장 (`chunks=1`, 200 OK)
- ✅ Chroma 저장 확인 (`저장된 청크 수: 1`, metadata 정상)
- ✅ RAG 검색 + LLM 질문 생성 (`rag=True`, `count=10`)
- ✅ CS 지식 임베딩/검색/포맷 (스텁 end-to-end)
- ✅ 자동 시딩 (비면 채우고, 있으면 스킵)
