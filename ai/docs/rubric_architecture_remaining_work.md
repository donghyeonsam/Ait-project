# 루브릭 기반 동적 꼬리질문 아키텍처 전환 — 전체 완성도 및 잔여 작업

> 이 문서는 [`rubric_architecture_migration.md`](./rubric_architecture_migration.md) 에서
> 완료한 작업(Phase 1, Phase 2, 답변 보완 재설계)을 제외한, **아직 진행하지 않은
> "면접 전체 총평/피드백" 리포트 엔드포인트의 범위와 예상 작업**을 정리한 것이다.
> 실제 코드는 포함되어 있지 않다.

---

## 1. 전체 진행률

| 항목 | 내용 | 상태 |
|---|---|---|
| Phase 1 | 질문 5개 + 질문당 루브릭(채점 기준) 2~3개 생성 | ✅ 완료 |
| Phase 2 | 실시간 채점(rubric pass/fail) + 동적 꼬리질문 One-Call 생성 | ✅ 완료 |
| 답변 보완 재설계 | expected_answer 폐기, 답변 제출 후 비동기 ai_answer 생성 | ✅ 완료 |
| 면접 총평/피드백 리포트 | 면접 종료 후 전체 대화를 아우르는 총평/피드백 생성 | ⬜ 미착수 |

**중요한 설계 변경**: 원래 계획된 "Phase 3(모범 답안 생성)"은 이번 작업에서
["답변 보완" 재설계](./rubric_architecture_migration.md)로 흡수되어 이미 구현되었다
(사용자가 답변을 제출할 때마다 비동기로 `ai_answer`를 생성하는 방식으로, 면접
종료 후 일괄 처리하지 않는다). 따라서 지금 남은 것은 "질문별 모범 답안"이 아니라,
**면접 전체를 관통하는 총평/피드백**(예: "전반적으로 근거 제시가 약했습니다",
"CS 기초는 탄탄하나 트러블슈팅 경험 서술이 부족했습니다" 같은 요약형 피드백)이다.

---

## 2. 면접 총평/피드백 리포트 (미착수)

### 2.1 목표
면접 종료 후 호출되는 엔드포인트(동기/비동기 여부는 2.3 참고). 전체 대화 기록
(질문, 사용자 답변, rubric 채점 결과, `ai_answer` — 이미 답변 보완 단계에서 모두
생성되어 있음)을 입력받아, **면접 전체에 대한 총평과 개선 방향 피드백**을 생성한다.
질문별 `ai_answer`는 이미 완료되었으므로, 이 단계는 "개별 답변 교정"이 아니라
"전체 경향 분석"에 집중한다.

### 2.2 예상 수정/신규 대상

- **`schemas/interview.py`** (신규 스키마 추가)
  - 입력: `ai_interview_id`, `qa_history: list[...]` — 질문/사용자답변/rubric_results/
    ai_answer 를 이미 포함한 전체 대화 기록. (답변 보완 단계에서 이미 만든 데이터를
    BE가 취합해 넘겨주는 것을 전제로 함 — AI 서비스가 Redis/MySQL 을 직접 조회하지
    않는다는 기존 원칙 유지.)
  - 출력: `overall_feedback`(총평 텍스트), `strengths`(잘한 점), `weaknesses`(부족한 점),
    `improvement_suggestions`(개선 방향) 등 — 정확한 필드 구성은 FE 화면 설계와
    맞춰 확정 필요.

- **`prompts/templates.py`** (신규 프롬프트 추가)
  - "질문별 rubric 채점 결과(몇 개 중 몇 개를 놓쳤는지)를 종합해 지원자의 전반적인
    경향을 파악하고, 구체적이고 실행 가능한 개선 방향을 제시하라"는 지시.
  - 특정 질문 하나가 아니라 면접 전체 패턴(예: "특정 주제에서 반복적으로 약함",
    "질문 초반보다 후반에 답변 품질이 떨어짐")을 짚어내도록 유도하는 것이 이
    프롬프트의 핵심 가치.

- **`services/report_service.py`** (신규 파일)
  - 전체 대화 기록을 받아 프롬프트 구성 → GMS 호출 → 파싱.
  - 기존 서비스들의 GMS 호출 패턴(`chat_json`, tenacity 재시도, 코드펜스 방어 파서)
    그대로 재사용.
  - 질문별 `ai_answer`는 이미 완료된 데이터를 그대로 전달만 하면 되므로, 이 서비스가
    다시 생성할 필요는 없음(단순 통과/요약용 컨텍스트로만 사용).

- **`routers/interview.py`**
  - `POST /api/v1/interviews/report` (예시 이름) 신규 엔드포인트 추가.

### 2.3 설계상 고려/논의 필요 사항
- **동기/비동기 처리 방식**: 개별 답변 보완처럼 완전 비동기로 뒤에서 처리할지,
  "면접 완료" 버튼을 누른 시점에 사용자가 짧게 기다리는 동기 호출로 처리할지
  미정. 이미 질문별 `ai_answer`는 답변마다 비동기로 준비되어 있으므로, 이 리포트
  자체는 "총평 텍스트 하나"만 생성하면 되어 지연시간이 상대적으로 짧을 수 있다
  (LLM 호출 1회, 짧은 출력) — 동기 처리도 현실적인 선택지.
- **`capped=true`로 강제 종료된 질문 처리**: Phase 2에서 횟수 상한으로 강제
  종료된 질문(rubric을 다 채점하지 못함)을 총평에서 "이 부분은 판단이 어려웠음"
  으로 명시할지, 그냥 넘어갈지 정책 확정 필요.
- **총평의 톤/형식**: 정량적 점수(예: 5점 만점)를 함께 낼지, 정성적 서술로만
  구성할지는 FE 화면 설계와 맞물려 있어 기획/FE와 논의 필요.

## 3. 완료된 작업 관련 잔여 확인 사항 (코드는 완료, 검증 미완료)

Phase 1, Phase 2, 답변 보완 재설계 모두 코드 구현은 완료됐지만, 다음은 아직
확인되지 않았다:

1. **BE 연동**: `/followup`, `/answers/supplement` 는 모두 신규이거나 스키마가
   바뀐 엔드포인트이므로(migration.md 4절), BE 팀이 이 변경 사항을 반영해야
   실제 동작이 가능하다. 특히 `/answers/supplement`를 "답변 저장 직후 비동기
   호출"하는 트리거 자체가 BE에 아직 없다면 `ai_answer`가 영구히 비게 된다.
2. **실제 GMS LLM 응답 품질 검증**: `.env`의 GMS 키로 실제 호출해봐야 다음을
   확인 가능하다:
   - rubric 채점 프롬프트가 안정적인 JSON을 반환하는지, `rubric_results` 개수가
     입력과 항상 일치하는지.
   - 답변 보완 프롬프트가 "새 답변을 지어내지 않고 원문을 보완"하라는 지시를
     실제로 잘 따르는지(과도하게 다시 쓰거나, 사실을 지어내는 경우가 없는지).
3. **`max_followup_per_question` 값 재검토**: 실제 사용해보면서 2회가 적절한
   상한인지 BE/기획과 논의가 필요할 수 있다.
4. **`answer_service.py`의 RAG 재검색 비용**: 답변마다(기본 질문 + 모든 꼬리질문)
   RAG 검색을 1회씩 수행하므로, 질문당 최대 3회(기본 답변 + 꼬리질문 최대 2회)의
   추가 검색이 발생한다. 실사용 트래픽에서 Chroma 조회 비용이 문제가 되는지
   모니터링 필요.
