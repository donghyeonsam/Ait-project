## 1. 작업 배경 — rubric 진동 문제

`/api/v1/interviews/followup`은 매 턴 rubric 전체를 백지 상태에서 재채점하는
방식이었다(`services/followup_service.py`, 이전 버전 113행 부근). FastAPI는
stateless이므로 "이전 턴에 어떤 rubric이 이미 통과됐는지"를 서버가 스스로 알 방법이
없었고, BE도 통과 항목을 걸러내지 않고 매번 rubric 전체를 그대로 패스스루했다.

그 결과 다음과 같은 진동이 발생했다.

```
질문: "나이와 성별이 뭡니까?"  rubric: [A "나이를 밝혔는가", B "성별을 밝혔는가"]

1턴  답변 "28살입니다"     → A pass, B fail → 꼬리질문 "성별은?"
2턴  답변 "남자입니다"      → A FAIL(!), B pass → 꼬리질문 "나이는?"   ← 무한 반복
```

`schemas/interview.py`의 이전 `FollowupRequest.rubric` 주변에는 "꼬리질문에 대한
재꼬리질문인 경우, BE는 아직 통과하지 못한 rubric 항목만 추려서 넘겨주는 것을
전제로 한다"는 주석이 있었지만, 이는 **아무도 구현하지 않은 문서상의 가정**이었다
— 실제로는 BE가 최초 rubric 전체를 매 턴 그대로 되돌려 보내는 구조였고, 서버도
이를 걸러낼 방법이 없었다.

## 2. 검토했다가 기각한 대안

### 2.1 채점을 타 파트(BE)로 분리

"AI 서비스는 채점 결과만 반환하고, 통과 항목을 걸러내는 책임은 BE가 진다"는
방향도 고려했다. 하지만 이러면 BE가 매 턴 (a) 이전 rubric 목록, (b) 이번 채점
결과 두 가지를 대조해 차집합을 계산하는 로직을 별도로 구현해야 한다. 이 로직은
AI 서비스가 이미 rubric 원문과 LLM 응답을 둘 다 들고 있는 시점에 훨씬 자연스럽게
구현할 수 있고, 타 파트에 새로운 상태 관리 책임을 떠넘기는 것이므로 기각했다.

### 2.2 rubric에 통과 플래그를 심는 방식

`rubric: list[str]`을 `rubric: list[{criterion: str, passed: bool}]`처럼 항목별
통과 플래그를 가진 객체 배열로 바꾸는 방식도 검토했다. 이러면 "narrowing으로 항목이
사라지는" 대신 "항목은 그대로 두고 플래그만 갱신"하는 방식이 되어 원본 rubric이
요청 payload에 계속 남는다는 장점이 있다.

기각한 이유:
- `GeneratedQuestion.rubric`/`FollowupNextQuestion.rubric` 등 다른 파트가 이미
  `list[str]`을 전제로 소비하고 있어, 이 방식은 관련 DTO 타입을 전부 바꿔야 하는
  더 큰 Breaking Change가 된다.
- "한 번 pass한 항목은 다시 fail로 안 바뀐다"는 단조성(monotonicity)을 보장하려면
  병합 시점에 "기존 플래그가 true면 새 판정이 false여도 true를 유지"하는 코드를
  서버가 매번 짜야 한다. narrowing 방식은 애초에 통과 항목이 응답에 존재하지 않으므로
  이 로직 자체가 필요 없다 — narrowing이 구조적으로 더 안전하다고 판단했다.

## 3. 최종 선택 — rubric narrowing

**통과한 rubric 항목을 응답에서 제거해서 내려준다.** 다음 턴에는 미통과 항목만
요청에 실려 오므로, 이미 통과한 항목은 재채점 대상으로 물리적으로 존재하지 않는다.
통과 상태를 뒤집을 코드 경로 자체가 없어지므로 진동이 구조적으로 불가능해진다.

- rubric 리스트가 비면(narrowing으로 전부 사라졌거나 처음부터 빈 채로 온 경우)
  → `is_pass = true`.
- 상태는 여전히 요청/응답 payload가 왕복시키므로 FastAPI stateless 원칙은 그대로
  유지된다.
- rubric 타입은 `list[str]` 그대로라 다른 파트의 DTO 타입 변경을 유발하지 않는다
  (2.2절과의 핵심 차이).
- GMS 호출은 답변 1건당 1회 유지(기존과 동일, 증가 없음) — narrowing 판단까지
  기존 One-Call JSON Mode 안에서 처리한다.

## 4. 변경 사항

### `schemas/interview.py`

- `FollowupQuestionInfo`(신규): 요청에 실리는 "직전에 답한 질문" — `GeneratedQuestion`과
  동일한 필드 구성. `rubric`은 "아직 통과하지 못한 채점 기준"으로 의미가
  재정의됐고, `min_length` 제약을 두지 않는다(빈 배열은 정상 상태).
- `FollowupRequest` 전면 교체: 기존 flat 구조(`parent_question`/`rubric`/`depth`가
  최상위 필드)에서 `question: FollowupQuestionInfo` 중첩 구조로 변경. `user_answer` →
  `answer`로 필드명 변경. `ai_interview_id`는 요청에서는 선택 필드로 유지(로깅
  전용, 7.2절 참고), 응답에서는 제거.
- `FollowupNextQuestion`(신규): 응답의 다음 질문 — `GeneratedQuestion`과 동일한
  필드 구성이어야 소비 측(BE/FE)이 두 객체를 같은 타입으로 다룰 수 있다.
- `FollowupResponse` 전면 교체: `rubric_results`/`all_passed`/`capped`/
  `ai_interview_id` 필드를 제거하고 `is_pass`/`next_question` 둘로 단순화.
  `is_pass=true`는 "모든 rubric 통과"와 "depth 상한 도달로 강제 종료" 두 의미를
  함께 갖는다(기존 `capped` 필드가 하던 구분을, 호출측이 `question.depth`로
  판단하도록 흡수시켰다).
- `RubricResult` 클래스 삭제: `FollowupResponse`(narrowing으로 항목별 채점 결과
  리스트 자체가 불필요해짐)와 `AnswerSupplementRequest`(아래 참고) 양쪽에서 더
  이상 쓰이지 않는다.
- `AnswerSupplementRequest.rubric_results` 필드 삭제: narrowing 방식에서는
  `/followup` 요청에 실렸던 `question.rubric` 자체가 이미 "이 답변이 놓친 기준"
  이므로, 별도로 pass/fail 채점 결과를 다시 실어 보내는 것이 중복 정보였다.
- `GeneratedQuestion`은 변경하지 않았다 — rubric은 계속 `list[str]`.

### `prompts/templates.py`

- `FOLLOWUP_SYSTEM`: "항목별 pass/fail 채점" 뉘앙스에서 "통과하지 못한 기준만
  골라내고 그중 하나를 겨냥해 되묻는다"로 문구 수정.
- `build_followup_prompt`: 시그니처(`parent_question`/`rubric`/`user_answer`/
  `context`/`interview_type`)는 유지하되, 출력 형식을 `rubric_results`/
  `all_passed` 대신 `unpassed_rubric`/`followup_question`으로 교체. LLM에게
  "기준 문구는 원문 그대로(변형·요약 금지) 반환하라"고 명시했다 — 서버가 원문
  대조로 검증하므로 표현이 바뀌면 그 항목이 버려지기 때문이다.
- `build_answer_supplement_prompt`: `rubric_results` 인자와 관련 프롬프트 섹션
  분기를 제거하고, `rubric` 목록만으로 "미충족 위주로 보완"을 지시하도록 단순화.

### `services/followup_service.py`

`generate_followup()`을 다음 순서로 재작성했다.

1. `req.question.rubric`이 비어 있으면 GMS 호출 없이 즉시 `is_pass=true` 반환
   (호출측이 방어적으로 호출해도 안전하게, 불필요한 토큰 소비도 방지).
2. `req.question.depth >= settings.max_followup_per_question`이면 GMS 호출 없이
   즉시 `is_pass=true` 반환(기존 capped 로직 계승. `is_pass=true`가 "모두 통과"와
   "상한 도달"의 이중 의미를 갖게 됐다는 점을 주석/문서에 명시).
3. 기존과 동일하게 RAG 검색(질문+답변 쿼리, `build_target_ids`로 문서 범위 제한).
4. GMS 1회 호출(temperature=0.7, 기존과 동일).
5. `_narrow_rubric()`으로 LLM이 반환한 `unpassed_rubric`을 입력 rubric과 원문
   대조해 정규화 — ① 정확 일치 → ② 공백/구두점 제거 후 일치 순으로 매칭하고,
   둘 다 실패한 항목은 버린다(LLM이 지어낸 기준이 rubric에 흘러들지 않도록).
   결과는 입력 rubric의 부분집합임이 보장되며(중복 제거, 입력 순서 유지), 이
   불변식을 함수 docstring에 명시했다.
6. 정규화 결과가 비면 `is_pass=true`.
7. `followup_question`이 비어있으면(LLM 형식 누락) 기존과 동일하게 `is_pass=true`로
   강제 전환하는 교착 방지 로직을 그대로 계승.
8. 그 외에는 `is_pass=false` + `next_question`(order/topic/source는 부모 승계,
   depth+1, rubric은 narrowing된 목록).

삭제: `RubricResult` import, `rubric_results` 파싱 블록, `all_passed` 재계산,
`capped` 관련 처리 — narrowing 구조에서는 전부 불필요해졌다.

### `services/answer_service.py`

`rubric_results` → dict 변환 및 프롬프트 전달 블록을 제거했다. `req.rubric`만
`build_answer_supplement_prompt()`에 넘긴다.

### `routers/interview.py`

`create_followup` 핸들러 docstring을 새 계약(중첩 `question` 구조, `is_pass`/
`next_question`, `is_pass=true`의 이중 의미)에 맞춰 갱신했다. try/except 구조
자체는 변경하지 않았다.

### `README.md`

"3. 꼬리질문" 섹션을 새 요청/응답 형식으로 교체하고 Breaking Change 경고 블록을
추가했다. "4. 답변 보완" 섹션도 `rubric_results` 필드 제거를 반영해 요청 예시와

## 7. 결정 사항 — 타 파트 확인 필요

작업 지침에 정해진 기본값을 따랐으며, 아래 항목은 타 파트 확인이 필요하다.

1. **`interview_type` 유지.** 새 요청 예시에는 이 필드가 없었으나,
   `retrieve_context()`의 면접 유형별 문서 참고 비율(`DOC_TYPE_WEIGHTS`)과
   프롬프트의 `INTERVIEW_TYPE_GUIDE`가 이 값에 의존한다. 빼면 기능 퇴행이므로
   요청 필드로 유지했다.
2. **`ai_interview_id`는 요청에서 선택 필드(`int | None = None`)로 유지**,
   응답에서는 제거. 로그에 세션 식별자가 안 남으면 장애 추적이 불가능해서다.
3. **네이밍 컨벤션은 snake_case로 통일.** 호출측 wire 포맷이 이미 snake_case라
   응답의 `is_pass`/`next_question`도 이와 일관되게 뒀다.

## 8. 남는 한계

- **depth 상한 도달 시 마지막 답변은 채점되지 않는다.** `req.question.depth >=
  max_followup_per_question`이면 GMS 호출 자체를 생략하므로, 그 턴에 제출된
  답변이 실제로 rubric을 충족했는지 여부는 확인되지 않은 채 `is_pass=true`로
  넘어간다. "더 이상 파고들지 않기로 함"이지 "진짜로 다 통과함"이 아니라는 점을
  호출측이 `question.depth` 값으로 구분해야 하는 이유이기도 하다.
- **원본 rubric(질문 생성 시점의 전체 채점 기준)이 요청 payload에서 소실된다.**
  narrowing이 진행될수록 요청에 실리는 rubric은 점점 줄어들므로, 나중에 "이
  질문에 원래 rubric이 몇 개였는지"를 AI 서비스 쪽에서는 더 이상 알 수 없다.
  이 정보가 리포트/총평 등에서 필요하다면, BE가 `/questions` 응답 시점의 원본
  rubric을 별도로 보관해야 한다(인터페이스 명세 문서에 "호출측 요청 사항"으로
  명시).
