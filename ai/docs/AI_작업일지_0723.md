## 1. 개인 문서 임베딩 `replace` 동작 버그 수정

> 대상: `POST /api/v1/embeddings` (개인 문서 임베딩)

### 1.1 작업 배경

개인 문서 임베딩 API(`POST /api/v1/embeddings`)는 이력서/자소서/GitHub 분석 결과를
Chroma에 벡터로 저장한다. 요청 스키마(`schemas/embedding.py`의 `EmbedRequest`)에는
`replace: bool = True` 필드가 있는데, 기본값이 `True`인 이유는 "동일 문서를 재분석해서
다시 임베딩 요청이 오면 예전 버전이 검색 결과에 함께 섞여 나오는 것을 방지"하기
위함이다.

### 1.2 문제

`services/embedding_service.py`의 `embed_user_documents()`는 `req.replace=True`일 때
`delete_user_embeddings(req.user_id)`를 호출했다. 그런데 이 함수는 Chroma에서
**`user_id`로만** 필터링해서 해당 사용자의 이력서/자소서/GitHub 임베딩을 **전부**
지운다 — "문서 하나만 갱신"이라는 의도와 실제 삭제 범위("사용자 전체")가 어긋나 있었다.

**재현 시나리오**: 사용자가 이력서 1개, 자소서 4개, GitHub 레포 4개를 이미 임베딩해둔
상태에서 자소서 1개(`target_id=2`)만 수정 후 재분석해 임베딩 요청(`replace=True`,
기본값)을 보내면 → 이력서 1개 + 자소서 3개 + GitHub 4개가 전부 삭제되고, 방금 수정한
자소서 1개만 Chroma에 남는다. 이후 면접 질문 생성/RAG 검색(`services/rag_service.py`)
시 나머지 8개 문서가 근거 자료에서 완전히 빠지게 되어 질문 품질이 급격히 떨어지는
결과로 이어진다.

의도한 동작은 "수정된 자소서 1개의 기존 임베딩만 지우고, 나머지 8개 문서는 그대로
유지"하는 것이다.

### 1.3 변경 사항

#### `services/embedding_service.py`

**신규 함수 `delete_document_embedding(user_id, doc_type, target_id)`** (`delete_user_embeddings` 바로 아래에 추가)

```python
def delete_document_embedding(user_id: int, doc_type: str, target_id: int) -> None:
    collection = get_collection()
    collection.delete(
        where={
            "$and": [
                {"user_id": user_id},
                {"doc_type": doc_type},
                {"target_id": target_id},
            ]
        }
    )
    ...
```

`user_id` / `doc_type` / `target_id` 세 조건을 모두 걸어야 다른 사용자·다른 문서
타입·다른 문서를 잘못 지우지 않는다. 이 세 필드 조합은 `_make_id()`가 청크 ID
(`u{user_id}:{doc_type}:{target_id}:{idx}`)를 만들 때 이미 "문서 고유 키"로 쓰고 있는
것과 동일하다 — 삭제 범위를 그 키 기준과 일관되게 맞춘 것이다.

**`embed_user_documents()` 수정**

기존:
```python
if req.replace:
    delete_user_embeddings(req.user_id)   # 루프 진입 전, 사용자 전체 삭제

for item in req.items:
    ...
```

변경 후:
```python
for item in req.items:
    if req.replace:
        delete_document_embedding(req.user_id, item.doc_type.value, item.target_id)
    ...  # 기존 로직 유지
```

루프 밖에서 한 번 실행하던 전체 삭제를 제거하고, 루프 안에서 아이템(문서)마다
개별적으로 그 문서의 기존 임베딩만 지우도록 옮겼다. `req.replace=False`인 경우는
삭제 호출 자체가 스킵되어 upsert만 수행되는 기존 동작 그대로 유지된다.

이미 존재하는 `_make_id()`의 upsert 갱신 방식(동일 id는 자동 덮어쓰기)만으로는
부족한 이유: 문서를 재분석했을 때 청크 개수가 줄어드는 경우(예: 5개 → 3개)
`idx=3, 4`였던 뒤쪽 청크는 upsert 대상에서 아예 빠지기 때문에 삭제 없이는 Chroma에
그대로 남아 "유령 청크"가 된다. 따라서 upsert 이전에 문서 단위 삭제를 명시적으로
수행하는 것이 필요하다.

**`delete_user_embeddings(user_id)`는 변경하지 않았다.** 이 함수는
`routers/embedding.py`의 `DELETE /api/v1/embeddings/{user_id}` 엔드포인트가 그대로
사용 중이며(회원 탈퇴 시 해당 사용자의 임베딩 전체 삭제), 이 용도에서는 "user_id
전체 삭제"가 여전히 올바른 동작이다. 함수 docstring에 "재임베딩용으로는 더 이상 쓰이지
않음 + 이 함수 자체는 그대로 유지"라는 점만 주석으로 명시했다.

#### `db/chroma.py`

변경 없음. `delete_document_embedding()`은 기존 `get_collection()`을 그대로
재사용하도록 `services/embedding_service.py`에 추가했다(신규 DB 접근 경로 불필요).

### 1.4 영향받는 파일

- `services/embedding_service.py` — 유일하게 수정된 파일.
  - 신규: `delete_document_embedding()`
  - 수정: `embed_user_documents()` (삭제 호출 위치를 루프 밖 → 루프 안으로 이동)
  - 변경 없음: `delete_user_embeddings()`, `_make_id()`, `_split_text()`

다른 파일(`schemas/embedding.py`, `routers/embedding.py`, `db/chroma.py`)은 수정하지
않았다.

### 1.5 BE 영향 여부

**API 요청/응답 스키마(JSON 계약)는 전혀 바뀌지 않는다.** `EmbedRequest`/`EmbedResponse`
필드, 엔드포인트 URL, HTTP 메서드 모두 기존 그대로이므로 BE 코드 수정은 필요 없다.

다만 **`replace` 파라미터의 실제 동작 범위가 바뀐다는 점은 BE 팀이 인지해야 한다**:

| | 변경 전 (버그) | 변경 후 |
|---|---|---|
| `replace=True`일 때 삭제 범위 | 해당 `user_id`의 **모든** 문서(이력서+전체 자소서+전체 GitHub) | 요청에 포함된 `items`의 **각 문서(doc_type+target_id)만** |
| 다른 문서(요청에 포함 안 된 것)에 미치는 영향 | 삭제됨 (버그) | 영향 없음 (의도한 동작) |

BE가 "자소서 1개 재분석 → 그 1개만 담아서 임베딩 API 호출"하는 방식으로 이미
호출하고 있었다면(문제 시나리오와 일치), 이번 수정으로 그 호출 패턴이 의도대로
동작하게 된다 — BE 쪽 호출 코드 변경은 필요 없다. 만약 BE가 이 버그를 우회하기 위해
"항상 사용자의 전체 문서를 한 번에 모아서 보낸다" 같은 별도 방어 로직을 두고 있었다면
그 로직은 이제 불필요해지지만, 있어도 동작에 문제는 없다(그냥 매번 전체를 재삭제/재삽입
하는 것과 동일).

### 1.6 검증 방법

- `python -m py_compile services/embedding_service.py db/chroma.py` — 문법 오류 없음 확인.
- 실제 Chroma/임베딩 모델을 띄운 통합 테스트는 수행하지 않음(로컬에 `.env`/모델
  다운로드 필요). BE/QA 단계에서 다음을 확인해야 한다:
  1. 이력서 1개 + 자소서 4개 + GitHub 4개를 임베딩한 뒤, 자소서 1개(`target_id=2`)만
     담아 `replace=True`(기본값)로 재요청 → Chroma에서 나머지 8개 문서(이력서 1,
     자소서 3, GitHub 4)의 청크 개수가 요청 전후로 변하지 않는지 확인.
  2. 같은 시나리오에서 `target_id=2` 자소서의 임베딩만 새 내용으로 갱신되고, 청크
     개수가 줄어든 경우(문서를 짧게 재작성) 이전 청크가 유령으로 남지 않는지 확인.
  3. `replace=False`로 요청 시 기존 임베딩이 그대로 유지된 채 upsert만 되는지(기존
     동작과 동일한지) 확인.
  4. `DELETE /api/v1/embeddings/{user_id}` 호출 시 여전히 해당 사용자의 모든 문서가
     삭제되는지(회원 탈퇴 시나리오, `delete_user_embeddings` 미변경 확인) 확인.

## 2. 질문 생성 — 면접관 스타일(어조) 반영 (신규)

> 대상: `POST /api/v1/interviews/questions` (질문 생성)

### 2.1 작업 배경

기존 질문 생성 요청(`schemas/interview.py`의 `QuestionGenerateRequest`)에는 난이도
(`difficulty`)는 있었지만, "면접관이 어떤 말투로 질문하는지"를 지정하는 필드가 없었다.
FE/BE에서 사용자가 면접관 스타일을 3가지 중 하나로 선택해서 넘겨줄 예정이므로, 이
값을 AI 서비스가 받아 LLM이 생성하는 질문의 **말투/어조**에 반영하도록 스키마와
프롬프트를 수정했다.

면접관 스타일 3종:
- **편안하게(`comfortable`)**: 친근하고 부드러운 어투. 지원자가 편하게 이야기할 수
  있도록 격려하는 톤으로 질문.
- **실전처럼(`realistic`, 기본값)**: 실제 면접장과 유사한 담백하고 표준적인 존댓말
  톤. 과도한 격려나 압박 없이 사실적으로 질문.
- **압박형(`pressure`)**: 날카롭고 도전적인 어투. 답변의 허점을 파고들 준비가 된
  듯한 압박감 있는 표현(단, 인신공격/무례한 표현은 금지 — 질문의 날카로움으로만 표현).

이 값은 질문의 "내용"(rubric, 주제, 난이도)에는 영향을 주지 않고 오직 "말투"에만
반영되는 것이 핵심 요구사항이다.

### 2.2 변경 사항

#### `schemas/common.py`

- `InterviewerStyle(str, Enum)` 신규 추가 (`Difficulty` 바로 아래): `COMFORTABLE` /
  `REALISTIC` / `PRESSURE`. 기존 `CSCategory`와 동일하게 "⚠️ BE 계약 주의" 문구를
  docstring에 명시 — 신규 필드이므로 BE와 문자열 스펙 동기화 필요.
- `INTERVIEWER_STYLE_LABEL: dict[InterviewerStyle, str]` 신규 추가 (`CS_CATEGORY_LABEL`
  바로 아래) — 한국어 라벨. 기존 라벨 dict 패턴과 동일하게 구성.

#### `schemas/interview.py`

- `QuestionGenerateRequest`에 `interviewer_style: InterviewerStyle = InterviewerStyle.REALISTIC`
  필드 추가(`difficulty` 바로 아래). 기본값을 "실전처럼"으로 둔 이유는 실제 면접장과
  가장 가까운 표준 톤이라 미지정 시 부작용이 가장 적기 때문.
- import에 `InterviewerStyle` 추가.

#### `prompts/templates.py`

- `INTERVIEWER_STYLE_GUIDE: dict[InterviewerStyle, str]` 신규 추가 (`DIFFICULTY_GUIDE`
  바로 아래) — 스타일별 어조 지시문. `DIFFICULTY_GUIDE`와 동일한 "enum → 지시문
  테이블" 전략 패턴을 그대로 따랐다.
- `build_question_prompt()`에 `interviewer_style: InterviewerStyle` 파라미터 추가
  (`difficulty` 바로 다음), `style_guide = INTERVIEWER_STYLE_GUIDE[interviewer_style]`
  조회 추가.
- 반환 프롬프트의 "## 난이도" 섹션 바로 아래에 "## 면접관 스타일" 섹션을 신규
  추가했고, "이 스타일은 말투에만 적용하고 질문 내용/rubric/난이도는 그대로 따르라"는
  지시문을 함께 넣어 스타일 지시가 질문 내용까지 바꾸지 않도록 명시적으로 분리했다.

#### `services/question_service.py`

- `generate_questions()`에서 `build_question_prompt(...)` 호출 시
  `interviewer_style=req.interviewer_style` 인자를 추가로 전달.

### 2.3 범위 제한

이번 작업은 **질문 생성(`/api/v1/interviews/questions`)에만 적용**했다.
`followup_service.py`(꼬리질문)와 `answer_service.py`(답변 보완)의 프롬프트는
건드리지 않았다 — 그쪽까지 스타일을 반영할지는 별도 논의 후 결정 예정.

### 2.4 영향받는 파일

- `schemas/common.py` — `InterviewerStyle` enum, `INTERVIEWER_STYLE_LABEL` dict 신규 추가.
- `schemas/interview.py` — `QuestionGenerateRequest.interviewer_style` 필드 신규 추가.
- `prompts/templates.py` — `INTERVIEWER_STYLE_GUIDE` dict 신규 추가,
  `build_question_prompt()` 파라미터/프롬프트 섹션 추가.
- `services/question_service.py` — `build_question_prompt()` 호출부 인자 1개 추가.
- `README.md` — "2. 질문 생성" API 섹션에 `interviewer_style` 반영.

`followup_service.py`, `answer_service.py`, `rag_service.py`, `db/chroma.py`는 이번
작업과 무관하며 수정하지 않았다.

### 2.5 영향받는 API 계약 (BE 연동)

`QuestionGenerateRequest`(요청 바디)에 필드 1개가 **선택 필드로** 추가됨(하위 호환,
Breaking Change 아님):

```json
{
  "user_id": 1,
  "ai_interview_id": 100,
  "interview_type": "tech",
  "difficulty": "normal",
  "interviewer_style": "pressure",
  "company_name": "삼성전자",
  "position": "백엔드 개발자",
  "career": "3년차",
  "skills": ["Java", "Spring", "MySQL"]
}
```

- `interviewer_style` 값은 `schemas/common.py`의 `InterviewerStyle` enum과 정확히
  일치해야 한다: `comfortable`(편안하게) / `realistic`(실전처럼) / `pressure`(압박형).
- **선택 필드**이며, BE가 아예 보내지 않아도 기본값 `realistic`으로 처리되므로 기존
  BE 연동 코드를 당장 수정하지 않아도 API 자체는 깨지지 않는다. 다만 FE에서 실제로
  이 옵션을 사용자에게 노출하려면 BE가 이 값을 요청에 실어 보내야 반영된다.
- 응답 스키마(`QuestionGenerateResponse`)는 변경 사항 없음.
- BE 팀과 위 3개 문자열 스펙을 동기화할 것.

### 2.6 검증 방법

- `python -m py_compile schemas/common.py schemas/interview.py prompts/templates.py services/question_service.py` — 문법 오류 없음 확인.
- 실제 GMS LLM 호출을 통한 통합 테스트는 수행하지 않음(`.env`의 GMS 키 필요). BE/QA
  단계에서 다음을 확인해야 한다:
  1. `interviewer_style`을 생략하고 요청 시 422 없이 기본값(`realistic`)으로 정상
     처리되는지.
  2. `comfortable` / `realistic` / `pressure` 각각으로 요청했을 때 응답
     `questions[].question`의 말투가 실제로 구분되게 달라지는지, 반면 `rubric`
     개수/성격이나 `topic`/`source` 등 "내용" 관련 필드는 스타일과 무관하게 일정한지.
  3. 잘못된 문자열(예: `"aggressive"`)을 `interviewer_style`로 보내면 pydantic이
     422로 거부하는지.

## 3. 질문 생성 — BE 요청 형식 개편 대응 (Breaking Change)

> 대상: `POST /api/v1/interviews/questions` (질문 생성) 요청 스키마 전면 개편

### 3.1 작업 배경

BE(Spring Boot)가 면접 시작 시 호출하는 `POST /api/v1/interviews/questions`의 요청
파라미터 형식이 대대적으로 바뀔 예정이다. 필드명은 snake_case로 오므로(파이썬/pydantic
필드명과 1:1 매칭, camelCase 변환 로직 불필요) 필드명 자체를 wire 이름과 동일하게
맞추면 되지만, 일부 값이 **한글 라벨/대문자**로 오고 **필드 구조 자체가 바뀐 부분**도
있다. 새 요청 예시:

```json
{
  "user_id": "1",
  "ai_interview_id": "100",
  "position": "백엔드 개발자",
  "career": "신입",
  "skills": ["Java", "Spring Boot", "MySQL", "Redis"],
  "resume_id": "1",
  "cover_letter_id": "1",
  "github_repo_id": "1",
  "interview_type": "CS",
  "cs_categories": ["자료구조", "네트워크", "운영체제"],
  "difficulty": "중",
  "ai_attitude_style": "압박면접"
}
```
(`interview_type`이 `"CS"`가 아니면 `cs_categories`는 빈 배열로 온다)

### 3.2 기존 스키마 대비 변경점 요약

| 기존 필드 (영문 enum 값) | 신규 필드 (snake_case, 한글 값 포함) | 비고 |
|---|---|---|
| `user_id` (int) | `user_id` (`"1"`, 문자열) | pydantic이 숫자 문자열→int 자동 변환 — 필드명/타입 변경 없음(검증 완료) |
| `ai_interview_id` (int) | `ai_interview_id` (`"100"`) | 필드명 변경 없음, 값만 문자열로 옴 |
| `interview_type` (`"job"`/`"cs"`/...) | `interview_type` (`"CS"` 대문자) | 필드명은 그대로, 값의 대소문자만 무관하게 매칭되도록 처리 |
| `difficulty` (`"easy"`/`"normal"`/`"hard"`) | `difficulty` (`"하"`/`"중"`/`"상"` 추정) | 필드명은 그대로, 한글 라벨 → 내부 enum 매핑 (⚠️ 추정값) |
| `interviewer_style` (`"comfortable"`/...) | `ai_attitude_style` (`"압박면접"` 등) | **필드명 자체가 변경**, 값도 한글. `"압박면접"`만 확인, 나머지 2개는 추정 (⚠️ 확인 필요) |
| `cs_category` (단일, 영문) | `cs_categories` (배열, 최대 3개, 한글 라벨) | 단일 선택 → 다중 선택으로 구조 자체가 바뀜 |
| (없음, 신규) | `resume_id`, `cover_letter_id`, `github_repo_id` | 이 면접에서 참고할 특정 문서 지정 — RAG 검색 범위를 "이 사용자의 전체 문서"에서 "이 특정 문서"로 좁히는 용도 |
| `company_name` | (신규 예시엔 없음) | 그대로 선택 필드로 유지(제거하지 않음 — 하위 호환) |
| `career`, `skills` | `career`, `skills` | 변경 없음 |

### 3.3 변경 사항

#### `schemas/common.py`

`InterviewType`은 값 변경 없음(대소문자 정규화는 `schemas/interview.py`의
`field_validator`에서 처리). 나머지 3개 enum(`Difficulty`/`InterviewerStyle`/
`CSCategory`) 값은 **영문 그대로 유지**하고, "BE가 보내는 wire 값(한글) → 내부 enum"
매핑 테이블만 각 enum 정의 바로 아래에 신규 추가했다. enum 자체의 값을 한글로 바꾸지
않은 이유: `prompts/templates.py`의 `DIFFICULTY_GUIDE`/`INTERVIEWER_STYLE_GUIDE` 등
다른 코드 전반이 이미 영문 값을 전제로 하고 있고, 나중에 BE가 한글 문구를 살짝
바꿔도(예: `"중"` → `"보통"`) 매핑 테이블 하나만 고치면 되도록 wire 표현과 내부
표현을 분리해두기 위함이다.

- `DIFFICULTY_KOREAN_INPUT_MAP`: `{"하": EASY, "중": NORMAL, "상": HARD}`.
- `INTERVIEWER_STYLE_KOREAN_INPUT_MAP`: `{"편안한 면접": COMFORTABLE, "실전 면접": REALISTIC, "압박면접": PRESSURE}`.
- `CS_CATEGORY_KOREAN_INPUT_MAP`: BE 예시("자료구조"/"네트워크"/"운영체제")와 기존
  `CS_CATEGORY_LABEL`의 표기("자료구조/알고리즘" 등)가 다를 수 있어, 두 표기 모두
  인식하도록 동의어(`"자료구조"`, `"자료구조/알고리즘"`, `"알고리즘"` 모두
  `DATA_STRUCTURE_ALGORITHM`)를 넣었다.

세 매핑 모두 "⚠️ BE 확인 필요" 문구를 docstring/주석에 명시했다(3.6절 참고).

#### `schemas/interview.py`

`QuestionGenerateRequest`를 다음과 같이 개편했다(camelCase 관련 alias/ConfigDict는
불필요 — BE가 snake_case로 그대로 보내므로 필드 선언 그대로 매칭됨):

- **필드명 변경**: `interviewer_style` → `ai_attitude_style` (타입은 기존
  `InterviewerStyle` enum 그대로 재사용, 기본값 `REALISTIC`).
- **필드 구조 변경**: `cs_category: CSCategory | None` → `cs_categories: list[CSCategory] = Field(default_factory=list, max_length=3)`.
- **신규 필드**: `resume_id`, `cover_letter_id`, `github_repo_id` (모두 `int | None`,
  선택 필드 — 문서 종류에 따라 없을 수 있음, 예: GitHub 미연동 사용자).
- **신규 `field_validator(mode="before")` 4개** — pydantic이 값을 enum으로 강제
  변환하기 "전"에 개입해 BE의 원시 wire 값을 내부 enum으로 바꾼다:
  - `_normalize_interview_type`: 문자열이면 `.lower()`만 적용(`"CS"` → `"cs"`).
  - `_normalize_difficulty`: `DIFFICULTY_KOREAN_INPUT_MAP`에 있으면 변환, 없으면
    (예: 이미 영문으로 온 내부 테스트 값) 그대로 통과시켜 pydantic 기본 검증에 위임.
  - `_normalize_ai_attitude_style`: 위와 동일한 패턴.
  - `_normalize_cs_categories`: 리스트의 각 원소를 매핑 시도하되, **매핑에 없는 값은
    조용히 무시하지 않고 그대로 남겨 pydantic이 enum 검증 에러(422)를 내게 한다** —
    조용히 무시하면 "카테고리 필터가 의도보다 좁게 걸리는" 디버깅하기 어려운 버그로
    이어지기 때문에 의도적으로 fail-fast하게 만들었다.
- `_validate_cs_category` (`model_validator`)를 다중 선택 버전으로 교체: CS 면접인데
  `cs_categories`가 비어있으면 422. 최대 3개 제한은 `Field(max_length=3)`가 이미
  강제하므로 이 validator는 "최소 1개" 조건만 확인한다.
- `GeneratedQuestion`/`QuestionGenerateResponse`(응답 스키마)는 이번 작업에서
  변경하지 않았다 — 응답도 snake_case 그대로이므로 별도 변환이 필요 없다.

#### `services/rag_service.py`

CS 카테고리 관련 함수를 전부 "단일 → 리스트(최대 3개)"로 바꾸고, `retrieve_context()`에
특정 문서 지정 기능을 추가했다:

- `_cs_category_where(cs_categories: list[CSCategory])`: 선택된 카테고리들의
  `CS_CATEGORY_RAW_MAP` 매핑을 **합쳐서(union)** `$in` 필터를 만든다 — 여러 카테고리
  중 하나라도 매칭되면 검색 대상이 되는 것이 자연스러운 동작이라고 판단.
- `_has_no_seed_data(cs_categories: list[CSCategory])`: 선택된 카테고리 전부의 매핑을
  합쳤을 때 완전히 비어있으면 `True`.
- `retrieve_cs_knowledge()`/`retrieve_cs_knowledge_random()`: 파라미터를
  `cs_category: CSCategory | None` → `cs_categories: list[CSCategory]`로 변경, 내부에서
  위 두 함수를 그대로 호출. 로그의 `category=%s`도 `categories=%s`로 바꿔 리스트를
  남긴다. `retrieve_cs_knowledge_random()`의 "카테고리 내부에서 무작위 추출" 로직 자체는
  그대로 두었다 — 여러 카테고리가 합쳐진 pool에서 무작위로 뽑는 것으로 동작이 자연스럽게
  확장되며, 카테고리별 균등 배분(예: 카테고리마다 정확히 N개씩)은 이번 범위에 포함하지
  않았다(필요하면 `DOC_TYPE_WEIGHTS`처럼 나중에 별도 개선).
- `retrieve_context()`에 `target_ids: dict[DocType, int] | None = None` 파라미터
  **신규 추가**([신규] `resume_id`/`cover_letter_id`/`github_repo_id` 반영). 주어지면
  (예: `{DocType.RESUME: 10}`) 해당 doc_type 검색 시 "이 사용자의 해당 타입 문서
  전체"가 아니라 "이 특정 target_id 문서"로 범위를 좁힌다. 두 분기 모두 처리했다:
  - 가중치 있는 분기(JOB/CS/TECH/PORTFOLIO): doc_type별 `where` 절에 `target_id`
    조건을 추가로 걸었다.
  - 가중치 없는 분기(COMPREHENSIVE 등, 기존엔 `{"user_id": user_id}`로 doc_type
    구분 없이 통으로 조회): 원래 목적("문서 종류 구분 없이 유사도 순")은 유지하되,
    `target_ids`가 주어졌을 때만 예외적으로 doc_type별로 나눠 `target_id` 필터를
    걸도록 분기를 추가했다 — target_ids가 있는데 조용히 무시되는 상황을 만들지
    않기 위함이다.
  - **기본값 `None`으로 하위 호환 유지**: `followup_service.py`/`answer_service.py`는
    이 함수를 인자 추가 없이 그대로 호출하며, 이 경우 `target_ids`가 빈 dict로
    처리되어 기존과 완전히 동일하게 동작한다(이번 작업으로 건드리지 않음).

#### `services/question_service.py`

- `_build_cs_query()`: `req.cs_categories`의 각 라벨을 `", "`로 이어붙여 하나의 쿼리
  문자열로 조합하도록 변경.
- `_build_target_ids()` 신규 헬퍼: `resume_id`/`cover_letter_id`/`github_repo_id` 중
  값이 있는 것만 모아 `retrieve_context()`가 기대하는 `dict[DocType, int]`로 변환.
- `generate_questions()`:
  - `target_ids = _build_target_ids(req)`를 구성해 CS/비CS 분기의 모든
    `retrieve_context()` 호출에 전달.
  - CS 분기: `retrieve_cs_knowledge(cs_query, cs_categories=req.cs_categories)`,
    `retrieve_cs_knowledge_random(req.cs_categories)`로 인자명/값 변경.
  - COMPREHENSIVE 분기: `retrieve_cs_knowledge(cs_query, cs_categories=req.cs_categories)`
    동일 적용(`req.cs_categories`가 빈 리스트여도 `_has_no_seed_data`가 `True`를
    반환해 빈 리스트를 안전하게 돌려줌).
  - `build_question_prompt()` 호출: `cs_category=` → `cs_categories=req.cs_categories`,
    `interviewer_style=req.interviewer_style` → `interviewer_style=req.ai_attitude_style`
    로 변경(BE wire 필드명은 바뀌었지만, `build_question_prompt()` 자체의 파라미터명은
    "면접관 스타일"이라는 프롬프트 내부 개념을 그대로 유지하기 위해 `interviewer_style`
    그대로 두었다 — 호출부에서 넘기는 값의 출처만 바뀐 것).

#### `prompts/templates.py`

`build_question_prompt()`의 `cs_category: CSCategory | None` 파라미터를
`cs_categories: list[CSCategory] | None`로 변경. "## CS 카테고리" 섹션 생성 로직을
복수 카테고리 대응으로 바꾸고, 여러 카테고리가 주어졌을 때 "한쪽에만 질문이 몰리지
않도록 골고루 다루라"는 지시문을 추가했다. `interviewer_style` 관련 프롬프트 섹션(2절
작업에서 이미 반영됨)은 이번 작업에서 변경하지 않았다 — 호출부에서 넘기는 값의
출처(`req.ai_attitude_style`)만 바뀌었을 뿐, 템플릿 로직 자체는 무관하다.

### 3.4 범위 제한

- 이번 작업은 `POST /api/v1/interviews/questions`(`QuestionGenerateRequest`) 요청
  처리에만 적용했다. `FollowupRequest`/`AnswerSupplementRequest`, `EmbedRequest` 등
  다른 스키마는 건드리지 않았다.
- `retrieve_context()`의 `target_ids` 파라미터는 기본값 `None`으로 두어,
  `followup_service.py`/`answer_service.py`가 이 함수를 인자 추가 없이 그대로
  호출해도 기존과 동일하게 동작하는 하위 호환을 유지했다.
- `QuestionGenerateResponse`(응답 스키마)는 이번에 변경하지 않았다.

### 3.5 영향받는 파일

- `schemas/common.py` — 한글 wire 값 매핑 테이블 3종 신규 추가(enum 값 자체는 불변).
- `schemas/interview.py` — `QuestionGenerateRequest` 필드/검증 로직 전면 개편.
- `services/rag_service.py` — CS 카테고리 관련 4개 함수를 리스트 기반으로 변경,
  `retrieve_context()`에 `target_ids` 파라미터 추가.
- `services/question_service.py` — `_build_cs_query()` 변경, `_build_target_ids()`
  신규, `generate_questions()` 호출부 갱신.
- `prompts/templates.py` — `build_question_prompt()` 파라미터/섹션 로직 변경.
- `README.md` — "질문 생성" API 섹션을 새 요청 형식으로 전면 갱신.

`FollowupRequest`/`AnswerSupplementRequest`/`EmbedRequest`, `followup_service.py`,
`answer_service.py`, `db/chroma.py`, `embedding_service.py`는 이번 작업과 무관하며
수정하지 않았다.

### 3.6 확인 필요 / 가정 사항 (BE 확인 필요) — 이 문서화의 핵심

1. **`difficulty` 한글 값**: 정확히 `"하"`/`"중"`/`"상"` 3개인지 BE 확인 필요
   (현재 추정값 — `DIFFICULTY_KOREAN_INPUT_MAP` 참고).
2. **`ai_attitude_style` 값**: `"편안한 면접"`/`"실전 면접"` 2개는 추정값이다.
   `"압박면접"`만 실제 BE 예시 요청에서 확인됨. BE가 실제로 보내는 정확한 3개
   문자열 확인 필요(`INTERVIEWER_STYLE_KOREAN_INPUT_MAP` 참고).
3. **`cs_categories` 나머지 6개 카테고리**: BE 예시엔 `"자료구조"`/`"네트워크"`/
   `"운영체제"` 3개만 등장했다. 나머지 6개(WEB/데이터베이스/보안/소프트웨어 공학/AI/
   언어 및 프레임워크)의 정확한 한글 표기를 BE와 맞춰야 한다
   (`CS_CATEGORY_KOREAN_INPUT_MAP` 참고, 현재 값은 미확인 추정).
4. **id 필드가 문자열로 옴**: `user_id`/`ai_interview_id`/`resume_id`/
   `cover_letter_id`/`github_repo_id`가 `"1"`처럼 문자열로 오는데, pydantic이 숫자
   문자열을 int로 자동 변환하므로 스키마 타입은 `int`로 유지해도 동작은 확인됨
   (검증 완료, 3.7절 참고). 다만 향후 숫자가 아닌 값(UUID 등)으로 바뀔 가능성이
   있는지도 BE와 확인해두면 좋다.
5. **응답 스키마는 이번 범위에 포함하지 않음**: `QuestionGenerateResponse`는
   그대로 유지했다.
6. **`cs_category`(단일) → `cs_categories`(복수) — Breaking Change**: 이 필드를
   참조하던 기존 BE 연동 코드가 있다면 전부 고쳐야 한다.
7. **`interviewer_style` → `ai_attitude_style` — Breaking Change**: 필드명 자체가
   바뀌었으므로, 기존 BE 연동 코드 기준으로는 이것도 Breaking Change다(2절에서
   `interviewer_style`을 신규 추가했었는데, 이번 3절 작업으로 실제 배포 전에 필드명이
   다시 바뀐 것 — 아직 BE가 이 필드를 실제로 쓰기 전이라 실질적인 하위 호환 이슈는
   없지만, BE 팀에 최종 필드명이 `ai_attitude_style`임을 명확히 공지할 것).

### 3.7 검증 방법

- `python -m py_compile schemas/common.py schemas/interview.py services/rag_service.py services/question_service.py prompts/templates.py` — 문법 오류 없음 확인.
- `QuestionGenerateRequest`를 실제 값(BE 예시 기반 가짜 데이터)으로 인스턴스화해
  검증 로직을 단위 테스트했다(임시 venv에 `pydantic==2.9.2`만 설치, chromadb/GMS 등
  무거운 의존성은 스키마 계층과 무관해 불필요 — 총 11개 케이스 전부 통과):
  1. `interview_type="CS"`(대문자) → `InterviewType.CS`로 정규화되는지.
  2. `interview_type="cs"`(소문자)도 동일하게 처리되는지.
  3. `difficulty="중"` → `Difficulty.NORMAL`로 매핑되는지.
  4. `ai_attitude_style="압박면접"` → `InterviewerStyle.PRESSURE`로 매핑되는지.
  5. `cs_categories`에 3개(`["자료구조", "네트워크", "운영체제"]`) 넣었을 때 422 없이
     통과하고, 각각 올바른 `CSCategory`로 매핑되는지.
  6. `cs_categories`에 4개 넣으면 `max_length=3` 검증으로 `ValidationError`(422)가
     나는지.
  7. `interview_type="cs"`인데 `cs_categories=[]`(빈 배열)이면 `ValidationError`가
     나는지.
  8. `interview_type="job"`이고 `cs_categories=[]`이면(CS가 아니므로) 정상 통과하는지.
  9. `cs_categories`에 매핑되지 않는 문자열(예: `"존재하지않는카테고리"`)이 섞이면
     `ValidationError`가 나는지.
  10. 모든 선택 필드를 생략했을 때 기본값(`difficulty=NORMAL`,
      `ai_attitude_style=REALISTIC`, `cs_categories=[]`, `resume_id`/
      `cover_letter_id`/`github_repo_id`=`None`)이 올바르게 적용되는지.
  11. `company_name`이 여전히 선택 필드로 동작해 하위 호환이 유지되는지.
  12. `user_id`/`ai_interview_id`가 숫자 문자열(`"1"`)로 와도 `int`로 자동 변환되는지.
- 실제 GMS LLM 호출/Chroma 연동을 통한 통합 테스트는 수행하지 않음(`.env`의 GMS 키,
  실행 중인 Chroma 필요). BE/QA 단계에서 추가로 확인해야 하는 것:
  - `resume_id`/`cover_letter_id`/`github_repo_id`를 지정했을 때 실제로 RAG 검색이
    "그 문서"로만 좁혀지는지(예: 이력서를 2개 등록해두고 특정 `resume_id`만 지정 →
    지정 안 한 이력서 내용이 프롬프트 컨텍스트에 섞여 들어가지 않는지).
  - `cs_categories`를 2~3개 선택했을 때 생성된 질문들이 실제로 여러 카테고리에
    걸쳐 나오는지(하나의 카테고리에만 쏠리지 않는지).
  - 3.6절의 "BE 확인 필요" 7개 항목이 실제 값과 일치하는지 BE 팀과 교차 확인.

## 4. 지정 문서 참고 범위를 꼬리질문/답변 보완까지 세션 전체로 확장

> 대상: `POST /api/v1/interviews/followup`, `POST /api/v1/interviews/answers/supplement`
> (3절에서 질문 생성에만 적용했던 것을 같은 날 바로 확장한 후속 작업)

### 4.1 작업 배경

3절 작업 직후 "질문 생성(`/questions`) 때 사용자가 고른 이력서/자소서/GitHub만
분석하도록 파라미터를 받았는데, 해당 문서만 이 면접 세션 전체에서 계속 쓰이도록
로직이 되어있는가?"라는 질문을 받고 코드를 재확인했다.

확인 결과: **아니었다.** `retrieve_context()`에 `target_ids`를 넘기는 곳은
`question_service.py`(질문 생성) 하나뿐이었고, `followup_service.py`(꼬리질문)와
`answer_service.py`(답변 보완)는 여전히 `target_ids` 없이 호출하고 있었다. 그
결과 같은 면접 세션 안에서도 **질문 생성 단계에서만** 지정 문서로 검색 범위가
좁혀지고, 그 이후 꼬리질문/답변 보완 단계에서는 다시 사용자의 **해당 doc_type
전체**(예: 이력서를 여러 개 등록해뒀다면 지정 안 한 이력서까지 전부)가 검색
대상이 되는 비일관적인 상태였다. 이는 실수가 아니라 3절 작업 지시서에 "이번
작업은 `/questions`에만 적용, `followup_service.py`/`answer_service.py`는
건드리지 말 것"이라는 명시적 범위 제한이 있었기 때문이다. 이 사실을 사용자에게
보고했고, "지금 확장해달라"는 답변을 받아 이어서 진행했다.

### 4.2 변경 사항

#### `services/rag_service.py`

`question_service.py` 안에 로컬로만 있던 `_build_target_ids()` 헬퍼를
`build_target_ids(resume_id, cover_letter_id, github_repo_id)`라는 이름의 **공용
함수로 승격**해 `retrieve_context()` 바로 위에 두었다. `QuestionGenerateRequest`
객체 전체가 아니라 개별 int 인자 3개를 받도록 설계한 이유: 이 시점부터
`QuestionGenerateRequest`/`FollowupRequest`/`AnswerSupplementRequest` 세 스키마
모두가 동일한 3개 필드(`resume_id`/`cover_letter_id`/`github_repo_id`)를 갖게
되는데, 특정 스키마 타입에 결합시키지 않아야 세 서비스가 각자 자기 request
객체를 그대로 넘겨 재사용할 수 있기 때문이다.

`retrieve_context()`의 docstring도 갱신 — "기본값 `None`은 `followup_service.py`/
`answer_service.py`가 이 인자 없이 호출하기 위한 하위 호환용"이라는 기존 설명이
이제 틀린 설명이 되었으므로(두 서비스도 이제 넘김), "세 서비스 모두 동일한
target_ids를 넘겨 세션 전체에서 일관되게 문서를 좁힌다"는 내용으로 수정했다.

#### `schemas/interview.py`

`FollowupRequest`, `AnswerSupplementRequest`에 각각 `resume_id`/`cover_letter_id`/
`github_repo_id`(모두 `int | None`, 선택 필드) 3개를 신규 추가했다. 주석에 "AI
서비스는 세션 상태를 저장하지 않는 stateless 구조이므로, 질문 생성 때 지정한 값을
BE가 이후 호출에도 매번 동일하게 실어 보내야 한다"는 이유를 명시했다 — 이 부분을
빠뜨리면 필드는 있는데 항상 비어있는 상태로 호출되어 사실상 효과가 없는 상황이
될 수 있어, BE가 반드시 인지해야 하는 부분이다.

#### `services/question_service.py`

로컬 `_build_target_ids()` 함수를 제거하고 `services.rag_service.build_target_ids`를
가져다 쓰도록 변경. 동작 자체는 동일(3절에서 검증한 로직 그대로), 중복 제거만 수행.

#### `services/followup_service.py`, `services/answer_service.py`

각각 RAG 검색 직전에 `target_ids = build_target_ids(req.resume_id, req.cover_letter_id, req.github_repo_id)`를
구성해 `retrieve_context(..., target_ids=target_ids)`로 넘기도록 수정했다. 그
외 로직(rubric 채점, 답변 보완 프롬프트 구성 등)은 변경하지 않았다.

#### `README.md`

"3. 꼬리질문", "4. 답변 보완" API 섹션 예시에 `resume_id`/`cover_letter_id`/
`github_repo_id`를 추가하고, "질문 생성 때와 동일한 값을 그대로 넘겨야 한다"는
안내 문구를 넣었다.

### 4.3 영향받는 파일

- `services/rag_service.py` — `build_target_ids()` 신규 공용 함수(질문 생성 코드에서
  이전), `retrieve_context()` docstring 갱신.
- `schemas/interview.py` — `FollowupRequest`/`AnswerSupplementRequest`에 문서 id
  필드 3개씩 신규 추가.
- `services/question_service.py` — 로컬 헬퍼 제거, 공용 함수로 교체(동작 변경 없음).
- `services/followup_service.py`, `services/answer_service.py` — RAG 검색 시
  `target_ids` 반영.
- `README.md` — `/followup`, `/answers/supplement` 섹션에 신규 필드 반영.

### 4.4 영향받는 API 계약 (BE 연동 필요)

`FollowupRequest`, `AnswerSupplementRequest` 요청 바디에 각각 필드 3개가 **선택
필드로** 추가됨(하위 호환 — 안 보내도 422 없이 동작하지만, 안 보내면 4.1절의
비일관 문제가 그대로 남는다는 점에 유의):

```jsonc
// POST /api/v1/interviews/followup, POST /api/v1/interviews/answers/supplement 공통 추가분
{
  "resume_id": 1,
  "cover_letter_id": 1,
  "github_repo_id": 1
}
```

**BE가 반드시 해야 할 일**: 면접 시작 시(`/questions`) 사용자가 지정한
`resume_id`/`cover_letter_id`/`github_repo_id` 값을 세션 어딘가(Redis 등)에
저장해뒀다가, 같은 면접의 `/followup`, `/answers/supplement` 요청을 보낼 때마다
**동일한 값을 매번 함께 실어 보내야** 한다. AI 서비스는 상태를 저장하지 않으므로,
이 값을 빠뜨리면 필드가 있어도 항상 `None`으로 처리되어 3절 이전과 동일하게
사용자의 전체 문서가 검색된다(에러는 나지 않으므로 이 문제는 조용히 발생한다 —
BE 통합 테스트 시 반드시 확인 필요).

### 4.5 검증 방법

- `python -m py_compile services/rag_service.py schemas/interview.py services/question_service.py services/followup_service.py services/answer_service.py` — 문법 오류 없음 확인.
- 임시 venv(`pydantic==2.9.2`)에서 `db.chroma`/`config`를 최소 스텁으로 대체해
  (chromadb 등 무거운 의존성 없이 스키마/헬퍼 로직만 검증) 다음을 확인:
  1. `FollowupRequest`가 `resume_id`/`cover_letter_id`/`github_repo_id`를 정상
     수신하는지.
  2. 세 필드를 생략하면 기본값 `None`으로 처리되는지(하위 호환).
  3. `AnswerSupplementRequest`가 세 필드 중 일부만 지정해도(`resume_id`만 등)
     정상 동작하는지.
  4. `build_target_ids()`가 `None`/일부 지정/전부 지정 케이스에서 각각 올바른
     `dict[DocType, int]`를 만드는지(빈 dict, 부분 dict, 전체 dict).
- 실제 Chroma/GMS 연동 통합 테스트는 수행하지 않음. BE/QA 단계에서 반드시 확인:
  - 면접 하나를 시작해 `/questions`에 `resume_id=10`을 지정한 뒤, 같은 면접의
    `/followup`·`/answers/supplement` 호출에도 `resume_id=10`을 실어 보내는지,
    빠뜨렸을 때 검색 범위가 다시 넓어지는지(에러 없이 조용히 넓어지므로 로그로
    확인: `RAG 조회` 관련 로그의 `target_ids=` 값).
