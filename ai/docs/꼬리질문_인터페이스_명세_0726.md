# 꼬리질문 API 인터페이스 명세 — 2026-07-26 (BE/FE 전달용)

> 대상: `POST /api/v1/interviews/followup`
> AI 서버가 rubric narrowing 방식으로 전환하면서 이 API의 요청/응답 형식이
> 전면적으로 바뀌었다(Breaking Change). 이 문서는 **AI 서버가 무엇을 주고받는지**를
> 정리한 안내 문서이며, 여기 적힌 "확인 요청" 항목은 코드로 확정된 스펙이 아니라
> BE/FE 담당자와 조율이 필요한 부분이다.
>
> 변경 배경(rubric 진동 문제)과 검토했다가 기각한 대안은 `docs/AI_작업일지_0726.md`
> 참고.

## 1. 왜 형식이 바뀌었는가 (한 문단 요약)

기존에는 매 턴 rubric 전체를 AI 서버가 재채점했는데, AI 서버가 stateless라
"이전 턴에 어떤 rubric이 이미 통과됐는지" 스스로 알 방법이 없어 같은 rubric이
턴마다 pass/fail을 오가는 무한 반복이 발생했다. 이제는 **AI 서버가 통과한 rubric
항목을 응답에서 제거해서 내려주고**, 다음 턴 요청에는 미통과 항목만 실려 오는
것을 전제로 동작한다. 그래서 이번 전환에서 가장 중요한 계약은: **호출측이 응답의
`next_question`을 가공 없이 그대로 다음 요청의 `question`에 넣어야 한다**는 것이다.

## 2. 새 요청 형식

```json
{
  "user_id": 1,
  "interview_type": "cs",
  "resume_id": 1,
  "cover_letter_id": 1,
  "github_repo_id": 1,
  "question": {
    "order": 1,
    "question": "Redis를 캐시로 도입하셨다고 하셨는데, TTL 설정 기준은 어떻게 정하셨나요?",
    "rubric": [
      "TTL 값을 정한 구체적인 근거를 설명했는가",
      "캐시 무효화 전략을 함께 언급했는가"
    ],
    "topic": "캐싱 전략",
    "source": "cover_letter",
    "depth": 0
  },
  "answer": "레디스를 캐시로 도입한 이유는 저도 잘 모르겠습니다."
}
```

| 필드 | 타입 | 설명 |
|---|---|---|
| `user_id` | int | 기존과 동일 |
| `interview_type` | string | 기존과 동일 (`job`/`cs`/`tech`/`portfolio`/`comprehensive`) |
| `resume_id`/`cover_letter_id`/`github_repo_id` | int\|null | 기존과 동일, 선택 |
| `ai_interview_id` | int\|null | (신규 표기 없음, 선택) — 3절 "확인 요청" 참고 |
| `question` | object | 아래 표 |
| `answer` | string | 사용자 답변(STT 텍스트). 기존 `user_answer`에서 이름 변경 |

`question` 객체:

| 필드 | 타입 | 설명 |
|---|---|---|
| `order` | int | 질문 순서 (부모 질문과 동일 값 유지) |
| `question` | string | 직전 질문(기본 질문 또는 꼬리질문) 원문 |
| `rubric` | list[string] | **"아직 통과하지 못한 채점 기준"만** — 전체 기준이 아니다 |
| `topic` | string\|null | 질문 주제 태그 |
| `source` | string\|null | 근거 문서 출처 |
| `depth` | int | 지금까지 이 질문에 나간 꼬리질문 횟수 |

### 기존 형식과의 차이 (Breaking Change)

| 변경 | 내용 |
|---|---|
| 이동 | `parent_question`(최상위) → `question.question` |
| 이동 + 의미 재정의 | `rubric`(최상위, "전체 채점 기준") → `question.rubric`("아직 통과 못한 기준"만) |
| 이동 | `depth`(최상위) → `question.depth` |
| 이름 변경 | `user_answer` → `answer` |
| 유지 | `interview_type`, `resume_id`, `cover_letter_id`, `github_repo_id` |
| 유지(응답에서는 제거) | `ai_interview_id` |
| 신규 | `question.order`, `question.topic`, `question.source` |

## 3. 새 응답 형식

```json
// 꼬리질문이 필요한 경우
{
  "is_pass": false,
  "next_question": {
    "order": 1,
    "question": "그렇다면 TTL을 짧게 잡았을 때와 길게 잡았을 때 각각 어떤 문제가 생길 수 있을까요?",
    "rubric": ["TTL 값을 정한 구체적인 근거를 설명했는가"],
    "topic": "캐싱 전략",
    "source": "cover_letter",
    "depth": 1
  }
}

// 꼬리질문이 필요 없는 경우 (모두 통과, 또는 depth 상한 도달)
{
  "is_pass": true,
  "next_question": null
}
```

- `next_question`은 `/questions` 응답의 `GeneratedQuestion`과 **동일한 필드
  구성**이다 — 소비하는 쪽에서 두 객체를 같은 타입으로 다룰 수 있게 하기 위함.
- 기존 `rubric_results`(항목별 pass/fail), `all_passed`, `capped`,
  `ai_interview_id` 필드는 전부 제거됐다.

### `is_pass=true`의 두 가지 의미

`is_pass=true`는 다음 두 경우를 모두 포함하며, 응답 자체에는 이를 구분하는
별도 플래그가 없다.

1. **모든 rubric을 실제로 통과함.**
2. **꼬리질문 횟수 상한(`depth`)에 도달해 강제로 종료함** — 이 경우 통과하지
   못한 rubric이 남아있어도 무시하고 종료한다.

두 경우를 구분해야 한다면(예: 리포트에서 "정말 다 통과한 질문"과 "그냥 넘어간
질문"을 다르게 표시하려는 경우), 호출측이 **요청에 실어 보낸 `question.depth`
값**으로 판단해야 한다 — `question.depth`가 `MAX_FOLLOWUP_PER_QUESTION`(현재
서버 기본값 2) 이상이었다면 2번 경우다.

## 4. 호출측 요청 사항

### FE에게

응답의 `next_question` 객체를 다음 턴 요청의 `question`에 **가공 없이 그대로**
넣어야 한다. rubric을 임의로 추가·복원하거나 다른 값으로 대체하면, 이미 통과한
기준이 되살아나 진동(같은 rubric이 pass/fail을 반복하는 문제, 1절 참고)이
그대로 재발한다.

### BE에게

요청을 AI 서버로 그대로 패스스루하되, **`/questions` 시점의 원본 rubric 전체를
별도로 보관**해야 한다. narrowing이 진행될수록 `/followup` 요청에 실리는
`question.rubric`은 점점 줄어들기 때문에, AI 서버는 "이 질문에 원래 rubric이
몇 개였는지"를 더 이상 알지 못한다. 면접 종료 후 리포트/총평 등에서 "원래
채점 기준 대비 실제로 몇 개를 통과했는지"가 필요하다면, 그 계산에 필요한 원본
rubric은 BE가 `/questions` 응답 시점에 저장해둔 값을 써야 한다.

## 5. 확인 요청 (AI 서버가 정한 기본값 — 조정 필요 시 알려주시면 반영)

- **요청에 `interview_type` 필드가 계속 필요합니다.** AI 서버 내부적으로 면접
  유형별 문서 참고 비율, 프롬프트 가이드에 이 값을 계속 사용하고 있어, 이번
  개편에서도 요청 필드로 유지했습니다.
- **요청에 `ai_interview_id`(선택, int)를 계속 보내주시면 좋겠습니다.** 응답에는
  포함하지 않지만, AI 서버 로그에 세션 식별자가 남아야 장애 발생 시 추적이
  가능합니다.
- **`question`을 중첩 객체로 받는 구조로 확정했습니다.** BE의 요청 DTO에
  `order`/`topic`/`source` 필드 추가가 필요할 수 있습니다. 응답 DTO도
  `is_pass`/`next_question` 구조로 맞춰주셔야 합니다 — 현재 AI 서버가 이
  형식으로 주고받으니 확인 부탁드립니다.
- **네이밍은 snake_case로 통일**했습니다(`is_pass`, `next_question`) — 기존
  요청 wire 포맷이 이미 snake_case였던 것과 일관되게 맞춘 것입니다.
