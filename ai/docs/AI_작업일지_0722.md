## 1. 루브릭 기반 동적 꼬리질문 아키텍처 전환 (Phase 1 + Phase 2 + 답변 보완 재설계)

> 범위: **Phase 1(질문 + 루브릭 생성)**, **Phase 2(실시간 채점 + 꼬리질문 One-Call 생성)**,
> 그리고 기존 계획에서 **재설계된 "답변 보완"** (사용자가 답변을 제출할 때마다 비동기로
> AI 보완 답변을 생성하는 신규 플로우)까지 구현했다. "면접 전체에 대한 총평/피드백"을
> 만드는 최종 리포트 엔드포인트는 아직 착수하지 않았으며, 남은 작업은 [2절](#2-잔여-작업--면접-총평피드백-리포트-미착수)에 정리했다.

### 1.1 무엇을 했는가 (요약)

**Phase 1 — 질문 + 루브릭 생성**
기존 질문 생성 로직은 "면접 질문 N개 + 예상 답안"만 생성했다. 여기에 **질문마다
채점 기준(rubric) 2~3개를 함께 생성**하도록 바꿨다. 질문 개수도 10개 → 5개로
줄였다(정적으로 많이 만들어두는 대신, 답변 품질에 따라 동적으로 깊이를 확보하는
쪽으로 전략을 바꿨기 때문).

**Phase 2 — 실시간 채점 + 동적 꼬리질문**
기존 꼬리질문 로직은 "꼬리질문이 필요한가?"를 LLM이 애매하게(`need_followup` bool)
판단하고, `followup_depth` 카운터로만 종료를 제어했다. 이번 작업에서 이를 rubric
기반 채점으로 전면 교체했다:
- BE가 Phase 1에서 받은 rubric을 답변과 함께 `/followup`에 넘기면,
- LLM 1회 호출(One-Call JSON Mode)로 **rubric 항목별 pass/fail 채점**과
  **통과 못한 항목을 겨냥한 꼬리질문 생성**을 동시에 수행한다.
- 종료 조건이 "카운터 소진"에서 "**rubric을 실제로 다 통과했는가(`all_passed`)**"로
  바뀌었다. 다만 rubric이 계속 통과되지 못해 대화가 무한정 이어지는 것을 막기 위해,
  `followup_depth`를 **안전장치용 상한 체크**로만 남겨뒀다(주 종료 조건은 아님).

**답변 보완 재설계 — `expected_answer` 폐기 → 답변 제출 후 비동기 `ai_answer` 생성 (신규)**
원래 계획(Phase 3)은 "면접 종료 후 전체 대화 기록을 한 번에 처리해 모범 답안을
만드는" 방식이었다. 작업 중 **설계를 다시 논의**해 다음과 같이 바꿨다:
- `GeneratedQuestion.expected_answer`, `FollowupResponse.expected_answer` — 질문/꼬리질문을
  "만들 때" 미리 써두던 예상 답안 필드를 **완전히 제거**했다. 질문 생성 시점에는
  아직 사용자가 답하지 않았으므로, 미리 만든 답을 보여주는 것 자체가 개념적으로
  맞지 않다고 판단.
- 대신 `ai_interview_questions.ai_answer` 컬럼의 의미를 **"사용자가 실제로 제출한
  답변을 AI가 보완한 결과"**로 재정의했다. 이 값은 사용자가 답변을 제출한 직후
  **백그라운드에서 비동기로** 신규 엔드포인트(`POST /api/v1/interviews/answers/supplement`)를
  호출해 채워진다 — 기본 질문 답변이든 꼬리질문 답변이든 구분 없이 매번 호출된다.
  Phase 2에서 이미 rubric 채점을 했다면 그 결과(`rubric_results`)를 함께 넘겨,
  "정확히 어떤 기준을 놓쳤는지" 알고 보완하도록 설계했다(재채점 불필요).
- 이 데이터(질문, 사용자 답변, `ai_answer`)는 **면접 최종 완료 화면**에서 지원자에게
  "전반적인 분석/피드백"과 함께 노출하는 데 쓰일 예정이다. "전반적인 분석/피드백"
  자체(면접 전체를 아우르는 총평)는 이번 작업 범위가 아니며 별도 엔드포인트로
  남아있다([2절](#2-잔여-작업--면접-총평피드백-리포트-미착수) 참고).

세 가지 변경 모두 엔드포인트 URL(`/api/v1/interviews/questions`, `/followup`)은
유지했고, `/answers/supplement`만 신규 추가했다. Phase 1은 필드 추가 위주라 하위
호환이 유지되지만, **Phase 2(`FollowupRequest`/`FollowupResponse`)와 답변 보완 재설계
(`expected_answer` 제거)는 기존 BE 연동을 깨는 Breaking Change**다([1.4절](#14-be와-반드시-맞춰야-할-사항-breaking-change) 참고).

기존 RAG 파이프라인(`rag_service.py`), 임베딩 서비스, Chroma DB 연동은 이 단계에서는
건드리지 않았다(이후 [3절](#3-cs-카테고리-제한--면접-유형별-문서-참고-비율-기능) 작업에서 별도로 수정).

### 1.2 전체 코드 흐름 (요청 → 응답)

#### 1.2.1 Phase 1 — 질문 생성 (`POST /api/v1/interviews/questions`)

```
[BE: Spring Boot]
   │  POST /api/v1/interviews/questions
   │  { user_id, ai_interview_id, interview_type, difficulty,
   │    company_name?, position?, question_count? }
   ▼
[routers/interview.py] create_questions()
   │  - services.question_service.generate_questions() 에 위임
   │  - GMSError / 기타 예외를 HTTP 502 / 500 으로 변환
   ▼
[services/question_service.py] generate_questions()
   │  1) count = req.question_count or settings.question_count  (기본 5개)
   │  2) _build_rag_query() 로 검색 쿼리 문자열 구성
   │  3) rag_service.retrieve_context() 로 사용자 개인 문서 검색
   │     (CS/종합 면접이면 retrieve_cs_knowledge() 로 CS 전역 지식도 추가 검색)
   │  4) format_context() 로 검색 결과를 프롬프트용 텍스트로 정리
   │  5) build_question_prompt() 로 최종 프롬프트 생성
   │     - rubric_min_count/rubric_max_count(기본 2~3) 를 프롬프트에 전달
   │     - "질문마다 rubric을 N~M개 작성하라"는 지시문과 출력 예시 포함
   │     - "expected_answer는 생성하지 말라"는 지시 포함 (답변 보완 재설계)
   │  6) gms_client.chat_json(QUESTION_SYSTEM, prompt) 로 GMS LLM 호출
   │  7) 응답 JSON의 questions[] 를 GeneratedQuestion 객체로 정규화
   │     - rubric 필드: 비문자열/빈 문자열 제거, rubric_max_count 초과분 트리밍
   │     - expected_answer 는 파싱하지 않음(스키마에서 필드 자체가 제거됨)
   │     - order 재정렬
   │  8) rubric이 비어있는 질문 수를 로그로 남김 (모니터링용)
   ▼
[routers/interview.py] → QuestionGenerateResponse 반환
   │  { ai_interview_id, interview_type,
   │    questions: [ { order, question, rubric: [...], topic, source }, ... ],
   │    rag_used }
   ▼
[BE: Spring Boot]
   - 질문 + rubric 을 세션 상태(예: Redis Queue)에 저장
   - 사용자가 답변을 제출할 때마다 해당 질문의 rubric 을 /followup 호출 시 함께 전달
```

#### 1.2.2 Phase 2 — 꼬리질문 채점/생성 (`POST /api/v1/interviews/followup`)

```
[BE: Spring Boot]
   │  POST /api/v1/interviews/followup
   │  { user_id, ai_interview_id, parent_question, rubric: [...],
   │    user_answer, interview_type, followup_depth }
   │  ※ rubric 은 Phase 1 에서 BE가 저장해둔 해당 질문의 rubric.
   │    재꼬리질문인 경우, 아직 통과 못한 rubric 항목만 추려 넘기는 것을 전제로 함.
   ▼
[routers/interview.py] create_followup()
   │  - services.followup_service.generate_followup() 에 위임
   ▼
[services/followup_service.py] generate_followup()
   │  1) 안전장치 체크: followup_depth >= max_followup_per_question(기본 2) 이면
   │     LLM 호출 없이 즉시 종료 → all_passed=true, capped=true, rubric_results=[]
   │     (rubric을 실제로 채점하지 않았다는 뜻이므로 "진짜 통과"와 구분됨)
   │  2) query = f"{parent_question} {user_answer}" 로 RAG 재검색(top_k=3, 근거 보강)
   │  3) build_followup_prompt() 로 프롬프트 생성
   │     - rubric 목록을 번호 매겨 그대로 노출
   │     - "rubric 항목별 채점 + 통과 못한 항목 중 1개를 겨냥한 꼬리질문 생성" 지시
   │     - "꼬리질문의 expected_answer는 생성하지 말라"는 지시 포함 (답변 보완 재설계)
   │  4) gms_client.chat_json(FOLLOWUP_SYSTEM, prompt) 로 GMS LLM 1회 호출
   │     (rubric 채점 + 꼬리질문 생성을 한 번에 처리 = One-Call JSON Mode)
   │  5) rubric_results 파싱 & 정규화
   │     - LLM이 criterion 문구를 누락하면 입력 rubric의 같은 순번 항목으로 보정
   │     - passed 는 bool 로 강제 캐스팅
   │  6) all_passed 서버 측 재계산: rubric_results 가 모두 passed=true 일 때만 true
   │     (LLM이 보낸 all_passed 플래그를 그대로 신뢰하지 않고 재검증)
   │  7) 방어 처리: all_passed=false 인데 followup_question 이 비어있으면
   │     교착 상태를 막기 위해 all_passed=true 로 강제 전환
   │  8) followup_depth 갱신: 실제로 꼬리질문이 나간 경우에만 +1
   ▼
[routers/interview.py] → FollowupResponse 반환
   │  { ai_interview_id, rubric_results: [{criterion, passed, reason}, ...],
   │    all_passed, followup_question, followup_depth, capped }
   ▼
[BE: Spring Boot]
   - all_passed=true  → 다음 기본 질문으로 진행
   - all_passed=false → followup_question 을 Redis Queue 맨 앞에 끼워넣어 다음 차례로 제시
   - capped=true 인 경우는 "rubric을 다 통과해서"가 아니라 "횟수 상한이라 강제 종료"이므로
     리포트 등에서 구분해서 다뤄야 함
   - (질문/꼬리질문과 무관하게) 답변을 저장한 직후, 아래 1.2.3 을 비동기로 트리거
```

```
   │  백그라운드 작업에서 비동기 호출 (동기 응답을 기다리지 않음)

   │  { user_id, ai_interview_id, question, rubric: [...],

   │  ※ rubric_results 는 1.2.2 에서 이미 채점했다면 그 결과를 그대로 실어 보낸다(선택).

   │  - services.answer_service.generate_answer_supplement() 에 위임
   ▼

   │     - "지원자 답변을 존중하며 자연스럽게 보완, 새 답변을 지어내지 말 것" 지시
   │  4) gms_client.chat_json(ANSWER_SUPPLEMENT_SYSTEM, prompt) 로 GMS LLM 호출
   │  5) ai_answer 파싱. 비어있으면 사용자 원문 답변으로 폴백(화면 깨짐 방지)
   ▼
[routers/interview.py] → AnswerSupplementResponse 반환
   │  { ai_interview_id, question, ai_answer }
   ▼
[BE: Spring Boot]
   - ai_interview_questions.ai_answer 컬럼에 저장
   - 면접 최종 완료 화면에서 (질문, 사용자 답변, ai_answer) 목록 + 전반적 분석/피드백과
     함께 노출 ("전반적 분석/피드백" 생성 자체는 별도 미구현 엔드포인트, 2절 참고)
```

### 1.3 수정한 파일 상세 설명

**`ai/config.py`**
- `question_count: int = 10` → `5` 로 변경.
- `rubric_min_count: int = 2`, `rubric_max_count: int = 3` 신규 추가.
- `max_followup_per_question: int = 2` (기존 값, 그대로 유지).
  - **[Phase 2에서 역할 변경]** 기존에는 "종료 판단의 주 기준"이었지만, 이제는
    rubric이 계속 통과되지 못할 때의 **안전장치용 상한**으로 역할이 바뀌었다.

**`ai/schemas/interview.py`**

Phase 1
- `GeneratedQuestion` 에 `rubric: list[str]` 필드 추가.
- `GeneratedQuestion.expected_answer` **필드 제거** (답변 보완 재설계).
  기존에는 `ai_interview_questions.ai_answer` 컬럼에 매핑되는 "사전 예상 답안"이었지만,
  이제 그 컬럼은 답변 제출 후 비동기로 생성되는 값이므로 질문 생성 응답에 담을 값이 없다.
- `QuestionGenerateRequest.question_count` 설명 문구를 "기본값 10" → "기본값 5"로 수정.

Phase 2 (Breaking Change)
- `RubricResult` 모델 신규 추가: `criterion`(str), `passed`(bool | None — None은
  capped로 인해 채점 자체를 생략한 경우), `reason`(str | None, 판정 근거).
- `FollowupRequest`: `rubric: list[str]` 추가, `followup_depth`는 안전장치 상한 체크
  전용으로 의미 축소(필드는 유지).
- `FollowupResponse` (기존 `need_followup`/`question`/`reason` 제거):
  `rubric_results`, `all_passed`, `followup_question`(이름 변경), `capped` 추가.
- `FollowupResponse.expected_answer` **필드 제거** (답변 보완 재설계) — 꼬리질문
  생성 시점에도 더 이상 사전 예상 답안을 만들지 않는다.

답변 보완 재설계 (신규)
- `AnswerSupplementRequest` 신규: `user_id`, `ai_interview_id`, `question`,
  `rubric`(참고용), `rubric_results`(Phase 2 결과 재사용, optional), `user_answer`,
  `interview_type`.
- `AnswerSupplementResponse` 신규: `ai_interview_id`, `question`,
  `ai_answer`(`ai_interview_questions.ai_answer` 저장용).

**`ai/prompts/templates.py`**

Phase 1
- `QUESTION_SYSTEM`: "채점 기준 설계자" 역할 문구 추가.
- `build_question_prompt()`: `rubric_min_count`/`rubric_max_count` 파라미터 추가,
  rubric 작성 지시문/JSON 예시 추가, **"expected_answer는 생성하지 말라"는 지시 추가**
  (답변 보완 재설계).

Phase 2
- `FOLLOWUP_SYSTEM`: "판단자" → "채점관 + 채점 결과에 근거한 질문 설계자" 역할로 문구 갱신.
- `build_followup_prompt()`: `remaining` 제거, `rubric` 추가, "통과 못한 항목 중 1개만
  겨냥"하도록 지시, JSON 출력에서 **`expected_answer` 제거**(답변 보완 재설계).

답변 보완 재설계 (신규)
- `ANSWER_SUPPLEMENT_SYSTEM`, `build_answer_supplement_prompt()` 신규 작성:
  - rubric_results(이미 채점된 결과)가 있으면 통과/미통과 여부를 그대로 프롬프트에
    노출해 "무엇을 놓쳤는지" 재계산 없이 알려준다.
  - "지원자 답변을 존중하며 미충족 부분만 자연스럽게 보강, 새 경험을 지어내지 말 것"을
    핵심 지시로 명시 — "새 모범 답안 생성"이 아니라 "답변 보완"이라는 성격을 지키기 위함.

**`ai/services/question_service.py`** (Phase 1 + 답변 보완 재설계)
- `build_question_prompt()` 호출 시 rubric 개수 인자 전달, rubric 필드 정규화/로깅.
- `GeneratedQuestion` 생성 시 `expected_answer` 파싱 코드 제거 — LLM이 옛 습관으로
  여전히 `expected_answer`를 보내더라도 무시한다.

**`ai/services/followup_service.py`** (Phase 2 — 전면 교체 + 답변 보완 재설계)
- "횟수 초과 시 종료"를 "안전장치(capped)"로 재정의.
- rubric 채점 기반 프롬프트로 교체, `rubric_results` 파싱/검증, `all_passed` 서버
  재계산, 교착 상태 방어(`followup_question` 누락 시 `all_passed=true`로 강제 전환).
- `FollowupResponse` 생성 시 `expected_answer` 인자 제거(필드 자체가 스키마에서 사라짐).

**`ai/services/answer_service.py`** (신규 — 답변 보완 재설계)
- `generate_answer_supplement()`:
  1. 질문+답변으로 RAG 재검색(top_k=3).
  2. `req.rubric_results`(Phase 2 채점 결과, optional)를 dict로 변환해 프롬프트에 전달.
  3. `build_answer_supplement_prompt()` + `gms_client.chat_json()` 호출
     (temperature=0.6 — 사실 보완 성격이 강해 다른 서비스보다 낮게 설정).
  4. `ai_answer`가 빈 문자열로 오면(LLM 형식 오류 등) 사용자 원문 답변을 그대로
     폴백으로 사용 — 최종 화면에 빈 값이 노출되는 것을 방지.

**`ai/routers/interview.py`**
- `create_questions()`, `create_followup()` docstring을 최신 스키마 기준으로 갱신
  (더 이상 "Phase 2는 범위 아님" 같은 stale 문구 없음).
- `create_answer_supplement()` 신규: `POST /answers/supplement` 엔드포인트,
  BE가 답변 저장 직후 비동기로 호출한다는 전제와 `rubric_results` 재사용 방식을
  docstring에 명시.

### 1.4 BE와 반드시 맞춰야 할 사항 (Breaking Change)

1. **`/followup` 요청**: `rubric: list[str]`을 반드시 함께 보내야 한다(없으면 422).
2. **`/followup` 응답**: `need_followup`/`question`/`reason`/`expected_answer`가 사라지고
   `all_passed`/`followup_question`/`rubric_results`/`capped`로 대체되었다.
   BE의 분기 로직도 `if not response.all_passed: ...` 형태로 함께 수정해야 한다.
3. **`/questions` 응답**: `expected_answer` 필드가 더 이상 내려오지 않는다. BE가
   기존에 이 값을 `ai_interview_questions.ai_answer`에 즉시 저장하고 있었다면,
   그 로직을 제거하고 대신 답변 제출 후 `/answers/supplement` 호출 결과로 채우도록
   바꿔야 한다.
4. **신규 연동 필요**: 사용자가 답변을 제출/저장한 직후, `POST
   /api/v1/interviews/answers/supplement`를 (기본 질문/꼬리질문 구분 없이) 비동기로
   호출하는 백그라운드 트리거를 BE에 추가해야 한다. 이 호출 없이는 `ai_answer`가
   영구히 비어있게 된다.
5. **capped 처리**: `capped=true`인 응답은 리포트/통계에서 "완전히 통과한 질문"과
   구분해서 다루는 것을 권장한다.
6. *(3절에서 추가됨)* **`/questions` 요청**: `cs_category`(CS 면접 시 필수), `career`,
   `skills` 필드가 추가되었다. 자세한 내용은 [3.3절](#33-영향받는-api-계약-be-연동-필요) 참고.

### 1.5 건드리지 않은 파일 (Phase 1/2 작업 시점 기준, 의도적으로 제외)

- `services/embedding_service.py`, `services/rag_service.py`,
  `services/cs_embedding_service.py`, `db/chroma.py`
  → 이 아키텍처 변경과 무관하며, 지시사항에서도 명시적으로 제외 대상으로 지정됨.
  (단, 이후 [3절](#3-cs-카테고리-제한--면접-유형별-문서-참고-비율-기능) 작업에서
  `rag_service.py`는 별도 요청으로 수정했다.)
- "면접 전체 총평/피드백" 생성용 리포트 엔드포인트(신규 예정)
  → 아직 착수하지 않음. 자세한 내용은 [2절](#2-잔여-작업--면접-총평피드백-리포트-미착수) 참고.

### 1.6 검증

- 변경/신규 7개 파일(`config.py`, `schemas/interview.py`, `prompts/templates.py`,
  `services/question_service.py`, `services/followup_service.py`,
  `services/answer_service.py`, `routers/interview.py`) 모두 `python -m py_compile`
  로 문법 오류 없음을 확인.
- `ai/README.md`의 API 문서(2~5절)를 새 스키마/엔드포인트 기준으로 갱신.
- 실제 GMS LLM 호출을 통한 통합 테스트는 수행하지 않음(별도 `.env`의 GMS 키 필요).
  BE/QA 단계에서 다음을 확인해야 한다:
  - `/api/v1/interviews/questions` 응답에 `expected_answer`가 더 이상 없고,
    `questions[].rubric`이 2~3개의 문자열 배열로 채워지는지.
  - `/api/v1/interviews/followup` 응답의 `rubric_results` 개수가 요청 `rubric`
    개수와 일치하는지, `all_passed=false`일 때 `followup_question`이 항상
    채워지는지, `followup_depth`가 상한에 도달했을 때 `capped=true`로 종료되는지.
  - `/api/v1/interviews/answers/supplement` 호출 시 `ai_answer`가 항상 비어있지
    않은 문자열로 채워지는지(폴백 동작 포함), `rubric_results`를 넘겼을 때와
    안 넘겼을 때 응답 품질 차이를 확인.

## 2. 잔여 작업 — 면접 총평/피드백 리포트 (미착수)

> 1절에서 완료한 작업(Phase 1, Phase 2, 답변 보완 재설계)을 제외한, **아직 진행하지 않은
> "면접 전체 총평/피드백" 리포트 엔드포인트의 범위와 예상 작업**을 정리한 것이다.
> 실제 코드는 포함되어 있지 않다.

### 2.1 전체 진행률

| 항목 | 내용 | 상태 |
|---|---|---|
| Phase 1 | 질문 5개 + 질문당 루브릭(채점 기준) 2~3개 생성 | ✅ 완료 |
| Phase 2 | 실시간 채점(rubric pass/fail) + 동적 꼬리질문 One-Call 생성 | ✅ 완료 |
| 답변 보완 재설계 | expected_answer 폐기, 답변 제출 후 비동기 ai_answer 생성 | ✅ 완료 |
| CS 카테고리 제한 / 문서 참고 비율 | 3절 참고 | ✅ 완료 |
| 면접 총평/피드백 리포트 | 면접 종료 후 전체 대화를 아우르는 총평/피드백 생성 | ⬜ 미착수 |

**중요한 설계 변경**: 원래 계획된 "Phase 3(모범 답안 생성)"은 이번 작업에서
[1절의 "답변 보완" 재설계](#1-루브릭-기반-동적-꼬리질문-아키텍처-전환-phase-1--phase-2--답변-보완-재설계)로
흡수되어 이미 구현되었다 (사용자가 답변을 제출할 때마다 비동기로 `ai_answer`를 생성하는
방식으로, 면접 종료 후 일괄 처리하지 않는다). 따라서 지금 남은 것은 "질문별 모범 답안"이
아니라, **면접 전체를 관통하는 총평/피드백**(예: "전반적으로 근거 제시가 약했습니다",
"CS 기초는 탄탄하나 트러블슈팅 경험 서술이 부족했습니다" 같은 요약형 피드백)이다.

### 2.2 면접 총평/피드백 리포트 (미착수)

#### 2.2.1 목표
면접 종료 후 호출되는 엔드포인트(동기/비동기 여부는 2.2.3 참고). 전체 대화 기록
(질문, 사용자 답변, rubric 채점 결과, `ai_answer` — 이미 답변 보완 단계에서 모두
생성되어 있음)을 입력받아, **면접 전체에 대한 총평과 개선 방향 피드백**을 생성한다.
질문별 `ai_answer`는 이미 완료되었으므로, 이 단계는 "개별 답변 교정"이 아니라
"전체 경향 분석"에 집중한다.

#### 2.2.2 예상 수정/신규 대상

- **`schemas/interview.py`** (신규 스키마 추가)
  - 입력: `ai_interview_id`, `qa_history: list[...]` — 질문/사용자답변/rubric_results/
    ai_answer 를 이미 포함한 전체 대화 기록. (답변 보완 단계에서 이미 만든 데이터를
    BE가 취합해 넘겨주는 것을 전제로 함 — AI 서비스가 Redis/MySQL 을 직접 조회하지
    않는다는 기존 원칙 유지.)
  - 출력: `overall_feedback`(총평 텍스트), `strengths`(잘한 점), `weaknesses`(부족한 점),
    `improvement_suggestions`(개선 방향) 등 — 정확한 필드 구성은 FE 화면 설계와
    맞춰 확정 필요.

- **`prompts/templates.py`** (신규 프롬프트 추가)
  - "질문별 rubric 채점 결과(몇 개 중 몇 개를 놓쳤는지)를 종합해 지원자의 전반적인
    경향을 파악하고, 구체적이고 실행 가능한 개선 방향을 제시하라"는 지시.
  - 특정 질문 하나가 아니라 면접 전체 패턴(예: "특정 주제에서 반복적으로 약함",
    "질문 초반보다 후반에 답변 품질이 떨어짐")을 짚어내도록 유도하는 것이 이
    프롬프트의 핵심 가치.

- **`services/report_service.py`** (신규 파일)
  - 전체 대화 기록을 받아 프롬프트 구성 → GMS 호출 → 파싱.
  - 기존 서비스들의 GMS 호출 패턴(`chat_json`, tenacity 재시도, 코드펜스 방어 파서)
    그대로 재사용.
  - 질문별 `ai_answer`는 이미 완료된 데이터를 그대로 전달만 하면 되므로, 이 서비스가
    다시 생성할 필요는 없음(단순 통과/요약용 컨텍스트로만 사용).

- **`routers/interview.py`**
  - `POST /api/v1/interviews/report` (예시 이름) 신규 엔드포인트 추가.

#### 2.2.3 설계상 고려/논의 필요 사항
- **동기/비동기 처리 방식**: 개별 답변 보완처럼 완전 비동기로 뒤에서 처리할지,
  "면접 완료" 버튼을 누른 시점에 사용자가 짧게 기다리는 동기 호출로 처리할지
  미정. 이미 질문별 `ai_answer`는 답변마다 비동기로 준비되어 있으므로, 이 리포트
  자체는 "총평 텍스트 하나"만 생성하면 되어 지연시간이 상대적으로 짧을 수 있다
  (LLM 호출 1회, 짧은 출력) — 동기 처리도 현실적인 선택지.
- **`capped=true`로 강제 종료된 질문 처리**: Phase 2에서 횟수 상한으로 강제
  종료된 질문(rubric을 다 채점하지 못함)을 총평에서 "이 부분은 판단이 어려웠음"
  으로 명시할지, 그냥 넘어갈지 정책 확정 필요.
- **총평의 톤/형식**: 정량적 점수(예: 5점 만점)를 함께 낼지, 정성적 서술로만
  구성할지는 FE 화면 설계와 맞물려 있어 기획/FE와 논의 필요.

### 2.3 완료된 작업 관련 잔여 확인 사항 (코드는 완료, 검증 미완료)

Phase 1, Phase 2, 답변 보완 재설계 모두 코드 구현은 완료됐지만, 다음은 아직
확인되지 않았다:

1. **BE 연동**: `/followup`, `/answers/supplement` 는 모두 신규이거나 스키마가
   바뀐 엔드포인트이므로([1.4절](#14-be와-반드시-맞춰야-할-사항-breaking-change)),
   BE 팀이 이 변경 사항을 반영해야 실제 동작이 가능하다. 특히 `/answers/supplement`를
   "답변 저장 직후 비동기 호출"하는 트리거 자체가 BE에 아직 없다면 `ai_answer`가
   영구히 비게 된다.
2. **실제 GMS LLM 응답 품질 검증**: `.env`의 GMS 키로 실제 호출해봐야 다음을
   확인 가능하다:
   - rubric 채점 프롬프트가 안정적인 JSON을 반환하는지, `rubric_results` 개수가
     입력과 항상 일치하는지.
   - 답변 보완 프롬프트가 "새 답변을 지어내지 않고 원문을 보완"하라는 지시를
     실제로 잘 따르는지(과도하게 다시 쓰거나, 사실을 지어내는 경우가 없는지).
3. **`max_followup_per_question` 값 재검토**: 실제 사용해보면서 2회가 적절한
   상한인지 BE/기획과 논의가 필요할 수 있다.
4. **`answer_service.py`의 RAG 재검색 비용**: 답변마다(기본 질문 + 모든 꼬리질문)
   RAG 검색을 1회씩 수행하므로, 질문당 최대 3회(기본 답변 + 꼬리질문 최대 2회)의
   추가 검색이 발생한다. 실사용 트래픽에서 Chroma 조회 비용이 문제가 되는지
   모니터링 필요.

## 3. CS 카테고리 제한 + 면접 유형별 문서 참고 비율 기능

> 관련 요청: "CS 면접은 사용자가 고른 CS 카테고리 내에서만 질문 생성 + 경력/스킬 반영",
> "면접 유형별로 이력서/자소서/GitHub 참고 비율을 다르게, 추후 쉽게 수정 가능하게"

### 3.1 배경

1절에서 완료한 질문/꼬리질문/답변보완 아키텍처는 그대로 두고, `/api/v1/interviews/questions`
(질문 생성)의 **RAG 검색 범위와 개인 문서 참고 비율**을 개선했다. 기존에는:
- CS 면접이어도 사용자가 고른 세부 카테고리를 전혀 받지 않고, CS 지식 전체 컬렉션에서
  검색해 질문을 만들었다.
- 개인 문서(이력서/자소서/GitHub)는 면접 유형과 무관하게 유사도 top_k(기본 5개)로만
  뽑혔고, "이력서를 몇 % 참고할지" 같은 비율 개념 자체가 없었다.
- 사용자 경력/보유 스킬은 요청 스키마에 아예 없었다.

이번 작업으로 위 세 가지를 모두 반영했다.

### 3.2 변경 사항 요약

#### 3.2.1 CS 카테고리 제한 (신규)

- `schemas/common.py`
  - `CSCategory` enum 9종 추가: 자료구조/알고리즘, 운영체제, 네트워크, WEB, 데이터베이스,
    보안, 소프트웨어 공학, AI, 언어 및 프레임워크.
  - `CS_CATEGORY_LABEL` dict: enum → 한국어 라벨 (프롬프트 노출용).
- `schemas/interview.py`
  - `QuestionGenerateRequest`에 `cs_category: CSCategory | None`, `career: str | None`,
    `skills: list[str] | None` 필드 추가.
  - `model_validator`로 `interview_type == CS`인데 `cs_category`가 없으면 422로 거부.
- `services/rag_service.py`
  - `CS_CATEGORY_RAW_MAP`: `CSCategory` → `data/cs_knowledge.json`에 실제로 들어있는
    원본 category 문자열(gyoogle 폴더 구조) 매핑 표.
  - `retrieve_cs_knowledge(query, cs_category, top_k)`: category `$in` 필터를 하드 필터로
    걸어 "선택한 카테고리 밖의 CS 지식은 절대 검색되지 않음"을 보장.
  - `retrieve_cs_knowledge_random(cs_category, top_k)`: 유사도 검색이 아니라 카테고리
    내부에서 무작위로 뽑는 함수(신규). "개인 문서가 카테고리와 무관하면 카테고리
    안에서 랜덤으로 질문을 만들어도 된다"는 요구사항 구현.
  - `_has_no_seed_data()`: 매핑된 원본 category가 하나도 없는 카테고리(예: SECURITY)를
    Chroma 호출 전에 미리 걸러, 빈 `$in` 필터로 인한 예외/오해성 로그를 방지.
- `services/question_service.py`
  - CS 면접 전용 분기(`generate_questions`) 추가:
    1. `_build_cs_query()`로 "선택한 카테고리 라벨 + 직무/스킬" 쿼리 생성.
    2. 그 쿼리로 개인 문서(RAG)를 검색하고, 최상위 결과의 코사인 거리가
       `settings.cs_relevance_distance_threshold`(기본 0.45)보다 크면(=유사도 낮음)
       "개인 문서가 이 카테고리와 무관"하다고 판단해 버린다.
    3. 관련 있으면: 개인 문서 + `retrieve_cs_knowledge(cs_category=...)` 조합.
       관련 없으면: 개인 문서 제외 + `retrieve_cs_knowledge_random(cs_category)`.
- `prompts/templates.py`
  - `build_question_prompt()`에 `cs_category` 파라미터 추가 → "## CS 카테고리 (반드시 이
    범위 내에서만 질문)" 섹션을 프롬프트에 명시적으로 삽입. RAG 컨텍스트가 비어 있어도
    (예: 시드 데이터 없는 카테고리) LLM이 카테고리를 벗어나지 않도록 하는 이중 안전장치.
- `config.py`
  - `cs_relevance_distance_threshold: float = 0.45` 추가.

**⚠️ 데이터 갭 (팀 확인 필요)**: 현재 CS 지식 시드 데이터(`data/cs_knowledge.json`)에는
"보안" 관련 카테고리가 전혀 없다. 사용자가 "보안"을 고르면 CS 지식 검색은 항상 0건이며,
질문 생성은 전적으로 LLM의 일반 지식(+ 프롬프트의 "문서 부족 시 일반 질문으로 채우기"
지시)에 의존한다. 추후 보안 카테고리 시드 데이터 보강이 필요하다.
또한 "컴퓨터 구조"는 별도 카테고리가 없어 임의로 "운영체제"에 포함시켰고,
"언어 및 프레임워크" 카테고리에는 `Web > React/Spring/Vue/DevOps`(프레임워크 구체 지식)를,
"WEB" 카테고리에는 범용 `Web`(HTTP/REST 등)만 배정했다 — 정확한 매핑 근거는
`services/rag_service.py`의 `CS_CATEGORY_RAW_MAP` 주석 참고.

#### 3.2.2 경력/보유 스킬 반영 (신규)

- `QuestionGenerateRequest.career`, `.skills` — RAG 검색 쿼리(`_build_rag_query`,
  `_build_cs_query`)와 프롬프트 "지원 정보" 섹션 양쪽에 반영.

#### 3.2.3 면접 유형별 문서 참고 비율 (신규)

- `services/rag_service.py`의 `DOC_TYPE_WEIGHTS` 표 하나로 관리 (100 기준 %):

  | 면접 유형 | 이력서 | 자소서 | GitHub |
  |---|---|---|---|
  | 직무(JOB) | 50 | 40 | 10 |
  | CS | 10 | 40 | 50 |
  | 기술(TECH) | 10 | 40 | 50 |
  | 포트폴리오(PORTFOLIO) | 10 | 30 | 60 |
  | 종합(COMPREHENSIVE) | 고정 비율 없음 (질문 특성/유사도에 맡김) |

  **비율 수정 방법**: `services/rag_service.py` 상단 `DOC_TYPE_WEIGHTS` 딕셔너리의 숫자만
  바꾸면 즉시 반영된다. 다른 코드는 건드릴 필요 없음.

- 구현 방식: `retrieve_context()`가 전체 `top_k`를 `_allocate_top_k()`(최대 나머지법,
  largest remainder method)로 doc_type별 정수 개수로 쪼갠 뒤, doc_type별로 **개별
  Chroma 쿼리**를 날려 합친다. 단순히 doc_type 필터만 걸고 top_k개를 통으로 뽑으면
  Chroma가 유사도 순으로만 채워서 비율이 보장되지 않기 때문에, doc_type마다 쿼리를
  분리하는 방식을 택했다.
- `top_k`가 작으면(예: `followup_service.py`/`answer_service.py`가 쓰는 `top_k=3`) 비율이
  낮은 doc_type은 배분이 0개가 될 수 있다 — 비율을 그대로 반영한 정상 동작이며,
  최소 1개를 강제로 보장하지 않는다.
- `retrieve_context()`는 질문 생성뿐 아니라 꼬리질문 채점(`followup_service.py`), 답변
  보완(`answer_service.py`)에서도 공용으로 쓰이므로, 이 비율 적용은 세 흐름 모두에
  일관되게 적용된다.

### 3.3 영향받는 API 계약 (BE 연동 필요)

`QuestionGenerateRequest`(요청 바디)에 필드 3개가 추가/필수화됨:

```jsonc
{
  "user_id": 1,
  "ai_interview_id": 10,
  "interview_type": "cs",          // "cs"면 cs_category 필수
  "cs_category": "database",        // 신규 — 9종 중 하나 (schemas/common.py CSCategory 참고)
  "career": "3년차",                // 신규 — 선택
  "skills": ["Java", "Spring", "MySQL"]  // 신규 — 선택
}
```

- `cs_category` 문자열 값은 `schemas/common.py`의 `CSCategory` enum 값과 정확히 일치해야
  한다: `data_structure_algorithm`, `operating_system`, `network`, `web`, `database`,
  `security`, `software_engineering`, `ai`, `language_framework`.
- BE 팀과 이 9개 문자열 스펙을 반드시 동기화할 것 (아직 ERD/BE 코드에 반영 전).

### 3.4 검증 방법

의존성(chromadb/pydantic)을 임시 venv에 설치하고, 실제 `SentenceTransformer` 모델 로딩
없이 결정론적 fake 임베딩 함수로 `db.chroma._get_embedding_function`을 모킹해 다음을
확인했다 (실제 서버 기동 없이 로직만 단위 검증한 것이며, 실제 한국어 임베딩 모델의
의미적 정확도까지 검증한 것은 아님):

- CS 면접인데 `cs_category` 누락 시 pydantic 422 검증 에러 발생.
- `_allocate_top_k()`가 모든 케이스(top_k=0/3/5/10)에서 합계를 정확히 지킴.
- JOB/CS/PORTFOLIO 각 비율대로 doc_type별 쿼리가 실제로 분리되어 나감.
- `CSCategory.SECURITY`(시드 데이터 없음)를 선택해도 예외 없이 빈 리스트를 반환하고
  프롬프트에는 "보안" 섹션이 정상적으로 노출됨.
- `question_service.generate_questions()` 전체 흐름(GMS 호출은 모킹)이 CS/JOB 각
  케이스에서 예외 없이 완료됨.

### 3.5 남은 작업 / 팀 확인 필요 사항

- CS 지식 시드 데이터에 "보안" 카테고리 보강 필요.
- `CS_CATEGORY_RAW_MAP`의 "컴퓨터 구조→운영체제", "프레임워크 구체 지식→언어 및
  프레임워크" 매핑은 임의 판단이므로 팀 리뷰 필요.
- `cs_relevance_distance_threshold`(0.45)는 실제 운영 데이터로 튜닝 필요 (현재는
  경험적 기본값).
- BE와 `cs_category`/`career`/`skills` 필드 스펙(타입, 값) 동기화 필요.
