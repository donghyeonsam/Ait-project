## 1. 작업 배경

답변 분석/보완/평가는 Spring Boot(BE)에서 처리하는 것으로 결정됐다. `docs/AI_작업일지_0722.md`
1절에서 설계했던 "사용자가 답변을 제출할 때마다 FastAPI가 비동기로 `ai_answer`를
보완 생성한다"는 아키텍처는 이번 결정으로 폐기됐다 — `POST /api/v1/interviews/answers/supplement`
엔드포인트는 BE 어디에서도 호출되지 않는 죽은 코드였고, 이 죽은 코드를 완전히 제거하는
것이 1절 작업의 목표다.

2절 작업(문서 단위 임베딩 삭제 API)은 별개의 요구사항이다. 사용자가 자기소개서나
GitHub 레포를 삭제해도 Chroma에 임베딩이 남아 면접 질문 생성 시 계속 검색 대상으로
잡히는 문제를 해결하기 위해 신설했다.

## 3. 문서 단위 임베딩 삭제 API 신설

### 3.1 배경

기존에 노출된 삭제 API는 `DELETE /api/v1/embeddings/{user_id}`(사용자 전체 삭제,
회원 탈퇴용) 하나뿐이었다. 사용자가 자기소개서 1건이나 GitHub 레포 1건만 삭제해도
Chroma에는 그 문서의 임베딩이 그대로 남아, 이후 면접 질문 생성 시 RAG 검색 대상으로
계속 잡히는 문제가 있었다.

문서 단위 삭제 로직 자체(`services/embedding_service.py`의
`delete_document_embedding(user_id, doc_type, target_id)`)는 이미 존재했다 — 문서
재임베딩 시(`embed_user_documents`의 `replace=True` 경로) 내부적으로 쓰이고 있어
검증된 코드였다. 이번 작업은 이 함수를 라우터로 노출하기만 하면 되는 작업이었다.

### 3.2 엔드포인트: `POST /api/v1/embeddings/delete`

`DELETE`가 아니라 `POST`를 선택한 이유 세 가지(코드 주석에도 남김):

1. Spring `RestClient`의 `.delete()`는 `RequestHeadersSpec`을 반환해 요청 바디를
   실을 수 없다 — 삭제 대상을 배열로 지정해야 하는 이 API는 바디가 필수라 `DELETE`로
   표현할 수 없었다.
2. `DELETE` 메서드에 바디를 실어도 중간 프록시(nginx 등)가 이를 버리는 경우가 있어
   배포 환경에 따라 깨질 수 있다.
3. 기존 `POST /api/v1/embeddings`(임베딩 저장)와 요청 형태(`items` 배열)를 대칭으로
   맞출 수 있어, 저장/삭제 두 API를 같은 패턴으로 이해할 수 있다.

### 3.3 스키마 설계

`schemas/embedding.py`에 `DeleteDocumentItem`(`doc_type: DocType`, `target_id: int`)와
`DeleteDocumentsRequest`(`user_id: int`, `items: list[DeleteDocumentItem]`,
`min_length=1`)를 추가했다. `doc_type`은 기존 `schemas/common.py`의 `DocType` enum을
그대로 재사용하며 `resume`을 서버에서 막지 않는다 — 현재 BE에 이력서 삭제 기능이
없어 실제로 호출될 일은 없지만(4절 참고), "어떤 문서를 지울지"는 호출측(BE)의 결정
영역이므로 AI 서비스가 임의로 제약을 걸 이유가 없다고 판단했다.

응답 `DeleteDocumentsResponse`는 `user_id`, `requested_count`(요청한 `items` 개수),
`deleted: bool`(항상 `True`, 멱등), `message` 네 필드로 구성했다.
`requested_count`가 **실제로 삭제된 청크 수가 아니라 요청 개수**인 이유는, Chroma의
`collection.delete(where=...)`가 삭제 건수를 반환하지 않기 때문이다 — 반환값이 없는
값을 억지로 추정해서 응답에 담기보다는, 기존 `DeleteEmbeddingResponse`가
`deleted: bool` 하나만 주는 컨벤션을 그대로 따르는 편이 정직하다고 판단했다.

### 3.4 서비스 로직: 왜 루프 방식을 택했는가

`services/embedding_service.py`에 `delete_document_embeddings(req)`를 추가했다.
내부는 기존 `delete_document_embedding()`을 `items` 개수만큼 순차 호출하는 단순
루프다.

Chroma `where` 절을 `$or`로 묶어 여러 문서를 한 번의 `collection.delete()` 호출로
처리하는 최적화도 검토했지만 채택하지 않았다. 이유는 이 프로젝트가 사용하는
chromadb 0.5.5 버전에서 `$or` 절 안에 `$and` 절이 중첩 가능한지(지금 삭제 조건은
`{"$and": [{"user_id": ...}, {"doc_type": ...}, {"target_id": ...}]}` 형태라, 여러
문서를 묶으려면 `$or` 안에 이 `$and` 블록 여러 개가 들어가야 한다) 검증되지
않았기 때문이다. 반면 루프 방식은 `embed_user_documents()`가 문서별 재임베딩 시
이미 쓰고 있는, 실제로 검증된 패턴이다. 삭제는 자주 발생하지 않는 경로(문서 삭제
시에만 1회)라 성능 이득보다 검증되지 않은 쿼리 문법으로 인한 장애 리스크가 더
크다고 판단했다.

### 3.5 라우터

`routers/embedding.py`에 `delete_document_embeddings_route()`를 추가했다. 기존
`delete_embeddings()`(`DELETE /{user_id}`)는 그대로 유지되며 계속 회원 탈퇴용으로
쓰인다. 에러 처리는 기존 `delete_embeddings()`와 동일한 try/except +
`HTTPException(500)` 패턴을 따랐고, 삭제 대상이 없는 `item`이 섞여 있어도(이미
삭제된 문서를 재요청하는 경우 등) 실패로 취급하지 않는다 — `delete_document_embedding()`
자체가 대상이 없어도 예외 없이 조용히 종료되는 멱등 함수이므로, 그 성질이 새
엔드포인트에도 그대로 이어진다.

## 4. BE 연동 안내

자소서 삭제 또는 GitHub 레포 삭제 시, BE는 해당 삭제 트랜잭션 처리 과정에서
`POST /api/v1/embeddings/delete`를 호출해야 한다. **이 호출은 try-catch + 로그로
처리하고, 실패하더라도 삭제 트랜잭션 자체를 롤백시키면 안 된다** — 임베딩 정리는
"검색 정확도를 위한 부가 정리 작업"이지 삭제 트랜잭션의 필수 조건이 아니기 때문이다.
AI 서비스 호출이 실패했다고 자소서/레포 삭제 자체가 실패하는 것은 사용자 입장에서
과도한 실패이며, 유령 임베딩이 잠시 남는 것은 재시도/배치 정리로 복구 가능한 문제다.

이력서는 이 API의 호출 대상이 아니다 — 현재 BE에 이력서 삭제 기능 자체가 없다.

- `ai/` 전체(`.py` 파일 한정, 과거 작업일지 제외)에서 `supplement`/`Supplement`/`SUPPLEMENT`
  grep — `services/rag_service.py`의 의도적으로 남긴 공유 함수 docstring 3곳
  외에는 잔여 참조 없음을 확인(2.3절 참고).
- 실제 GMS LLM 호출/Chroma 연동을 통한 통합 테스트는 수행하지 않았다(`.env`의
  GMS 키와 실제 chromadb/sentence-transformers 설치가 필요). BE/QA 단계에서 다음을
  확인해야 한다:
  1. `docker compose up --build` 후 `/docs`(Swagger)에서 `/answers/supplement`가
     더 이상 노출되지 않고, `POST /api/v1/embeddings/delete`가 정상 노출되는지.
  2. 자소서/GitHub 레포 삭제 흐름에서 `POST /api/v1/embeddings/delete` 호출 후,
     해당 문서가 실제로 면접 질문 생성 RAG 검색 결과에서 더 이상 나오지 않는지.
  3. `POST /api/v1/embeddings/delete`에 존재하지 않는 `target_id`를 섞어 보내도
     500이 아니라 정상 응답(`deleted: true`)이 오는지(멱등성).
