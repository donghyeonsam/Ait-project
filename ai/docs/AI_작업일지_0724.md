## 1. `followup_depth` → `depth` 필드명 통일 (Breaking Change)

> 대상: `POST /api/v1/interviews/followup` 요청/응답 필드명 통일

### 1.1 작업 배경

BE(Spring Boot)가 AI 서비스 응답을 Jackson으로 역직렬화할 때, 다단어 snake_case
필드(`followup_depth`)에 대해 camelCase 변환 어노테이션(`@JsonProperty` 등)이
누락되면 해당 필드가 **조용히 null**로 매핑되는 문제가 반복적으로 발생했다. 필드가
존재하는데도 값이 비어있어 원인 파악에 시간이 걸리는 유형의 버그다.

`schemas/interview.py`의 `GeneratedQuestion.depth`(질문 생성 응답의 초기 꼬리질문
횟수, 항상 0)는 이미 같은 이유로 한 단어 필드명 `depth`를 쓰고 있었다. 이번 작업은
`FollowupRequest`/`FollowupResponse`의 `followup_depth`도 `depth`로 통일해:

1. 한 단어 필드명은 애초에 snake_case ↔ camelCase 변환 자체가 필요 없어 이 문제를
   원천 차단하고,
2. "이 질문/꼬리질문에 나간 꼬리질문 횟수"라는 동일한 개념을 가리키는 필드명을
   스키마 전체에서 하나로 통일한다.

### 1.2 변경 사항

#### `schemas/interview.py`

- `FollowupRequest.followup_depth` → `depth` (타입/기본값/`ge=0` 제약 동일, 설명 문구
  동일). 필드 바로 위에 이번 rename의 배경(Breaking Change임, `GeneratedQuestion.depth`와
  이름 통일, Jackson 역직렬화 null 문제 차단)을 설명하는 주석을 추가했다.
- `FollowupResponse.followup_depth` → `depth` (타입/설명 동일).
- **`GeneratedQuestion.depth`는 이번 변경 대상이 아니다** — 이미 `depth`라는 이름을
  쓰고 있었으므로 그대로 두었다.

#### `services/followup_service.py`

`req.followup_depth` 참조, `followup_depth=` 키워드 인자를 전부 `req.depth`,
`depth=`로 교체했다:

- 상한 체크: `if req.followup_depth >= max_depth` → `if req.depth >= max_depth`.
- capped 로그/응답: 로그의 `req.followup_depth` → `req.depth`,
  `FollowupResponse(..., followup_depth=req.followup_depth, ...)` →
  `FollowupResponse(..., depth=req.depth, ...)`.
- `new_depth` 계산: `req.followup_depth + 1 if ... else req.followup_depth` →
  `req.depth + 1 if ... else req.depth` (지역 변수명 `new_depth`/`max_depth` 자체는
  필드가 아니라 지역 변수라 변경하지 않았다).
- 최종 로그/응답: 로그의 `req.followup_depth` → `req.depth`,
  `FollowupResponse(..., followup_depth=new_depth, ...)` →
  `FollowupResponse(..., depth=new_depth, ...)`.
- 모듈 docstring 중 "followup_depth 카운터로만 종료를 제어했다",
  "followup_depth 는 '안전장치용 상한 체크' 용도로만"의 텍스트도 `depth`로 통일해
  코드와 설명이 어긋나지 않게 했다(기능 변경 없음).

#### `README.md`

"3. 꼬리질문" API 섹션의 요청 예시 JSON(`"followup_depth": 0` → `"depth": 0`),
응답 필드 설명, 관련 서술 문구를 모두 `depth`로 갱신했다.

#### `docs/api_reference.md`

5.2절(꼬리질문) 요청 파라미터 표, 응답 파라미터 표, BE 분기 로직 요약, 7절 설정값
표의 `followup_depth` 언급을 모두 `depth`로 갱신했다.

> `docs/AI_작업일지_0722.md`, `docs/AI_개발일지_0721.md`는 과거 작업 시점의 기록
> 문서이므로 그대로 두었다(당시 필드명이 `followup_depth`였다는 사실 자체가
> 기록으로서의 가치이므로 소급 수정하지 않음).

### 1.3 영향받는 파일

- `schemas/interview.py` — `FollowupRequest`/`FollowupResponse` 필드명 변경.
- `services/followup_service.py` — 필드 참조 전부 갱신.
- `README.md` — 꼬리질문 API 섹션 갱신.
- `docs/api_reference.md` — 꼬리질문 관련 표/서술 갱신.

`schemas/common.py`, `prompts/templates.py`, `services/question_service.py`,
`services/answer_service.py`, `services/rag_service.py` 등 다른 파일은 이번 작업과
무관하며 수정하지 않았다.

### 1.4 BE 영향 (Breaking Change)

`POST /api/v1/interviews/followup`의 **요청**과 **응답** 양쪽 모두에서
`followup_depth` 필드명이 `depth`로 바뀌었다. BE는 요청을 보낼 때와 응답을 받을 때
둘 다 필드명을 `depth`로 맞춰야 한다.

**요청 예시 (변경 후)**

```json
{
  "user_id": 1,
  "ai_interview_id": 100,
  "parent_question": "React에서 상태 관리를 어떻게 했나요?",
  "rubric": ["Redux 도입 이유를 설명했는가", "다른 대안과 비교했는가"],
  "user_answer": "Redux를 썼습니다.",
  "interview_type": "tech",
  "depth": 0,
  "resume_id": 1,
  "cover_letter_id": 1,
  "github_repo_id": 1
}
```

**응답 예시 (변경 후)**

```json
{
  "ai_interview_id": 100,
  "rubric_results": [
    {"criterion": "Redux 도입 이유를 설명했는가", "passed": false, "reason": "이유 언급 없음"}
  ],
  "all_passed": false,
  "followup_question": "왜 Redux를 선택하셨나요? 다른 상태 관리 라이브러리와 비교해보셨나요?",
  "depth": 1,
  "capped": false
}
```

BE가 요청 시 여전히 `followup_depth`로 보내면 pydantic이 이를 인식하지 못해
`depth`가 기본값 `0`으로 처리되고(요청 스키마는 `Field(0, ...)`라 422는 나지 않고
조용히 기본값으로 대체됨), 응답을 받을 때 기존처럼 `followup_depth` 키를 읽으려
하면 이번엔 반대로 BE 쪽 Jackson 필드가 채워지지 않는다. 두 방향 모두 반드시
`depth`로 맞춰야 한다.

### 1.5 검증 방법

- `python -m py_compile schemas/interview.py services/followup_service.py` —
  문법 오류 없음 확인.
- 임시 venv(`pydantic==2.9.2`, chromadb/GMS 등 무거운 의존성 없이 스키마 계층만
  검증)에서 `FollowupRequest`/`FollowupResponse`를 실제 값으로 인스턴스화해 확인:
  - `FollowupRequest(..., depth=1)` 생성 후 `model_dump()` 결과에 `depth` 키가
    있고 `followup_depth` 키는 없음을 확인.
  - `FollowupResponse(..., depth=2, capped=False)` 생성 후 `model_dump()`/
    `model_dump_json()` 모두에서 `depth` 키만 존재하고 `followup_depth`는 없음을
    확인(직렬화 결과: `{"ai_interview_id":100,"rubric_results":[],"all_passed":true,
    "followup_question":null,"depth":2,"capped":false}`).
- `grep -r followup_depth schemas/interview.py services/followup_service.py` —
  주석(이번 rename을 설명하는 문구 자체에 등장하는 `followup_depth`라는 단어)을
  제외하면 `req.followup_depth`/`followup_depth=` 형태의 실제 필드 참조는 하나도
  남아있지 않음을 확인.
- 실제 GMS LLM 호출을 통한 통합 테스트는 수행하지 않음(`.env`의 GMS 키 필요).
  BE/QA 단계에서 다음을 확인해야 한다:
  1. `/followup` 요청 시 `depth` 필드로 보냈을 때 정상적으로 상한 체크가
     동작하는지(예: `depth=2`, `config.max_followup_per_question=2`로 요청 시
     `capped=true`로 즉시 종료되는지).
  2. 응답의 `depth` 값을 BE가 정상적으로 역직렬화해, 다음 `/followup` 요청에
     그대로 실어 보내는 왕복(round-trip)이 끊기지 않는지.

## 2. 구조화 분석 문서(임베딩) 지원 — 하위 호환

> 대상: `POST /api/v1/embeddings` (`items[].content` 파싱 방식 확장),
> `services/rag_service.py`(질문 생성/꼬리질문 프롬프트에서 신규 메타데이터 활용)

### 2.1 작업 배경

기존에는 BE가 `POST /api/v1/embeddings`로 보내는 각 문서(`EmbeddingItem.content`)가
그냥 "분석 결과 텍스트" 정도의 평문이었고, AI 서비스가 `_split_text()`로 500자 단위
슬라이딩 윈도우 청킹을 해서 Chroma에 저장했다.

이제 BE가 이력서/자소서/GitHub 분석을 할 때 별도의 "분석 LLM"을 한 번 더 돌려서,
이미 의미 단위로 청킹되고 풍부한 메타데이터(역량, 면접 질문 주제, 키워드, 불확실한
점 등)가 붙은 구조화된 JSON을 만들어 넘겨주는 방식으로 전환한다. 이 구조화된 JSON은
FastAPI가 자동으로 검증해주는 요청 바디가 아니라 **`EmbeddingItem.content` 필드
안에 문자열(str)로 그대로 들어온다**(분석 LLM의 출력 자체가 텍스트이기 때문). 그래서
AI 서비스가 직접 `json.loads()`로 파싱해서 사용해야 한다.

이번 작업 목표는 이 새 구조화 포맷을 파싱해서 청크 단위로 Chroma에 저장하고,
질문 생성/꼬리질문 프롬프트에도 이 메타데이터(특히 `question_topics`,
`uncertainties`)를 실제로 활용하도록 만드는 것이다 — 임베딩 저장과 질문 생성 활용을
한 작업 범위로 함께 처리했다.

`GITHUB` 문서 유형은 이력서/자소서와 달리 아직 정식 스펙 문서가 없고, 실제 응답
샘플 1건만 확보한 상태였다. 스펙 문서와 실제 샘플 데이터를 대조해보니 일부
불일치가 있었다(2.6절 참고) — 이 불일치를 흡수할 수 있도록 파싱 로직을 의도적으로
느슨하게 설계했다.

### 2.2 확정된 설계 방향

1. `EmbeddingItem.content`의 타입은 그대로 `str`로 유지한다(FastAPI 요청 스키마
   변경 없음). AI 서비스가 직접 `json.loads()`로 파싱한다.
2. 새 포맷/기존 평문 **둘 다 지원**(하위 호환): `content`를 `json.loads()` 시도해
   성공하고 결과 dict에 `"embedding_documents"` 키가 있으면 새 포맷, 아니면(파싱
   실패 또는 키 없음) 기존 평문 청킹 경로를 그대로 탄다. BE가 포맷 버전을 명시적으로
   알려주기로 확정되지 않았으므로, 내용 기반 자동 판별을 택했다.
3. 새 포맷에서는 `embedding_documents[]`의 각 항목 = Chroma 문서 1개.
   `embedding_text`만 임베딩 대상이고 나머지는 전부 metadata.
4. Chroma metadata는 str/int/float/bool 같은 flat 값만 허용하므로: 문자열 리스트
   (`competencies`/`keywords`/`uncertainties`)는 콤마 join, 리스트-of-객체/중첩
   객체(`question_topics`/`details`)는 `json.dumps(ensure_ascii=False)`로
   문자열화(사용 시 `json.loads()`로 복원).
5. Chroma 문서 id = `f"u{user_id}:{chunk_id}"`(BE가 준 `chunk_id`에 `user_id`
   prefix를 붙여 사용자 간 충돌 방지).
6. 기존 문서 단위 삭제 로직(`delete_document_embedding()`)은 수정하지 않았다 —
   이미 user_id/doc_type/target_id 세 조건으로 삭제 범위를 잡고 있어 새 포맷에서도
   그대로 정합성이 유지된다.
7. `document_summary`/`cross_document_insights`(청크 단위가 아니라 문서 전체/문서
   간 요약)는 이번 작업에서 검색 가능한 별도 Chroma 문서로 만들지 않는다 — RAG에서
   어떻게 활용할지 아직 결정되지 않았기 때문. 파싱은 해두되(구조 검증 겸 향후 확장
   대비) 저장/사용 로직 없이 로그로만 남긴다.

### 2.3 변경 사항

#### `schemas/analysis_document.py` (신규)

`EmbeddingItem.content`를 파싱한 *이후*의 내부 데이터 구조를 표현하는 pydantic
모델. FastAPI 요청 바디 검증과는 무관하며, 서비스 레이어 내부에서만 쓰인다.

- `EmbeddingDocumentChunk`: `chunk_id`(필수), `parent_id`/`experience_id`/`title`/
  `summary`(선택), `competencies`/`keywords`/`uncertainties`(`list[str]`),
  `question_topics`(`list[dict[str, Any]]`), `embedding_text`(str),
  `details`(`dict[str, Any]` — 문서 유형별 내부 구조가 다르고 GitHub는 스펙조차
  미확정이라 통짜 dict로 받음). `chunk_type`을 포함해 "enum처럼 보이는" 필드는
  전부 `str`/`list[str]`/`dict`로 느슨하게 타입을 둬서, 문서화되지 않은 새 값이
  와도 검증 실패로 요청 전체가 튕기지 않게 했다(2.6절 근거). `field_validator`로
  `competencies`/`keywords`/`uncertainties`/`question_topics`/`details`가 None이거나
  기대 타입이 아니어도 빈 리스트/dict로 방어한다.
- `AnalysisDocument`: `schema_version`/`document_type`(선택),
  `document_summary`/`cross_document_insights`(`Any | None` — 구조를 강제하지
  않음, GitHub처럼 아예 없거나 다른 구조일 수 있어 `.get()` 등 방어적 접근만
  허용), `embedding_documents`(`list[dict[str, Any]]` — 청크 하나가 스펙과 안
  맞아도 문서 전체가 함께 버려지지 않도록, 여기서는 원시 dict로만 받고 청크별
  검증은 서비스 레이어에서 개별적으로 수행).
- `AnalysisDocumentError`: "새 포맷인 것은 확실한데(`embedding_documents` 키
  존재) 구조 자체가 명백히 손상된"(예: 그 값이 리스트가 아님) 경우에만 발생시키는
  전용 예외. 애매한 파싱 실패(JSON 자체가 안 되거나 키가 없음)는 이 예외를 던지지
  않고 조용히 평문 경로로 fallback한다.
- 두 모델 모두 `model_config = ConfigDict(extra="ignore")` — 정의되지 않은 필드가
  섞여 있어도(2.6절의 스펙-실데이터 불일치처럼) 파싱이 깨지지 않는다.

#### `services/embedding_service.py`

- `_try_parse_analysis_document(content)`: `content`가 새 포맷인지 판별. 코드펜스
  (` ```json ... ``` `) 방어는 `core/gms_client.py`의 `_safe_json_parse()`와 동일한
  이유(분석 LLM 출력도 결국 LLM 출력)로 최소한만 반복 구현했다(도메인이 달라 그
  함수를 직접 재사용하지 않음). `embedding_documents` 키가 있는데 값이 리스트가
  아니면 `AnalysisDocumentError`를 던진다.
- `_make_structured_id(user_id, chunk_id)`: `f"u{user_id}:{chunk_id}"`.
- `_build_chunk_metadata(user_id, item, chunk)`: 청크 metadata 평탄화(2.2절 4번
  설계 반영). 기존 평문 청크와 동일한 4개 키(`user_id`/`doc_type`/`target_id`/
  `title`)는 그대로 유지해 `rag_service.py`의 필터/출처 표시가 포맷 구분 없이
  동작하게 했고, 청크 자체 제목은 `chunk_title`이라는 별도 키로 구분했다(문서
  전체 `title`과 의미가 다르므로).
- `_build_structured_chunks(user_id, item, document)`: `embedding_documents`의
  각 원시 dict를 `EmbeddingDocumentChunk.model_validate()`로 개별 검증 —
  실패하면 그 청크만 로그 남기고 스킵, 나머지 청크는 정상 처리(문서 전체가
  함께 버려지지 않음). `document_summary`가 dict면 "파싱됨(의도적으로 임베딩
  안 함)"이라는 로그만 남긴다.
- `_build_plain_text_chunks(user_id, item)`: 기존에 `embed_user_documents()`
  안에 인라인으로 있던 평문 청킹 로직을 그대로 추출(동작 변경 없음).
- `embed_user_documents()`: 아이템마다 `_try_parse_analysis_document()`로 판별해
  `_build_structured_chunks()`/`_build_plain_text_chunks()` 중 하나로 분기하도록
  수정. 문서 단위 삭제(`delete_document_embedding`) 호출은 그대로 두었다(2.2절
  6번) — 삭제 범위가 chunk id 스킴과 무관하게 user_id/doc_type/target_id로만
  잡히므로, 재분석 시 청크 구성이 통째로 바뀌어도(예: 평문 5청크 → 구조화
  8청크) 이전 청크가 유령으로 남지 않는다.
- `_split_text()`/`_make_id()`/`delete_document_embedding()`/
  `delete_user_embeddings()`는 수정하지 않았다(하위 호환 경로에서 계속 사용).

#### `routers/embedding.py`

`AnalysisDocumentError`를 `Exception`(500) 처리보다 먼저 잡아 400으로 응답하도록
분기 추가. "명백히 손상된 구조화 포맷"만 이 경로를 타며, 애매한 파싱 실패는
`embed_user_documents()` 내부에서 이미 평문으로 처리되므로 여기까지 오지 않는다.

#### `services/rag_service.py`

- `_parse_json_metadata(raw)`: `json.dumps()`로 저장해둔 metadata 값(주로
  `question_topics`)을 복원. 값이 없거나(기존 평문 청크) JSON이 아니면 조용히
  빈 리스트를 반환해 RAG 조회 자체를 막지 않는다.
- `_rows_to_contexts()`: 반환 dict에 `question_topics`/`uncertainties` 두 키를
  추가(기존 평문 청크는 항상 빈 값).
- `format_context()`: 청크에 `question_topics`/`uncertainties`가 있으면 문서
  블록 아래에 "(면접관이 확인하면 좋은 주제: ...)", "(추가로 확인이 필요한 부분:
  ...)" 문구를 덧붙인다. `prompts/templates.py`의 `build_question_prompt()`/
  `build_followup_prompt()`는 이 함수의 반환값을 그대로 "## 지원자 문서(RAG 검색
  결과)" 섹션에 삽입하므로, 두 프롬프트 빌더의 시그니처나 `services/
  question_service.py`/`services/followup_service.py`의 호출부는 전혀 건드리지
  않고도 신규 메타데이터가 프롬프트에 자연스럽게 녹아들게 했다.

#### `README.md`, `docs/api_reference.md`

"1. 임베딩 저장" 섹션에 구조화 포맷 지원 안내(요청 스키마 자체는 안 바뀜, 자동
판별, 하위 호환)를 추가했다. `docs/api_reference.md`에는 `embedding_documents[]`
청크 필드 표(3.1.1절 신설), metadata 평탄화 규칙, GitHub 스펙 미확정 관련
주의사항, 신규 400 에러 케이스(`AnalysisDocumentError`)를 추가했다.

### 2.4 영향받는 파일

- `schemas/analysis_document.py` — 신규 파일.
- `services/embedding_service.py` — 파싱/분기 로직 추가, 청크 빌더 함수 분리.
- `routers/embedding.py` — `AnalysisDocumentError` → 400 매핑 추가.
- `services/rag_service.py` — `question_topics`/`uncertainties` 프롬프트 노출.
- `README.md`, `docs/api_reference.md` — 임베딩 섹션 갱신.

`schemas/embedding.py`(`EmbedRequest`/`EmbeddingItem` 요청 스키마 자체),
`prompts/templates.py`, `services/question_service.py`,
`services/followup_service.py`, `services/answer_service.py`,
`db/chroma.py`는 이번 작업과 무관하며 수정하지 않았다.

### 2.5 BE 영향

**`EmbedRequest`/`EmbeddingItem` 요청 스키마 자체는 변경 없음 — Breaking Change
아니다.** `content`(str) 안에 새 구조화 JSON을 문자열로 실어 보내기만 하면 AI
서비스가 자동으로 인식한다. 기존처럼 평문을 보내는 것도 그대로 지원되므로 BE가
당장 이 포맷으로 마이그레이션하지 않아도 기존 연동은 깨지지 않는다.

다만 BE 팀과 공유해야 할 사항:

1. **GitHub 쪽 enum이 아직 미확정**: `chunk_type`/`competencies`/`question_type`
   값이 정식 스펙 문서에 없는 것들(`COMMIT_HISTORY`, `VERSION_CONTROL`,
   `CLEAN_CODE`, `CODE_QUALITY` 등)이 실제 샘플에 이미 등장했다. AI 서비스는 이
   값들을 str로 그대로 받아 저장하므로 새 값이 추가돼도 요청이 실패하지 않지만,
   BE/분석 LLM 쪽에서 이 값들의 최종 스펙이 확정되면 공유가 필요하다.
2. **스펙 문서와 실제 데이터 불일치**: 스펙 문서는 `technologies.evidence`/
   `problems_and_solutions.evidence`/`results.evidence`를 "사용하지 않음"이라고
   명시했지만, 실제 GitHub 샘플에는 이 필드들이 들어있었다. AI 서비스는 `details`를
   통째로 opaque하게 저장하므로 이 필드가 있든 없든 동작에 문제는 없지만, 스펙과
   실제 운영 데이터가 다르다는 사실 자체는 BE/분석 LLM 팀이 인지해야 한다.
3. 신규 400 에러 케이스: `content`가 새 포맷인 것은 확실한데(`embedding_documents`
   키 존재) 그 값이 리스트가 아닌 등 구조 자체가 손상된 경우 400을 반환한다
   (`docs/api_reference.md` 3.1절 에러 표 참고).

### 2.6 확인 필요 / 가정 사항

- GitHub `document_type` 값이 정확히 `"GITHUB"`인지 미확인(이력서/자소서
  `"RESUME"`/`"COVER_LETTER"`과의 명명 패턴에서 유추한 추정값). AI 서비스 코드
  자체는 이 필드를 로깅 외 용도로 사용하지 않으므로 값이 달라도 동작에는 영향
  없다.
- GitHub `document_summary`/`cross_document_insights` 존재 여부와 구조 미확인
  (받은 샘플이 JSON 중간부터 시작해 확인 못함) — 코드는 `.get()` 기반 방어적
  접근만 하므로 없어도 예외 없이 스킵된다(2.7절 검증 결과 참고).
- `EmbeddingDocumentChunk.details.team_size`의 실제 타입(문자열/숫자) 미확정 —
  `details`를 통짜 dict로 저장하므로 이번 작업에서는 영향 없음(향후 `details`
  내부 필드를 직접 파싱하는 코드가 추가될 때 재확인 필요).

### 2.7 검증 방법

- `python -m py_compile schemas/analysis_document.py services/embedding_service.py routers/embedding.py services/rag_service.py` — 문법 오류 없음 확인.
- 임시 venv(`pydantic==2.9.2`, chromadb 미설치 환경)에서 `db.chroma`를 최소
  스텁(업서트 호출을 기록하는 가짜 컬렉션)으로 대체해 `embed_user_documents()`를
  실제로 호출하는 스크립트로 다음을 확인(전부 통과):
  1. 이력서 1건(구조화, 청크 1개) + 자소서 1건(구조화, 청크 1개) + GitHub 1건
     (구조화, 청크 2개 — `chunk_type="COMMIT_HISTORY"`처럼 스펙에 없는 값과
     `technologies[].evidence`처럼 "사용 안 함"이라던 필드를 일부러 포함) +
     이력서 1건(기존 평문)을 한 요청에 담아 호출 → `embedded_items=4`,
     `chunk_count=5`(1+1+2+1)로 정확히 집계됨을 확인.
  2. 반환된 Chroma id가 설계대로 생성됨을 확인: 구조화 청크는
     `u{user_id}:{chunk_id}`(예: `u42:resume_project_1`, `u42:gh_commit_1`),
     평문 청크는 기존 스킴(`u{user_id}:{doc_type}:{target_id}:{순번}`)을 그대로
     유지.
  3. 모든 metadata 값이 str/int/float/bool(flat)인지 전수 검사 — 통과(리스트/dict
     가 섞여 들어가면 실제 Chroma에서 예외가 나므로 이 검증이 핵심).
  4. `competencies`/`keywords`/`uncertainties`가 콤마로 join된 문자열로,
     `question_topics`/`details`가 `json.dumps()` 문자열로 저장되고,
     `json.loads()`로 원래 구조(예: `details.organization`, GitHub
     `details.source_type`/`technologies[].evidence`)가 그대로 복원됨을 확인.
  5. GitHub 샘플의 `chunk_type="COMMIT_HISTORY"`, `competencies=["VERSION_CONTROL",
     "CLEAN_CODE"]`처럼 스펙 문서의 "공통 enum" 목록에 없는 값도 예외 없이 그대로
     저장됨을 확인(Enum이 아니라 str로 받은 설계가 의도대로 동작).
  6. 기존 평문 `content`도 여전히 정상 동작하고(`chunk_index` 메타데이터 유지),
     구조화 포맷 전용 키(`chunk_id` 등)는 생성되지 않음을 확인.
  7. `embedding_documents`가 리스트가 아닌 손상된 구조(`{"embedding_documents":
     "이건 리스트가 아님"}`)를 넣으면 `AnalysisDocumentError`가 실제로 발생함을
     확인(routers/embedding.py에서 400으로 매핑되는 지점).
  8. `services/rag_service.py`의 `_rows_to_contexts()`/`format_context()`에
     위 3단계에서 만들어진 metadata를 그대로 넣어, 반환된 프롬프트 텍스트에
     "(면접관이 확인하면 좋은 주제: MSA 분리 기준(...))", "(추가로 확인이 필요한
     부분: 트래픽 규모 미상, 장애 대응 경험 불명확)" 문구가 실제로 포함됨을 확인.
- 실제 Chroma(SentenceTransformer 임베딩 모델)/GMS 연동 통합 테스트는 수행하지
  않음(모델 다운로드, `.env`의 GMS 키 필요). BE/QA 단계에서 다음을 확인해야 한다:
  1. 실제 분석 LLM이 만든 GitHub JSON을 그대로 흘려보냈을 때도 이번 작업의
     "청크 단위 방어적 파싱"(청크 하나가 실패해도 나머지는 저장됨)이 기대대로
     동작하는지.
  2. 질문 생성(`/questions`)/꼬리질문(`/followup`) 응답에서, 구조화 포맷으로
     저장된 문서를 근거로 한 질문이 `question_topics`/`uncertainties`를 반영한
     듯한 더 구체적인 질문으로 실제로 이어지는지(정성적 확인).
