# AI 개발일지 0801 — 표정(face) 파이프라인 학습 완주 + teacher 신뢰도 검증

**작업 환경**: 윈도우(RTX 4050) → 맥북(M5 Pro 24GB) 이전 후 첫 세션
**한 줄 요약**: 표정 MLP 학습을 처음부터 끝까지 완주해 모델 파일을 만들었다. 다만 그 과정에서
teacher(EMO-AffectNet) 라벨이 "지금 얼마나 긴장했나"보다 "이 사람 얼굴이 원래 어떻게 생겼나"를
주로 반영한다는 정량적 증거를 확보했고, 이것이 현재 성능(R²≈0.34)의 천장이라고 판단했다.

## 2. 코드 변경 사항 (전부 `ai-evaluate/` 안)

### 2-1. `core/face/aggregator.py` — `duration_sec` 제거 (116 → 115차원)

FI-V2가 전부 15초 고정이라 `duration_sec` 피처가 학습 데이터에서 사실상 상수(분산≈0)였다.
정규화 스케일러가 mean≈15/std≈0.5 같은 극단적으로 좁은 분포를 학습해버려, 실서비스에서
30~90초짜리 답변이 들어오면 z-score가 수십에 달해 **다른 피처 신호를 전부 덮어버리는** 지뢰가 된다.

- 제거한 것: 벡터 마지막 칸에 `duration_sec` **원값**을 싣는 부분
- 유지한 것: `duration_sec` 파라미터 자체 (분당 깜빡임 정규화 분모, 프레임수-길이 정합성 검증)
- **API 요청/응답 스키마 변경 없음** — 프론트/BE는 여전히 `duration_sec`을 그대로 보낸다

### 2-2. `training/face/make_pseudo_labels.py` — `person_id` 자동 파싱

기존에는 `person_id`를 전부 `"unknown"`으로 채워 넣어 `train_mlp.py --group-split`이 무의미했다
(= 같은 사람의 클립이 train/val 양쪽에 섞이는 데이터 누수).

`infer_person_id()` 추가:
- FI-V2 `{유튜브ID}.{클립번호}.mp4` → 유튜브ID를 person_id로
- 팀 촬영본 `{본인번호}_{그룹}_{순번}.mp4` → 본인번호를 person_id로
- 둘 다 아니면 stem 전체 (전부 "unknown"으로 뭉쳐 누수 나는 것보다 나음)

결과: 8,000 클립에서 고유 person 2,886명 확보 → group-split이 실제로 동작.

### 2-3. `training/face/make_pseudo_labels.py` — `FACE_TENSION_WEIGHTS` 의 Fear 1.0 → 0.5

sanity check 결과를 반영한 조정. 근거는 4절 참고.

### 2-4. `core/face/aggregator.py` — 피처 확장 (115 → 167차원)

blendshape 52개의 **후반-전반 구간 차이(bs_delta)** 52차원 추가.

기존에는 blendshape 52개를 전체 평균/표준편차 2개로만 뭉개서, "눈썹이 클립 내내 일정하게
올라가 있는 사람"과 "후반부에 갑자기 올라간 사람"이 거의 같은 벡터가 됐다. teacher는 LSTM이라
시간 순서를 그대로 보므로 이 둘을 구분하는데 student는 못 했다. EAR/deviation에만 있던
delta 개념(`ear_delta`/`dev_delta`)을 정보량이 가장 많은 blendshape 축에도 적용한 것.
(음성 쪽 `feature_extractor.py`에서 `f0_delta`/`f0_slope`로 같은 효과를 본 전례를 따름)

```
[0:52]    blendshape 평균
[52:104]  blendshape 표준편차
[104:156] blendshape 후반-전반 차이   ← 신규
[156:158] EAR 평균/표준편차
[158:160] MAR 평균/표준편차
[160:162] 정면이탈 평균/표준편차
[162]     분당 깜빡임
[163]     시선이탈 비율
[164:167] ear_delta, dev_delta, dev_slope
```

⚠️ **이 변경도 API 스키마에 영향이 없다.** 프론트는 프레임별 원본 값만 보내고, 벡터 조립은
전적으로 서버(`aggregator.py`)가 한다. 벡터 차원이 52 늘었지만 요청 형식은 한 글자도 안 바뀜.
이것이 "프론트가 미리 집계해서 보내지 않고 서버가 집계한다"는 기존 설계 결정이 값어치를 한 사례.

## 3. 학습 결과 3회 비교

| # | 조건 | 샘플 | 차원 | val loss | Pearson r | R² |
|---|---|---|---|---|---|---|
| 1 | Fear=1.0 | 2,000 | 115 | 0.0063 | 0.5676 | 0.3221 |
| 2 | Fear=0.5 | 2,000 | 115 | 0.0034 | 0.5483 | 0.3006 |
| 3 | Fear=0.5 + bs_delta + train추가 | 8,000 | 167 | — | **0.5871** | **0.3447** |

**해석 주의**:
- #1 → #2 의 r 하락(-0.019)은 val n=405 기준 표준오차(≈0.05) 안이라 통계적으로 유의하지 않다.
  val loss가 크게 줄어든 것도 성능 개선이 아니라 **라벨 분포 자체가 좁아진 결과**다
  (라벨 범위 [0.34, 0.94] → [0.55, 0.95]). baseline(분산)도 함께 줄었으므로 loss 절대값 비교는 무의미.
- #3 의 r 상승(+0.039)은 val n=1585 기준 표준오차(≈0.025)의 약 1.5배로, 실재할 가능성은 있으나
  큰 개선은 아니다. 게다가 **피처 확장과 데이터 증가를 동시에 바꿔서 기여도 분리가 안 된다.**
- #3 기준: MSE 0.002886 / baseline(라벨 분산) 0.004386 → "평균만 예측하는 게으른 모델"보다는
  확실히 낫지만 분산의 65%를 설명하지 못한다.

**⚠️ r 이 재는 것이 무엇인지 오해 금지**: 이 r은 "student MLP가 **teacher 라벨을** 얼마나 잘
따라하는가"이지 "실제 긴장도를 얼마나 정확히 맞히는가"가 아니다. teacher 라벨이 틀린 부분은
r이 1.0이 되어도 똑같이 틀린다(오히려 더 정확하게 틀린다). 현재 파이프라인에는 **사람이 검증한
정답이 단 하나도 없다.**

## 4. ⭐ 가장 중요한 발견 — teacher 라벨이 "상태"가 아니라 "생김새"를 재고 있다

### 4-1. Fear 오분류 (눈 크기)

sanity check로 Fear top 클립 5개를 실제 영상과 대조한 결과, 대부분 실제로 불안해 보이지 않고
**그냥 눈을 크게 뜨고 말하는 표현 스타일**이었다. 수치로도 확인됨:

| 구분 | EAR(눈 개폐 비율) 평균 |
|---|---|
| Fear top 5개 클립 | 0.53 ~ 0.71 |
| 전체 200개 샘플 평균 | 0.48 (p90 = 0.595) |

Fear/Surprise는 "눈 크게 뜨기" Action Unit을 공유해 FER 모델이 흔히 혼동하는 조합이다.
Fear가 전체의 4.4%뿐인데 가중치는 제일 높아(1.0) **tension 분포의 높은 쪽 꼬리를 사실상
이 오분류가 만들고 있었다.** → Fear 1.0 → 0.5로 조정(2-3절).

### 4-2. 분산 분해 — 결정적 증거

`label_final` 8,000개를 사람 기준으로 쪼갠 결과:

```
전체 라벨 분산       : 0.004650
사람 내부 분산(평균) : 0.000879   ← 같은 사람인데 클립마다 달라지는 정도 (18.9%)
사람 간 분산         : 0.003778   ← (81.1%)
```

**라벨 분산의 81%가 "사람 간" 차이다.** 즉 teacher 점수는 "이 사람이 지금 얼마나 긴장했나"보다
**"이 사람 얼굴이 원래 어떻게 생겼나"에 훨씬 크게 좌우된다.** 같은 사람이 다른 클립에서
다른 얘기를 하고 있어도 점수가 거의 안 변한다.

4-1의 "눈 큰 사람 = Fear"는 이 현상의 구체적 사례였고, **예외가 아니라 전반적 경향**이었던 것.

### 4-3. 이것이 왜 성능 천장인가

현재 검증은 group-split(사람 단위 분리)이라 검증셋에는 학습 때 한 번도 못 본 사람만 들어간다.
그런데 teacher 점수가 개인 고유 특성에 81% 묶여 있으면, student는 **처음 보는 얼굴의 그 특성을
맞힐 방법이 없다.** r이 0.6 근처에서 천장을 치는 것이 상당 부분 이걸로 설명된다.

→ **피처를 더 늘리거나 데이터를 더 부어도 이 천장은 잘 안 뚫린다.** 문제가 student 쪽이 아니라
라벨 쪽에 있기 때문. (실제로 데이터를 4배로 늘리고 피처를 52차원 추가했는데 r은 +0.04였다)

### 4-4. 공정성 리스크

성능 문제를 넘어서, **눈이 크거나 이목구비가 강한 사용자가 실제 긴장 여부와 무관하게
"긴장했다"는 피드백을 받을 수 있다.** 모의 면접 연습 도구라 채용 의사결정에 직접 쓰이진 않지만,
사용자 신뢰를 무너뜨릴 수 있는 문제다.

## 5. 기각한 대안들 (검토 근거 포함)

### 5-1. teacher 모델 교체 — 보류

HF를 직접 검색해 확인한 결과:

| 후보 | 판단 |
|---|---|
| valence-arousal 계열 (arousal이 개념적으로 tension에 더 가까움) | **없음.** 얼굴 영상 기반 VA 모델이 HF에 사실상 부재. 검색되는 건 음성(Wav2Vec2)/텍스트(DistilBERT) 기반이거나 모델 카드조차 없는 방치된 업로드 |
| `dima806/facial_emotions_image_detection` | Apache-2.0, 91% 정확도 주장, 2.8만 DL/월. 단 클래스별 지원 수가 3,596개씩 **정확히 균등**해 재균형 데이터셋으로 보임 → 91%는 "쉬운 시험" 점수일 가능성 |
| `trpakov/vit-face-expression` | FER2013 기준 71%. 현 teacher보다 나을 근거 없음 |
| HF 인기 상위 `vit-Facial-Expression-Recognition` 다수 | 하나의 튜토리얼을 따라 만든 개인 사본들이 대부분(FER2013 기반) |

**핵심**: 어떤 분류기로 바꾸든 "7클래스 확률 → tension 스칼라" 휴리스틱 매핑은 그대로 남고,
4-2에서 확인한 "개인 특성 반영" 문제도 그대로다. 분류기 교체는 병목의 절반만 건드린다.

### 5-2. `tension = 1 - P(Neutral) - P(Happiness)` — 검토했으나 기각

**착안**: 지금까지 눈으로 검증한 결과 Happiness는 잘 맞고 Neutral도 대체로 맞는 반면,
Fear는 거의 못 믿고 Anger는 반반(5-3 참고). 즉 **가중치가 0이 아닌 클래스들이 전부 검증 실패이거나
미검증**이고, 신뢰할 수 있다고 확인된 두 클래스는 가중치 0.0이라 점수에 직접 기여하지 않는다.
그렇다면 "어떤 부정 감정인지" 구분을 포기하고 "차분함/긍정 표정이 얼마나 없는지"로만 재면
못 믿는 구분에 의존하지 않게 된다. (확률 합이 1이므로 부정 5개에 전부 가중치 1.0을 주는 것과 동치)

**기각 사유**: 이 방식은 4-2의 문제를 **악화**시킨다. 이목구비가 강해 무표정인데도 Anger로
찍히는 사람의 경우, 현재는 Anger 가중치 0.4라 tension이 0.4 언저리에서 눌리지만, 1.0으로 올리면
0.8~1.0까지 올라간다. **잘못된 신호를 더 크게 증폭한다.**

### 5-3. "짜증/화남 중심 재설계" — sanity check 결과 보류

**착안(도메인 추론)**: 면접 상황에서 슬픔·놀람·공포는 나올 일이 별로 없고, 짜증·화남이 실제
감점 포인트이며 더 자주 나타난다. → Sadness/Surprise/Fear 가중치를 낮추고 Anger/Disgust를 올리자.

**sanity check 결과**: Anger 확신도 상위 클립들을 확인한 결과 **"반반"**.

**보류 사유**: 확신도가 **가장 높은** 클립에서 반반이면 나머지는 더 나쁠 가능성이 높다. 게다가
FER 모델의 Anger는 "미간 찌푸림"에 반응하는데, 이건 화난 표정이자 **골똘히 생각하는 표정**이다.
면접에서 어려운 질문을 받고 고민하는 사람이 정확히 이 표정을 짓는다 →
**"깊이 생각하는 사람이 감점되는" 모델**이 될 수 있어 정확히 반대 방향의 신호다.
(원작성자도 코드 주석에 "'분노'는 표정 오검출(찡그림 등)과 헷갈리기 쉬워 가중치를 낮췄다"고 기록)

**8,000개 top emotion 분포 (참고)**
```
Neutral 3300 / Happiness 2260 / Surprise 918 / Sadness 550 / Anger 456 / Fear 356 / Disgust 160
```
Anger+Disgust는 합쳐서 7.7%뿐이라, 여기에만 가중치를 몰면 tension 신호가 희박해져
라벨 분산이 더 줄고 학습이 어려워질 수 있다는 문제도 있다.

## 6. ⭐ 향후 개선 방안

### 6-1. (최우선, 재학습 불필요) 세션 내 상대 비교 — 개인 baseline 정규화

**문제**: 절대 점수는 분산의 81%가 개인 생김새다(4-2).

**착안**: 우리 서비스는 FI-V2에 없는 결정적 이점이 있다. **같은 사람이 한 세션에서 답변을 여러 개
한다.** 그러면 절대 점수 대신 **그 사람 자신의 평균 대비 편차**로 해석할 수 있다.

```
A씨(이목구비 강함): 6.8  6.9  6.7  5.5  7.0  6.8  6.9   (평균 6.66)
B씨(동안):          8.5  8.6  8.4  7.3  8.5  8.6  8.4   (평균 8.33)
```

절대값으로 보면 A씨는 "긴장도 높음", B씨는 "안정적"이지만 이건 실제 긴장 차이가 아니라 생김새
차이다. 반면 각자 자기 평균과 비교하면 **둘 다 4번 질문에서 1.1~1.2점 떨어진 것**이 똑같이 잡히고,
이 결론은 두 사람 모두에게 정확하다. 개인 baseline이 평균에 흡수되어 상쇄되기 때문.

**장점**
- 오염원의 81%를 구조적으로 제거
- **재학습 불필요**. MLP는 지금처럼 답변당 점수 하나를 내고, 세션 종료 후 후처리로 비교만 하면 됨
- 모의 면접 연습 도구라는 목적에도 "당신은 긴장한 편입니다"보다 "3번 질문에서 유독 흔들렸습니다"가
  더 유용

**한계**
- 처음부터 끝까지 고르게 긴장한 사람은 편차가 안 잡힘 (절대 수준 정보 상실)
- 답변이 1개뿐이면 비교 대상 없음

**⚠️ 구현 위치 문제**: FastAPI는 답변 하나씩 요청받는 stateless 구조라 세션 전체를 못 본다.
이 비교는 **BE나 프론트에서 해야 하는데 둘 다 우리 파트가 아니다.**
→ 현실적 대응: `ai-evaluate`는 지금처럼 답변당 점수만 내려주고(코드 변경 0),
`docs/SPRING_INTEGRATION.md`에 **"절대값 단독 노출은 개인 편차 때문에 권장하지 않으며,
세션 내 상대 비교를 권장한다"**는 근거와 함께 제안으로 기록. 채택 여부는 BE 담당자 판단.

### 6-2. (중요) 7클래스 확률을 CSV에 저장 — 실험 비용 1/20

현재는 최종 tension 값만 CSV에 저장하고 7클래스 확률을 버린다. 그래서 **가중치를 하나 바꿀 때마다
teacher를 처음부터 다시 돌려야 한다(8,000개 = 약 65분).**

`make_pseudo_labels.py`가 `prob_neutral, prob_happiness, ...` 컬럼을 함께 저장하도록 고치면,
이후 가중치 실험은 **build_dataset + train_mlp 3분**이면 끝난다.
한 번만 더 돌리면(65분) 이후 실험이 사실상 공짜가 되므로, 가중치 실험을 계속할 계획이라면
반드시 먼저 해둘 것. (3개 안 비교 시: 현재 방식 3시간 15분 → 개선 후 75분)

### 6-3. (근본 해결, 미착수) 사람이 매긴 gold 라벨 확보

현재 파이프라인에는 사람이 검증한 정답이 **하나도 없다**. 그래서 이 모델이 실제로 쓸 만한지
**아무도 모르는 상태**다. r이 아무리 올라도 그건 teacher를 잘 흉내낸다는 뜻일 뿐이다.

- 원래 계획: 팀원 촬영본을 도메인 검증용 holdout으로 사용 (`표정분석_촬영가이드.pdf` 작성 완료)
- **2026-08-01 현재 팀원 촬영은 진행되지 않을 전망** → 대안 필요
- 대안 후보: FI-V2 공식 annotation(interview/comfortable 등 라벨) 확보. HF 미러에는 pickle이
  없어 공식 ChaLearn 사이트 가입 필요. 확보되면 **teacher 신뢰도를 처음으로 정량 검증** 가능
- 다른 후보: RecruitView 데이터셋 (HF 접근 신청 완료, 교신저자 수동 검토 대기 중)

### 6-4. (표시 단계) 정밀한 숫자 노출 금지

R²=0.34면 분산의 66%를 설명하지 못한다. "긴장도 7.2점" 같은 정밀한 숫자로 보여주면 사용자가
실제보다 훨씬 신뢰할 만한 지표로 오해한다. → 대략적인 구간/등급으로만 노출 권장.

## 7. 결론 — 이 모델을 지금 써도 되는가

**쓸 수 있는 조건부 상태**다.

**써도 되는 이유**
- 503(모델 없음)보다는 낫다. R²=0.34는 무작위가 아니며 실제 신호와 방향이 맞는다
- 캡스톤 맥락상 채용 의사결정이 아닌 **모의 면접 연습 도구**다
- BE 연동 테스트에는 지금 모델로 충분하다 (스키마/파이프라인 확인이 목적이라 정확도와 무관)

**그대로 쓰면 안 되는 이유**
- 정밀한 숫자로 노출하면 과신 유발 (6-4)
- 개인 생김새가 점수의 상당 부분을 차지 → 공정성 문제 (4-4)
- 실제 면접 상황(경직된 자세, 정장, 카메라 앞 긴장)에서 **한 번도 검증된 적 없음**

**권장**: BE 연동은 이 모델로 진행하되, 사용자 노출 시에는 (a) 등급화 표시, (b) 세션 내 상대 비교를
적용한다. 그리고 gold 라벨 확보(6-3) 없이는 "이 모델이 정확하다"고 말하지 않는다.

## 9. 별건 — `ai/` (질문 생성 서버) 수정안 (미적용, 파일만 전달)

**문제**: 첫 질문 생성 시 질문 7개 + 루브릭 2개로 바꾸려 했으나 동작하지 않아
`question_service.py`에 `count = 7` 하드코딩해둔 상태였음.

**원인**: `be/` 전체를 검색해도 `question_count`를 요청에 실어 보내는 코드가 **없다.**
즉 `req.question_count`는 항상 `None`이고 `req.question_count or settings.question_count`는
사실상 늘 `settings.question_count`로 귀결되는데, `config.py`의 기본값이 **여전히 5**였다.
로직 문제가 아니라 설정값 누락이었음.

**수정안 (3파일)**
- `config.py`: `question_count` 5 → 7, `rubric_max_count` 3 → 2 (min=max=2로 "딱 2개" 고정)
- `services/question_service.py`: `count = 7` 하드코딩 제거 → `req.question_count or settings.question_count` 복원
  (BE가 나중에 실제로 보내기 시작하면 그 값이 자동 우선 적용됨)
- `prompts/templates.py`: `rubric_min == rubric_max`일 때 "2~2개" 대신 **"정확히 2개"**로
  문구를 바꾸는 헬퍼 추가 (안 그러면 LLM에 이상한 지시가 나감)

**⚠️ 남은 한계**: "무조건 7개"는 보장되지 않는다. 프롬프트로 "정확히 7개"를 지시하고
`raw_questions[:count]`로 자르지만, LLM이 6개만 만들거나 일부 항목이 형식을 어겨 필터링되면
그대로 6개가 나간다. **부족분 재시도/보정 로직이 없다**(원래부터 그랬음, 이번 변경과 무관).
필요하면 `len(questions) != count` 시 로그 경고 또는 GMS 재호출 보정을 추가할 것. → **추후 과제**

**주의**: 이 수정은 `ai/` 안에서 완결되며 **`be/` 수정이 전혀 필요 없다.** 질문 개수도 루브릭 개수도
BE가 지시하는 값이 아니라 `ai/`가 프롬프트에 박아넣는 값이고, BE는 결과를 받기만 한다.
